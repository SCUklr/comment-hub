# 审核模式改造方案：从「先审后发」改为「先发后审」

> 创建时间：2026-06-12  
> 当前代码状态：评论 / 回复创建后 `audit_status = 0`（待审核），仅作者可见；审核通过后变为 `audit_status = 1`，对所有用户可见。  
> 目标状态：评论 / 回复创建后默认 `audit_status = 1`（直接可见），审核回调可将其改为 `audit_status = 2`（拒绝 / 隐藏）。

---

## 一、为什么要改

当前实现属于 **先审后发**：用户发完评论/回复后，非作者用户在审核通过前看不到任何内容。

如果产品策略希望内容**先发出来**，后续再由人工或机器审核发现并隐藏违规内容，则需要改为 **先发后审**。

---

## 二、核心改动思路

1. 创建评论 / 回复时，默认 `audit_status = 1`（已通过、可见）。
2. 审核回调可将状态改为 `audit_status = 2`（拒绝、隐藏）。
3. 列表查询只展示 `audit_status = 1` 的内容；`audit_status = 2` 的内容按产品策略决定是否对作者可见。
4. 内容被拒绝后，需要同步清理相关派生数据：热评缓存、回复数、用户评论索引、通知等。

---

## 三、详细改动清单

### 3.1 创建评论 / 回复时默认状态改为「已通过」

**涉及文件**：
- `ssp-comment-center-domain/src/main/java/com/ssp/comment/CommentDomainService.java`

**具体改动**：
- `createComment()` 中 `entity.setAuditStatus(0);` → `entity.setAuditStatus(1);`
- `createReply()` 中 `entity.setAuditStatus(0);` → `entity.setAuditStatus(1);`

**可选处理**：
- 创建时是否同时写入 `component_comment_audit` 记录：
  - 方案 A：写入一条 `audit_status = 1` 的初始审核记录，表示「默认通过」。
  - 方案 B：创建时不写审核记录，只有后续真正被审核时才产生记录。
  - **推荐方案 A**，这样 `/api/comment/audit/history` 对每条内容都有完整历史。

---

### 3.2 列表查询过滤条件调整

当前 SQL 过滤条件：

```sql
audit_status = 1 
or (comment_user_id = #{currentUserId} and audit_status != 1)
```

含义：非作者只能看已通过内容；作者可以看到自己的待审核 / 拒绝内容。

改为先发后审（拒绝即隐藏）后，有两种产品策略可选：

#### 策略 A：拒绝内容对所有人隐藏（包括作者）

```sql
audit_status = 1
```

**优点**：实现最简单，审核拒绝即彻底消失。  
**缺点**：作者无法感知自己的内容被屏蔽。

#### 策略 B：拒绝内容仅对作者可见（可提示「已被屏蔽」）

```sql
audit_status = 1 
or (comment_user_id = #{currentUserId} and audit_status = 2)
```

**优点**：作者能看到自己的内容被审核拒绝及原因。  
**缺点**：查询条件稍复杂，前端需要针对 `audit_status = 2` 做特殊展示。

**推荐策略 B**，更符合用户体验。

**涉及文件**：
- `ssp-comment-center-infrastructure/src/main/resources/mapper/CommentMapper.xml`
  - `countByObject`
  - `selectPageByObject`
  - `selectHotPageByObject`
  - `selectByIds`
- `ssp-comment-center-infrastructure/src/main/resources/mapper/ReplyMapper.xml`
  - `countByCommentAndParent`
  - `selectPageByCommentAndParent`
  - `selectByCommentIdsAndParent`

---

### 3.3 审核回调支持「通过 → 拒绝」的流转

当前 `CommentDomainService.handleAuditCallback()` 已经支持传入任意 `auditStatus` 并更新主表，所以理论上直接传 `auditStatus = 2` 即可。

但需要补充以下细节：

#### 3.3.1 事件命名调整（可选）

当前事件类名为 `CommentAuditPassedEvent`，在拒绝场景下语义不准确。

**建议**：改名为 `CommentAuditChangedEvent`，事件体中已携带 `auditStatus`，消费端按状态分支处理。

**涉及文件**：
- `ssp-comment-center-domain/src/main/java/com/ssp/comment/event/CommentAuditPassedEvent.java`
- 所有引用该事件的地方（Listener、DomainService）

#### 3.3.2 幂等性

当前每次回调都会 `insert` 一条新审核记录。先发后审场景下，一条内容可能被多次审核（先通过 → 后拒绝 → 再申诉通过），产生多条记录其实更符合「审核历史」语义，**无需改为 update**。

---

### 3.4 热评缓存清理

如果一条评论从 `audit_status = 1` 被改为 `2`，它可能仍然存在于 Redis 热评 ZSet 中。

**需要在拒绝时**：
- 从 `comment:hot:obj:{commentObjectId}:type:{commentType}` 中移除该评论 ID
- 可选：清理该对象对应的评论点赞数 Hash 缓存

**实现方式**：
- 在 `HotScoreUpdateListener` 中监听审核变更事件，当 `auditStatus = 2` 时执行 `ZSet.remove(targetId)`。
- 或新增一个专门的 `AuditStatusChangedListener` 统一处理拒绝后的副作用。

**涉及文件**：
- `ssp-comment-center-application/src/main/java/com/ssp/comment/listener/HotScoreUpdateListener.java`
- 或新增 `AuditStatusChangedListener.java`

---

### 3.5 回复数 `reply_count` 回退

如果一条回复先创建（已通过，父评论 `reply_count + 1`），后续审核被拒绝，那么这条回复实际上已不可见，父评论的 `reply_count` 应该 **-1**。

**改动点**：
- 在 `CommentDomainService.handleAuditCallback()` 中，当 `targetType = 2` 且 `auditStatus = 2` 时，调用 `commentRepository.updateReplyCount(commentId, -1)`。

**注意**：
- 需要防止重复拒绝导致 `reply_count` 被多次扣减。可以在回调时先查询当前主表 `audit_status`，只有从 `1` 变为 `2` 时才扣减。

---

### 3.6 用户评论索引标记删除

当前 `component_user_comment_index` 通过 `UserIndexUpdateListener` 异步维护。

如果内容被拒绝，建议将索引表里对应记录的 `is_delete` 置为 `1`，否则用户进入「我评论过的内容」列表会看到一条点进去不存在的记录。

**改动点**：
- 在 `UserIndexUpdateListener` 中监听审核变更事件。
- 当 `auditStatus = 2` 时，调用 `userCommentIndexRepository` 更新 `is_delete = 1`。

**涉及文件**：
- `ssp-comment-center-application/src/main/java/com/ssp/comment/listener/UserIndexUpdateListener.java`
- `ssp-comment-center-domain/src/main/java/com/ssp/comment/repository/UserCommentIndexRepository.java`
- `ssp-comment-center-infrastructure/src/main/java/com/ssp/comment/dao/persistance/UserCommentIndexRepositoryImpl.java`
- 对应 Mapper / XML

---

### 3.7 站内通知处理（可选）

如果评论 / 回复创建时已经发了通知（例如「有人回复了你」），后续审核拒绝时是否撤回通知？

**方案 A（简单）**：不撤回，用户点进去看不到具体内容。  
**方案 B（严谨）**：审核拒绝时，将相关通知标记为 `is_delete = 1` 或物理删除。

**推荐方案 A**，先发后审场景下通常不要求撤回已发通知。

---

## 四、数据迁移说明

改为先发后审时，**历史数据不需要修复**。因为：

- 当前历史数据 `audit_status = 0` 表示待审核，作者可见。
- 改造后新数据 `audit_status = 1` 表示直接可见。
- 历史数据可以保留原样，也可以通过已有的 `docs/05-database/migration-backfill-audit-20240612.sql` 把旧数据默认置为 `1`。

---

## 五、测试验证点

改造完成后需要验证：

1. 创建评论 / 回复后，未登录用户能立即看到（`audit_status = 1`）。
2. 审核回调 `auditStatus = 2` 后，非作者用户看不到该内容。
3. 拒绝后，热评列表中不再出现该评论。
4. 拒绝回复后，父评论的 `reply_count` 正确减少。
5. 拒绝后，「我评论过的内容」列表按策略 A/B 正确展示。
6. 审核历史接口 `/api/comment/audit/history` 能查到从通过到拒绝的完整记录。

---

## 六、推荐执行顺序

1. 修改 `CommentDomainService` 创建时默认状态为 `1`。
2. 修改 `CommentMapper.xml` / `ReplyMapper.xml` 的查询过滤条件（选策略 B）。
3. 在 `handleAuditCallback` 中补充拒绝时的副作用：
   - 回复数回退
   - 发布审核变更事件
4. 在 `HotScoreUpdateListener` / `UserIndexUpdateListener` 中处理拒绝事件。
5. 运行 `mvn clean compile -DskipTests` 编译验证。
6. 按 API 测试指南逐个接口验证。
