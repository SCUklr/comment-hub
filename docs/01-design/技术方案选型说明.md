# 技术方案选型说明

> 本文档说明 ssp-comment-center 关键技术选型的原因。本项目定位为评论中台，仅对外暴露 REST 接口，不附带前端展示工程。

---

## 一、后端核心技术选型

### 1.1 框架：Spring Boot 3.0.7 + Java 17

| 选型 | 说明 | 理由 |
|------|------|------|
| Spring Boot 3.x | 当前主流版本，支持 Jakarta EE 命名空间 | 与项目原有 `ssp-geek-commander` 设计蓝图保持一致；社区生态成熟，便于面试/教学讲解。 |
| Java 17 | LTS 版本 | 支持 Records、Pattern Matching、Sealed Classes 等新特性；与 Spring Boot 3.x 兼容。 |

### 1.2 数据库：MySQL 8.0

| 选型 | 说明 | 理由 |
|------|------|------|
| MySQL 8.0 | 关系型数据库 | 评论业务数据强关联（评论-回复-点赞），需要事务与一致性保障；MySQL 8.0 支持窗口函数、CTE、JSON 函数，便于后续复杂查询扩展。 |
| InnoDB | 存储引擎 | 支持行级锁、事务、MVCC，适合高并发读写与回滚场景。 |
| utf8mb4 | 字符集 | 支持 emoji 与特殊符号，满足评论内容多样性。 |

### 1.3 ORM：MyBatis 3.5

| 对比项 | MyBatis | JPA |
|--------|---------|-----|
| SQL 可控性 | ✅ 高，手写 XML | 中等，自动生成 |
| 分库分表友好度 | ✅ 高，可精确控制分片键 | 较低，复杂分片需额外适配 |
| 学习成本 | 中等 | 较高 |
| 团队熟悉度 | 假设更熟悉 | - |

**结论**：选用 MyBatis，原因是在分库分表场景下需要精确控制 SQL 与分片键，且项目规模不大，手写 XML 足以满足需求。

### 1.4 分库分表：ShardingSphere-JDBC 5.4.1

| 对比项 | ShardingSphere-JDBC | ShardingSphere-Proxy | 手动分表 |
|--------|---------------------|----------------------|---------|
| 侵入性 | 轻量，Jar 包引入 | 需独立中间件部署 | 极高，业务代码大量改造 |
| 性能 | 高，直连数据库 | 略低，多一跳代理 | 高 |
| 运维成本 | 低 | 高 | 中 |
| SQL 兼容性 | 好 | 更好 | 依赖实现 |

**结论**：选用 **ShardingSphere-JDBC**，理由是：
- 项目当前规模小，不需要独立 Proxy 中间件。
- 业务代码面向逻辑表开发，分片逻辑对应用层透明，便于演示和教学。
- 与现有 Spring Boot 3.x 集成简单，配置集中管理于 `application.yml`。

**分片策略**：
- 评论表：按 `comment_type` 分库（业务隔离），按 `comment_user_id` 分表。
- 回复表：按 `comment_id` 分库分表（同一评论的楼中楼落在同一分片）。
- 点赞表 / 用户索引表：按 `user_id` 分库分表（支撑用户维度高频反查）。

### 1.5 缓存：Redis + Redisson

| 对比项 | Redis（集群/单机） | 本地缓存（Caffeine/Guava） | 不用缓存 |
|--------|-------------------|---------------------------|---------|
| 共享性 | ✅ 多实例共享 | 单实例独享 | - |
| 点赞数一致性 | ✅ 最终一致 | 实例间不一致 | 强一致但数据库压力大 |
| 热榜排序 | ✅ ZSet 天然支持 | 需应用层排序 | 数据库排序压力大 |
| 复杂度 | 中 | 低 | 低 |

**结论**：选用 **Redis 单机 + Redisson 客户端**，理由是：
- 点赞数、用户点赞状态、热评 ZSet 需要跨实例共享，本地缓存无法满足。
- Redis ZSet 非常适合热评排序场景。
- Redisson 提供丰富的分布式数据结构（RMap、RScoredSortedSet、RBucket），虽当前未用作分布式锁，但预留了扩展能力。

**当前缓存结构**：

| 用途 | Key 模式 | 结构 |
|------|----------|------|
| 评论点赞数 | `comment:like:obj:{objectId}` | Hash |
| 回复点赞数 | `reply:like:obj:{objectId}` | Hash |
| 用户点赞状态 | `user:like:{userId}:target:{type}:{id}` | String |
| 热评排序 | `comment:hot:obj:{objectId}:type:{type}` | ZSet |

### 1.6 异步机制：Spring Event + `@Async`

| 对比项 | Spring Event | MQ（Kafka/RabbitMQ） | 同步调用 |
|--------|-------------|---------------------|---------|
| 复杂度 | 低 | 高 | 低 |
| 可靠性 | 中（内存事件，重启丢失） | 高（持久化） | 高 |
| 解耦性 | 中 | 高 | 低 |
| 适用阶段 | 演示/小型项目 | 生产大规模 | 非核心逻辑不推荐 |

**结论**：选用 **Spring Event + 自定义线程池**，理由是：
- 项目当前处于演示/教学阶段，无需引入 MQ 的运维复杂度。
- 缓存清理、热榜更新、用户索引维护等非核心逻辑可异步化，降低主链路延迟。
- 未来可平滑替换为 MQ：事件定义不变，仅监听器消费方式改变。

> ⚠️ 已知风险：事件发布未绑定事务提交，事务回滚后事件仍可能触发。详见《风险点与兜底策略.md》。

### 1.7 ID 生成：雪花算法

| 对比项 | 雪花算法 | 数据库自增 ID | UUID |
|--------|---------|--------------|------|
| 全局唯一 | ✅ | ❌（分片后冲突） | ✅ |
| 趋势递增 | ✅ | ✅ | ❌ |
| 可读性 | 好 | 好 | 差 |
| 分库分表友好 | ✅ | ❌ | ✅（但索引性能差） |

**结论**：选用 **雪花算法（自研 SnowflakeIdUtils）**，理由是分库分表环境下需要全局唯一、趋势递增的 ID，避免自增 ID 冲突。

## 二、不采用的方案及原因

| 不采用的方案 | 原因 |
|-------------|------|
| 分布式锁（Redisson RLock） | 当前点赞幂等可通过数据库唯一索引 `uk_user_target` 兜底；引入分布式锁会增加复杂度和死锁风险，且源码中虽已引入 Redisson 但未实际使用锁。 |
| TCC / Saga 分布式事务 | 项目无跨服务调用，本地 `@Transactional` 足以覆盖单次写操作。 |
| 本地消息表 / Binlog 监听 | 当前数据一致性要求可接受最终一致，Spring Event 已足够；消息表和 Canal 增加运维成本。 |
| Elasticsearch | 当前无全文搜索需求，MySQL LIKE 或后续扩展时再引入。 |
| Kafka / RabbitMQ | 当前事件量少，Spring Event 内存队列足够；MQ 作为未来扩展预留。 |
| 延迟双删 | 当前读多写少，且点赞缓存允许秒级不一致，未引入；若未来一致性要求提高可考虑。 |

## 三、部署架构

```
┌─────────────────────────────────────────┐
│  上游业务方（C 端 App、运营后台、网关等）  │
│  通过 HTTP 调用 /api/* 接入评论中台        │
└─────────────┬───────────────────────────┘
              │
┌─────────────▼───────────────────────────┐
│  Spring Boot 8080                         │
│  ├── CommentController / ReplyController  │
│  ├── CommentBizService                  │
│  ├── CommentDomainService               │
│  └── 异步事件监听（缓存/热榜）            │
└─────────────┬───────────────────────────┘
              │
    ┌─────────┴─────────┐
    ▼                   ▼
┌─────────┐      ┌─────────────┐
│ MySQL   │      │ Redis       │
│ 2库×4表 │      │ 单机/集群    │
└─────────┘      └─────────────┘
```

评论中台仅暴露 REST 接口，由上游业务方自行接入和呈现；用户身份通过 `X-User-Id` Header 从上游网关透传。
