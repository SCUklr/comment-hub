## 1. 项目一句话介绍

通用评论中心，支持评论/回复（楼中楼）/点赞/热评/审核状态机/站内通知/用户评论历史反查，基于 DDD 四层架构 + ShardingSphere 分库分表 + Redis 缓存，零外部私有依赖，独立可运行。

## 3. 数据库设计

### 3.1 6 张核心表

| 表名 | 职责 | 分片策略 |
|------|------|--------|
| `component_comment` | 一级评论主表 | **comment_object_id 分库分表(2库×4表)** |
| `component_comment_reply` | 回复 / 楼中楼表 | **comment_id 分库分表(2库×4表)** |
| `component_comment_like` | 点赞记录表 | **user_id 分库分表(2库×4表)** |
| `component_comment_audit` | 审核记录表 | 不分片，单表存储于默认库 |
| `component_user_comment_index` | 用户评论索引表 | **user_id 分库分表(2库×4表)** |
| `component_notification` | 站内通知表 | **user_id 分库分表(2库×4表)** |

> 分库分表建表脚本：`docs/05-database/ddl-sharding.sql`（5 张分片表各 2库×4表，共 40 张物理表；审核表为单表，合计 41 张）

### 3.2 表关系

```
内容对象（外部系统）
    │ 一对多
    ▼
component_comment（一级评论）
    │ 一对多
    ▼
component_comment_reply（回复 / 楼中楼）
    │
    │ 统一目标模型（target_id + target_type）
    ▼
component_comment_like（点赞）  component_comment_audit（审核）

component_user_comment_index（用户索引，独立维度，不直接关联主表）
component_notification（站内通知，按接收人分片）
```

## 4. 设计亮点（面试高频考点）

### 4.1 评论与回复的标准树形建模

- 评论表 `component_comment` 负责**对象维度**
- 回复表 `component_comment_reply` 负责**评论维度 + 树结构**
- `comment_id` 负责归属，`parent_reply_id` 负责树结构，两者解耦

### 4.2 评论列表批量组装，避免 N+1

- 先分页查评论
- 批量收集评论 ID，批量查一级回复
- 批量读 Redis 点赞数 Hash
- 应用层分组挂 `topReplies`

### 4.3 ShardingSphere-JDBC 分库分表

| 表 | 分库键 | 分表键 | 规模 |
|----|--------|--------|------|
| 评论表 | `comment_object_id` | `comment_object_id` | 2库 × 4表 |
| 回复表 | `comment_id` | `comment_id` | 2库 × 4表 |
| 点赞表 | `user_id` | `user_id` | 2库 × 4表 |
| 用户索引表 | `user_id` | `user_id` | 2库 × 4表 |
| 站内通知表 | `user_id` | `user_id` | 2库 × 4表 |

- 评论表按评论对象ID分片 → 同一对象下的评论落在同一物理分片，列表查询命中单分片
- 回复表按评论ID分片 → 同一评论的楼中楼数据落在同一分片，查询命中单分片
- 点赞/索引/通知按用户ID分片 → 支撑高频用户维度反查命中单分片
- 配置集中管理于 `application.yml`，业务代码面向逻辑表开发，零侵入

> 源码层通过 `CommentShardRouter` 显式体现路由思路，与 ShardingSphere INLINE 算法保持一致，便于面试讲解。

### 4.4 用户维度反查通过索引表承接

- "我评论过哪些"不命中主表分片键（主表按对象/评论维度分片）
- 单独设计 `component_user_comment_index`，以 `user_id` 为第一维度
- 主表继续按对象/评论维度分片，用户查询走索引表

### 4.5 Redis 缓存结构

| 缓存类型 | Key 模式 | 结构 | 用途 |
|----------|----------|------|------|
| 评论点赞数 | `comment:like:obj:{objectId}` | Hash | 批量读，避免 COUNT 聚合 |
| 回复点赞数 | `reply:like:obj:{objectId}` | Hash | 同上 |
| 用户点赞状态 | `user:like:{userId}:target:{type}:{id}` | String | 判断当前用户是否已赞 |
| 热评排序 | `comment:hot:obj:{objectId}:type:{type}` | ZSet | score=likeCount，取 Top N |

### 4.6 自研基础组件（零外部私有依赖）

| 组件 | 替代原依赖 | 位置 |
|------|-----------|------|
| `Result<T>` | `CommonResponse` | start/common |
| `PageResult<T>` | `PageResult` | start/common |
| `CheckUtil` | `CheckUtil` | start/common |
| `UserContext`（ThreadLocal） | `RequestContextUtil` | start/common |
| `SnowflakeIdUtils` | `SnowflakeIdUtils` | domain/common |
| `BizException` | `CommonBizException` | domain/common |

### 4.7 Spring Event 异步事件驱动

4 个监听器：通知生成、用户索引更新、热评分数计算、缓存失效，解耦核心写路径与附属逻辑。

## 6. 踩坑记录（面试加分项）

| 坑 | 根因 | 解法 |
|----|------|------|
| 雪花 ID 精度丢失 | `744087244154953728` 超出 JS `Number.MAX_SAFE_INTEGER`（2^53-1），JSON.parse 后尾部失真 | Jackson 全局将 boxed `Long` 序列化为字符串，前端按 string 处理 |
| 编辑/删除缺权限校验 | edit 接口未传 currentUserId，delete SQL 无归属条件 | controller 透传 userId → domain `checkOwner` 校验 |
| MySQL 8 `Public Key Retrieval` | caching_sha2_password 插件非 SSL 连接需公钥获取 | JDBC URL 加 `allowPublicKeyRetrieval=true` |
| 宿主机 MySQL 占 3306 | Homebrew launchd 服务与 Docker 容器竞争端口 | `launchctl unload ~/Library/LaunchAgents/homebrew.mxcl.mysql.plist` |
