- 更适合豆包、ChatGPT、Cursor、Claude 等 LLM 快速阅读与检索

## 1. 项目目标

评论平台是一个通用评论系统，目标是支持：

- 对任意内容对象发表评论
- 对评论进行回复，支持楼中楼
- 评论 / 回复的删除、编辑
- 评论置顶
- 点赞 / 取消点赞
- 热评列表
- 内容审核回调
- 用户维度反查：`我评论过哪些`

当前设计采用：

- `Spring Boot`
- `MySQL`
- `Redis`
- `MyBatis`
- DDD 风格四层架构
- 预留 `MQ / ES / 分库分表 / ShardingSphere-JDBC` 扩展能力

---

## 2. 业务对象与核心概念

### 2.1 评论对象

评论并不是独立存在，而是依附于某个内容对象，例如：

- 题解
- 面经
- 跳蚤帖子
- 视频 / 笔记

评论对象用以下字段标识：

- `comment_object_id`
- `comment_type`

### 2.2 评论与回复

- `评论`：一级评论，直接挂在某个内容对象下
- `回复`：挂在某条一级评论下，可继续形成楼中楼

### 2.3 回复树模型

回复表使用：

- `comment_id`：表示这条回复归属于哪条一级评论
- `parent_reply_id`：表示这条回复直接回复的是谁

因此：

- `comment_id` 负责归属
- `parent_reply_id` 负责树结构

## 3. 总体架构

### 3.1 分层架构

项目采用四层结构：

- `start`
  - Controller、ReqVO / RespVO、参数校验、登录态获取
- `application`
  - `CommentBizService`，负责业务编排和 BO 组装
- `domain`
  - `CommentDomainService`，负责核心规则、缓存读写、分片逻辑说明
- `infrastructure`
  - RepositoryImpl、Mapper、PO、XML，负责持久化

### 3.2 外部依赖

- `MySQL`：存储评论、回复、点赞记录、审核记录、用户评论索引
- `Redis`：点赞数缓存、用户点赞状态缓存、热评 ZSet
- `MQ`：用于异步更新统计、通知、审核等扩展逻辑
- `ES`：可选，用于搜索与复杂反查扩展

## 5. 核心访问模式

评论系统的主查询路径有两个：

### 5.1 对象维度

用户进入某个对象详情页后，查看该对象下的评论列表：

```text
comment_object_id + comment_type -> 评论列表
```

### 5.2 评论维度

用户点击某条评论后，展开这条评论下的回复：

```text
comment_id + parent_reply_id -> 回复列表
```

### 5.3 非主路径查询

例如：

- 我评论过哪些内容
- 某用户发过哪些回复

这类按用户维度反查，不是主路径查询，在分库分表后会更复杂，需要额外索引表承接。

## 6. 接口设计总览

当前评论模块共 15 个 HTTP 接口，包括评论、回复、点赞、热评、审核、站内通知等能力。

| 序号 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 1 | POST | `/api/comment/create` | 创建评论 / 回复 |
| 2 | POST | `/api/comment/delete` | 删除评论 / 回复 |
| 3 | POST | `/api/comment/edit` | 编辑评论 / 回复 |
| 4 | POST | `/api/comment/pin` | 置顶 / 取消置顶评论 |
| 5 | GET | `/api/comment/list` | 评论列表 |
| 6 | GET | `/api/reply/list` | 回复列表 |
| 7 | POST | `/api/comment/like` | 点赞评论 / 回复 |
| 8 | POST | `/api/comment/unlike` | 取消点赞 |
| 9 | POST | `/api/comment/audit/callback` | 审核回调 |
| 10 | GET | `/api/comment/audit/history` | 审核历史 |
| 11 | GET | `/api/comment/hot` | 热评列表 |
| 12 | GET | `/api/comment/my/list` | 我评论过的内容列表 |
| 13 | GET | `/api/notification/list` | 通知列表 |
| 14 | POST | `/api/notification/read` | 标记通知已读 |
| 15 | POST | `/api/notification/read/all` | 全部通知已读 |

### 6.1 统一设计原则

- 评论与回复的创建 / 删除 / 编辑走统一接口
- 通过 `type` 区分评论与回复
- 回复列表仍然保留独立接口 `/api/reply/list`
- 点赞目标统一使用：
  - `targetId`
  - `targetType`

## 7. 关键业务流程

### 7.1 创建评论 / 回复

流程：

1. Controller 收参
2. Application 编排
3. Domain 根据 `type` 分流：
   - 创建一级评论
   - 创建回复
4. Repository 写入评论表 / 回复表
5. 同步更新必要字段（如 `reply_count`）
6. 异步更新扩展逻辑（可选）

设计要点：

- 评论创建按 `comment_object_id` 路由
- 回复创建按 `comment_id` 路由
- 用户评论索引表改为异步事件维护，支撑“我评论过哪些”

### 7.2 评论列表查询

流程：

1. 按 `comment_object_id + comment_type` 查询评论分页
2. 批量收集评论 ID
3. 批量查一级回复
4. 应用层分组，给每条评论挂 `topReplies`
5. 批量填充评论 / 回复点赞数

设计要点：

- 避免 N+1 查询
- 评论列表路由按 `comment_object_id`
- 点赞数优先从 Redis 批量读

### 7.3 回复列表查询

流程：

1. 按 `comment_id + parent_reply_id` 查询回复分页
2. 填充回复点赞数和点赞状态

设计要点：

- 回复列表围绕 `comment_id` 路由
- `parent_reply_id = 0` 查一级回复
- `parent_reply_id > 0` 查某条回复的子回复

### 7.4 点赞 / 取消点赞

流程：

1. 校验目标是否存在
2. 操作 `component_comment_like`
3. 更新评论表 / 回复表中的 `like_count`
4. 更新 Redis 点赞数缓存
5. 更新用户点赞状态缓存
6. 若目标为评论，更新热评 ZSet

### 7.5 热评列表

流程：

1. 优先读 Redis ZSet
2. 命中则按评论 ID 回查详情并按 ZSet 顺序组装
3. 未命中则回源 MySQL
4. 回填 Redis

### 7.6 我评论过哪些

流程：

1. 不直接扫评论主表 / 回复主表
2. 查询 `component_user_comment_index`
3. 按 `latest_time` 倒序分页返回

设计要点：

- 这是用户维度反查，不命中主分片键
- 通过用户评论索引表承接

## 8. 数据库设计

### 8.1 核心表

当前核心是 6 张表：

1. `component_comment`
2. `component_comment_reply`
3. `component_comment_like`
4. `component_comment_audit`
5. `component_user_comment_index`
6. `component_notification`

可选扩展表：

7. `component_comment_stat`

### 8.2 每张表的职责

#### `component_comment`

一级评论表，存储：

- 评论对象信息
- 评论内容
- 评论用户
- 置顶排序
- 回复数
- 点赞数
- 审核状态

关键字段：

- `id`
- `comment_object_id`
- `comment_type`
- `content`
- `images`
- `comment_user_id`
- `sort`
- `reply_count`
- `like_count`
- `audit_status`
- `is_delete`

#### `component_comment_reply`

回复表，存储：

- 所属一级评论
- 父回复关系
- 回复内容
- 回复用户
- 被回复用户
- 点赞数
- 审核状态

关键字段：

- `id`
- `comment_id`
- `parent_reply_id`
- `reply_type`
- `content`
- `images`
- `reply_user_id`
- `be_replied_user_id`
- `like_count`
- `audit_status`
- `is_delete`

#### `component_comment_like`

点赞记录表。

统一目标模型：

- `user_id`
- `target_id`
- `target_type`

其中：

- `target_type = 1` 表示评论
- `target_type = 2` 表示回复

#### `component_comment_audit`

审核记录表。

同样采用统一目标模型：

- `target_id`
- `target_type`
- `audit_status`
- `audit_reason`

#### `component_user_comment_index`

用户评论索引表，用于支撑：

- “我评论过哪些”
- 用户维度互动历史查询

关键字段：

- `user_id`
- `comment_object_id`
- `comment_type`
- `interaction_type`
- `target_comment_id`
- `target_reply_id`
- `latest_content`
- `latest_time`
- `interaction_count`

#### `component_notification`

站内通知表，用于异步写入「有人回复了你」「有人赞了你」等通知。

关键字段：

- `user_id`：接收人 ID，分库分表键
- `type`：通知类型，1=回复通知 2=点赞通知
- `subject_id` / `subject_type`：触发对象
- `actor_id`：触发者用户 ID
- `content`：内容摘要
- `is_read`：是否已读

## 9. 表关系

### 9.1 主关系

#### 评论与回复

```text
component_comment.id = component_comment_reply.comment_id
```

关系：

- 一条一级评论 -> 多条回复

#### 回复自关联

```text
component_comment_reply.id = component_comment_reply.parent_reply_id
```

关系：

- 一条回复 -> 多条子回复

### 9.2 统一目标关系

#### 点赞

- 评论可以被点赞
- 回复也可以被点赞
- 通过 `target_id + target_type` 统一建模

#### 审核

- 评论可以被审核
- 回复也可以被审核
- 同样通过 `target_id + target_type` 统一建模

### 9.3 用户索引关系

`component_user_comment_index` 不是主存储表，而是用户维度索引表，用来承接分库分表后的反查需求。

## 10. 分库分表设计

### 10.1 分片键选择

#### 评论表分片键

- `comment_object_id`

原因：

- 评论列表主查询围绕对象维度展开
- 用户是先打开对象详情页，再看评论

#### 回复表分片键

- `comment_id`

原因：

- 回复列表主查询围绕某条一级评论展开
- 同一评论下的回复链应尽量落在同一分片

### 10.2 为什么不用用户 ID 做分片键

因为评论系统的主查询不是：

- 按用户查评论

而是：

- 按对象查评论
- 按评论查回复

如果按用户 ID 分片：

- 同一对象下评论会被打散
- 评论列表会变成跨分片聚合

### 10.3 第一版分片规模

示意方案：

- 评论表：`2 库 8 表`
- 回复表：`2 库 8 表`

### 10.4 路由规则

评论表：

```text
dbIndex = hash(comment_object_id) % 2
tableIndex = hash(comment_object_id) % 4
```

回复表：

```text
dbIndex = hash(comment_id) % 2
tableIndex = hash(comment_id) % 4
```

### 10.5 用户维度反查如何处理

“我评论过哪些”不命中主分片键，因此不直接扫主表，而是通过：

- `component_user_comment_index`

承担查询。

## 12. 缓存设计

### 12.1 设计目标

- 降低数据库读压力
- 提升列表加载性能
- 支撑点赞、热评等高频场景

### 12.2 点赞缓存

#### 评论点赞数缓存

```text
Key: comment:like:obj:{commentObjectId}
Type: Hash
Field: commentId
Value: likeCount
```

#### 回复点赞数缓存

```text
Key: reply:like:obj:{commentObjectId}
Type: Hash
Field: replyId
Value: likeCount
```

#### 用户点赞状态缓存

```text
Key: user:like:{userId}:target:{targetType}:{targetId}
Type: String
Value: 1
```

### 12.3 热评缓存

```text
Key: comment:hot:obj:{commentObjectId}:type:{commentType}
Type: ZSet
Member: commentId
Score: hotScore
```

热度分近似公式：

```text
hotScore = likeCount * 100 + 时间因子
```

### 12.4 读写策略

#### 列表查询

- 批量读评论点赞数 Hash
- 批量读回复点赞数 Hash

#### 点赞 / 取消点赞

- 更新数据库
- 更新 Hash
- 更新用户点赞状态
- 更新热评 ZSet

#### 热评查询

- 优先读 ZSet
- 未命中回源数据库并回填

## 13. 字段设计与技术选型演进

### 13.1 `content` 与 `images`

最终采用拆分设计，而不是一个大 JSON：

- `content`：纯文本，适合审核 / 搜索
- `images`：图片 URL 列表

### 13.2 回复结构

从“仅靠 `reply_type` 表达所有语义”，演进为：

- `comment_id`
- `parent_reply_id`
- `reply_type` 两态化

优点：

- 归属关系与树结构解耦
- 更适合楼中楼展开

### 13.3 `reply_count`

评论表增加冗余字段：

- `reply_count`

目的：

- 评论列表查询时不必实时 `COUNT(*)`

### 13.4 统一目标模型

点赞表和审核表都采用：

- `target_id + target_type`

避免评论和回复分别建两套几乎相同的表。

可承担：

- 缓存清理

主要承担异步能力：

## 16. 稳定性与工程策略

### 16.1 热点对象

热门帖子 / 视频 / 题解的评论会形成热点：

- 需要缓存
- 需要分库分表
- 需要热点数据保护

### 16.2 数据一致性

主要采用：

- 数据库为最终真实来源
- 缓存允许短时间最终一致
- 统计字段允许异步更新 + 定时校正

### 16.3 降级思路

当弱依赖不可用时：

- Redis 不可用 -> 回源数据库
- 审核服务不可用 -> 降级处理
- ES 不可用 -> 不影响主流程 CRUD
