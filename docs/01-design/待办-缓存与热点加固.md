### 以下是当时的问题分析（保留备查）

### 1. 用户点赞状态批量化（收益最直接）

- **位置**：`ssp-comment-center-domain/.../CommentDomainService.java` → `batchFillCommentLikeCount` / `batchFillReplyLikeCount` → `isUserLiked`
- **现状**：循环里对每条评论单独调 `getBucket(...).isExists()`，一页 20 条 = **20 次 Redis 往返**，全部串在列表返回之前。这是读链路 P99 218ms 的重要来源。
- **改法**：改成一次批量取（Redisson `RBuckets.get(...)` 传多个 key，等价 MGET）。
- **风险**：低，返回值语义不变。
- **验证**：`k6 run loadtest/list-baseline.js`，对比 P99。

### 2. 点赞计数改原子操作

- **位置**：`ssp-comment-center-application/.../listener/CacheEvictListener.java` → `onCommentLiked`（`map.get` + `map.put` 两步）
- **现状**：并发点赞时"读出来再加一写回去"会**丢更新**。
- **改法**：`RMap.addAndGet(targetId, delta)`；保留 `Math.max(..., 0)` 的下限保护（必要时用 Lua 包住"读取 + 夹紧"）。
- **附带**：`CommentDomainService` 里的 `incrementCommentLikeCache` / `incrementReplyLikeCache` 是**死代码**（定义了但无人调用），要么接回去要么删掉，别留着被问。
- **风险**：低。

### 3. 补缓存 TTL

- **位置**：`markUserLiked`（现有 7 天）、点赞计数 RMap（**无 TTL**）、热评 ZSet（**无 TTL**）；`HotScoreUpdateListener` 写入时也要带 TTL。
- **现状**：除了用户点赞状态，其余缓存**永不过期**——写错一次就永久错下去（`loadtest/REPORT.md` §4.2 那个"zset 残留旧 ID 导致 hot 返回空"就是这么来的）。
- **改法**：点赞 RMap / 热评 ZSet 加 expire（设计值：热评 1 小时，见 `设计与稳定性追问.md` §3.2）；**用户点赞状态的 7 天 TTL 本身是业务 BUG**——7 天后状态位消失，用户再点会撞 `uk_user_target` 唯一索引报错，建议去掉 TTL（或改为按用户维度存一个 Set）。
- **风险**：中。加 TTL 后会出现"过期 → 回源重建"窗口，重建逻辑要正确（见第 5 条）。
- **验证**：`redis-cli ttl comment:hot:obj:10001:type:1` 有值。

### 4. 热度公式加时间衰减

- **位置**：`CommentDomainService.updateHotCommentScore` 与 `HotScoreUpdateListener.onCommentLiked`（**两处公式重复**，建议抽成一个方法）。
- **现状**：`score = likeCount * 100 + 秒级时间戳`。时间戳量级 **1.7×10⁹**，点赞项要 **1700 万赞**才能压过 1 秒的时间差 → 实际效果是"**最新优先**"，不是"最热优先"。
- **改法**：时间项改为小权重衰减（如 `likes * 100 - ageHours`），或换 Reddit hot / 牛顿冷却。
- **风险**：中。**排序结果会变**，改完要清一次 Redis 让榜单重新回源。
- **⚠️ 注意**：`docs/02-interview/高频问答.md` 已有对该公式缺陷的说明，改完后要同步更新；旧文档里"点赞数差 1 就能覆盖时间差"的辩解是**算术错误**，不要背。

### 5. 读路径加降级

- **位置**：列表渲染主路径上的所有 Redis 调用（`batchFillCommentLikeCount` / `batchFillReplyLikeCount` / `isUserLiked`）。
- **现状**：**Redis 抖动或宕机 → 评论列表直接 500**（无 try/catch、无熔断、无本地缓存，Redis 还是单机 localhost）。
- **改法**：try/catch 包住，失败时回源 DB（点赞数取 `comment.like_count`、点赞状态置 false 或查库），并打 warn 日志。注意别把业务异常一起吞掉。
- **风险**：低。
- **验证**：停掉 Redis，`curl` 评论列表应仍返回数据而不是 500。

## 二、P1 — 一致性与事务

> **新发现（2026-09-14 改代码时看到，尚未修）**：`CommentDomainService` 里的 `commentLikedCarrier` / `replyLikedCarrier` / `commentLikeReplyCarrier` 是**单例 Bean 上的普通 `HashMap`**，却被当作"请求级上下文"使用（`queryPage` 里 `clear()` 后写入，业务层再通过 `isCommentLiked()` 读出来）。**并发请求会互相覆盖**——两个用户同时打开同一个评论区，A 可能读到 B 的点赞状态、甚至读到 B 的 topReplies。改法二选一：把 liked 标记直接塞进实体 / VO（推荐，彻底去掉载体），或改成 `ThreadLocal`（注意线程池复用必须 `remove()`，否则会内存泄漏）。

- [ ] **跨库事务原子性**：`@Transactional` 内同时写评论（`ds_{comment_object_id % 2}`）和审核记录（审核表固定在 `ds_0`）。ShardingSphere 本地事务**跨库不回滚**，第二段失败会留脏数据。选项：审核表按同一分片键分片 / 接受最终一致 + 补偿任务 / Seata AT。
- [ ] **事件可靠性**：`AFTER_COMMIT` 防了脏写，但进程宕机丢事件。选项：本地消息表 + 定时重投 / 换 MQ。
- [ ] **缓存监听器补 try/catch**：`CacheEvictListener`、`HotScoreUpdateListener` 目前无异常处理（`UserIndexUpdateListener` 有），失败是静默的。
- [ ] **缓存穿透路径**：热评榜在 `hotIds` 为空时每次都回源 DB 且**不缓存空结果**，冷对象被刷会持续打库。选项：空值缓存 / 布隆过滤器 / 单飞（singleflight）。

## 五、需要先拍板的三个决策
