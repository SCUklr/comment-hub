# 风险点与兜底策略

> 本文档列出 ssp-comment-center 在「新增前端展示页」及日常运行中最可能出问题的 3 个风险点，并给出可落地的防御与兜底措施。

---

## 风险点 1：高并发点赞导致重复点赞或计数偏差

### 问题描述

`like()` 方法内部存在 `exists → insert → update like_count → write Redis` 的多步操作：

1. 先 SELECT 检查是否已点赞。
2. 再 INSERT 点赞记录。
3. 更新评论/回复表 `like_count`。
4. 同步写 Redis 用户点赞状态、点赞数 Hash、热榜 ZSet。

在并发场景下：
- 两个请求同时通过 `exists` 检查，都会尝试 INSERT，最终一个成功、一个因唯一索引 `uk_user_target` 抛异常。
- 即使数据库层面唯一索引兜底成功，`like_count` 与 Redis 缓存可能因非原子更新出现偏差。
- Redis 写操作在 `@Transactional` 内部，若事务回滚，Redis 已脏写，且 Spring Event 已发出。

### 影响

- 用户体验：重复点击时可能收到「重复点赞」错误。
- 数据一致性：极端情况下 `like_count` 与真实点赞记录数不一致。
- 缓存一致性：事务回滚后 Redis 缓存脏写。

### 防御与兜底策略

| 层级 | 措施 | 落地方式 |
|------|------|---------|
| 前端 | 按钮防抖 | 点赞按钮点击后 500ms 内禁用，请求返回后才恢复。 |
| 数据库 | 唯一索引兜底 | 已存在 `UNIQUE INDEX uk_user_target (user_id, target_id, target_type)`，数据库层面保证不重复。 |
| SQL | 计数非负 | `UPDATE ... SET like_count = GREATEST(like_count + #{delta}, 0)`，避免取消赞时扣成负数。 |
| 应用层 | 幂等接口设计 | 对 `like`/`unlike` 增加「已点赞则不操作、未点赞则取消不报错」的幂等语义，降低用户感知错误。 |
| 缓存 | 定时校对 | 每日凌晨通过定时任务或脚本，按数据库 `component_comment_like` 重新计算并回填 `like_count` 与 Redis Hash。 |
| 事务 | 缓存后置 | 将 Redis 写操作从 `@Transactional` 中移出，改为事务提交后通过 `@TransactionalEventListener(AFTER_COMMIT)` 或 MQ 异步更新，避免事务回滚脏写。 |

### 优先级

**高**。点赞是评论系统最高频的操作之一，建议上线前至少完成「按钮防抖 + 幂等语义 + 定时校对」。

## 风险点 2：Spring Event 异步事件丢失或脏事件触发

### 问题描述

当前使用 Spring Event + `@Async` 实现异步事件：

- 事件在 `@Transactional` 方法内部发布。
- 未使用 `@TransactionalEventListener(phase = AFTER_COMMIT)`，事件监听器可能在事务提交前就开始执行。
- Spring Event 是内存队列，应用重启时未消费事件会丢失。
- 若事务回滚，事件已经发出，监听器会基于一个「最终未成功」的操作去更新缓存/热榜。

### 影响

- 缓存脏写：事务回滚后，缓存仍被更新。
- 热榜错误：未成功的点赞也会更新热评 ZSet。
- 用户索引不一致：创建评论事务失败后，索引表可能被异步写入。
- 事件丢失：重启后部分通知、缓存清理未执行。

### 防御与兜底策略

| 层级 | 措施 | 落地方式 |
|------|------|---------|
| 应用层 | 事件绑定事务提交 | 将 `publishEvent` 替换为 `TransactionSynchronizationManager.registerSynchronization(...)`，或在监听器上使用 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`。 |
| 应用层 | 事件持久化 | 将 Spring Event 替换为 Kafka/RabbitMQ，确保事件持久化、可重试、不丢失。 |
| 兜底 | 定时任务校对 | 每日扫描 `component_comment` / `component_comment_like` 与 Redis 缓存，发现偏差则回填或清理。 |
| 兜底 | 缓存过期策略 | 为 Redis 点赞数 Hash、用户点赞状态、热榜 ZSet 设置合理 TTL（如 1~24 小时），过期后自动回源数据库重建。 |
| 监控 | 事件消费监控 | 增加监听器执行日志与 metrics，记录事件处理成功/失败数量，失败时告警。 |

### 优先级

**高**。这是当前系统最突出的架构风险，建议在正式对外使用前完成「事件绑定事务提交」改造；若短期内无法引入 MQ，至少使用 `AFTER_COMMIT` 事件监听器。

## 风险点 3：前端展示页引发的安全与滥用问题

### 问题描述

新增前端展示页后：

1. **XSS 风险**：评论内容直接渲染到页面，若未做转义，可能执行恶意脚本。
2. **CSRF 风险**：虽然当前使用 `X-User-Id` 模拟登录，无 CSRF Token，但若后续接入 Cookie 会话，POST 接口存在 CSRF 风险。
3. **接口滥用**：页面暴露点赞、创建评论等接口，可能被脚本刷量。
4. **超长内容 / 高频提交**：前端未限制时，用户可能提交超长文本或高频调用接口，打满数据库连接或 Redis。

### 影响

- 安全：XSS 可导致用户 Cookie 泄露、页面篡改。
- 稳定性：刷量脚本可能导致数据库连接池耗尽、Redis 热点 Key 打满。
- 数据质量：垃圾评论、恶意点赞污染内容生态。

### 防御与兜底策略

| 层级 | 措施 | 落地方式 |
|------|------|---------|
| 前端 | 输入过滤 | 内容框限制最大长度（如 1000 字符），图片 URL 限制数量（如最多 9 张）。 |
| 前端 | 输出转义 | 渲染 `content` 前使用 `textContent` 或 DOMPurify 风格转义，禁止直接 `innerHTML`。 |
| 前端 | 按钮防抖 | 发布评论、点赞、删除等操作在请求返回前禁用按钮。 |
| 后端 | 参数校验 | 复用现有 `@Valid` + `@NotBlank` 校验；补充长度限制注解（如 `@Size(max=1000)`）。 |
| 后端 | 限流 | 对 `/api/comment/create`、`/api/comment/like` 等高频接口增加 RateLimiter（如 Guava RateLimiter 或 Sentinel），按用户 ID 限流。 |
| 后端 | 反垃圾 | 接入敏感词过滤或异步审核服务；第一版可在后端增加轻量敏感词黑名单。 |
| 后端 | CORS 配置 | 若前端独立部署，严格配置 `allowedOrigins`，禁止未授权域名调用。 |
| 运维 | 监控告警 | 对 QPS、错误率、慢 SQL、Redis 命中率设置告警阈值。 |

### 优先级

**中**。在「面试演示/开发者自测」场景下，XSS 与限流可适当放宽；但若页面面向真实用户开放，必须完成 XSS 转义、输入校验与限流。

## 四、风险矩阵汇总

| 风险点 | 发生概率 | 影响程度 | 优先级 | 核心措施 |
|--------|---------|---------|--------|---------|
| 高并发点赞不一致 | 中 | 高 | 🔴 高 | 按钮防抖 + 幂等 + 唯一索引 + 定时校对 |
| Spring Event 脏事件/丢失 | 中 | 高 | 🔴 高 | AFTER_COMMIT / MQ + 定时校对 + 缓存 TTL |
| 前端安全与滥用 | 中 | 中 | 🟡 中 | XSS 转义 + 输入校验 + 限流 |

---

## 五、建议的短期行动项

1. **本周完成**：
   - 前端点赞/发布按钮 500ms 防抖。
   - 前端 `content` 渲染做 HTML 转义。
   - 后端 `like`/`unlike` 接口幂等化改造（已点赞再点返回成功但不重复插入）。

2. **两周内完成**：
   - 将 Spring Event 监听器改为 `@TransactionalEventListener(phase = AFTER_COMMIT)`。
   - 为 Redis 缓存设置 TTL 与定时校对脚本。

3. **一个月内完成**：
   - 评估是否引入 Kafka/RabbitMQ 替代 Spring Event。
   - 接入轻量限流与敏感词过滤。
