# 评论系统关键问题拷打点

本文档用于整理评论系统面试中最容易被追问的几个关键问题，答案全部结合当前项目的真实设计来写，尽量做到：

- 不脱离项目实际
- 能解释“为什么这么设计”
- 可以直接在面试里口语化复述

---

## 1. 分库分表：分片键选什么维度？背后考量？

### 面试回答版

我这个评论系统里，评论表和回复表的分片键不是同一个。

- 评论表 `component_comment` 的分片键我选的是 `comment_object_id`
- 回复表 `component_comment_reply` 的分片键我选的是 `comment_id`

原因是评论系统的主查询路径不是按用户查，而是：

1. 用户先进入某个内容对象详情页，比如某个题解、某篇面经、某个帖子、某个视频；
2. 然后加载这个对象下的评论列表；
3. 再基于某条一级评论展开回复列表。

所以：

- 评论表最核心的查询条件是 `comment_object_id + comment_type`
- 回复表最核心的查询条件是 `comment_id`

这就决定了：

- 评论跟着内容对象走，所以评论表按 `comment_object_id` 分片最合理
- 回复跟着一级评论走，所以回复表按 `comment_id` 分片最合理

### 背后考量

#### 1. 要优先保证主查询链路命中分片

我做分片键选择时，最优先考虑的是：

> 高频主查询能不能稳定命中单分片，而不是跨片扫描

比如评论列表：

```sql
SELECT *
FROM component_comment
WHERE comment_object_id = ?
  AND comment_type = ?
  AND is_delete = 0
ORDER BY sort DESC, create_time DESC
LIMIT ?, ?;
```

这种查询天然就是对象维度，所以评论表用 `comment_object_id` 分片。

而回复列表：

```sql
SELECT *
FROM component_comment_reply
WHERE comment_id = ?
  AND parent_reply_id = ?
  AND is_delete = 0
ORDER BY create_time ASC
LIMIT ?, ?;
```

这种查询天然就是评论维度，所以回复表用 `comment_id` 分片。

#### 2. 不按 `user_id` 分片的原因

按用户 ID 分片听起来也有道理，因为“我发过什么评论”是个场景，但它不是评论系统主路径。

如果按 `user_id` 分片，会导致：

- 同一个视频 / 帖子下的评论被打散到多个分片
- 评论列表查询变成跨片聚合
- 热评、置顶、分页排序都更难做

所以我优先保证详情页评论列表和回复列表这种主路径，再通过额外索引表去解决用户维度反查。

#### 3. 用户维度反查怎么解决

像“我评论过哪些”这种场景，因为不命中主分片键，所以我单独设计了一张：

- `component_user_comment_index`

让主表继续按对象和评论维度分片，用户维度查询走索引表承接。

### 一句总结

> 评论表按 `comment_object_id` 分片，回复表按 `comment_id` 分片，本质上是为了让内容详情页评论列表和评论回复列表这两条主链路尽量命中单分片。

## 2. 数据倾斜：爆款视频评论热点问题怎么解决？

### 面试回答版

爆款视频或爆款帖子下的评论会出现典型热点问题。即使做了分库分表，如果一个超级热门对象的 `comment_object_id` 特别热，相关评论流量还是会集中到同一个逻辑分片，所以分库分表本身不能完全解决热点问题。

我会从 4 个层面处理：

1. **读流量优先走缓存**
2. **列表查询做分页 + 热评分离**
3. **写流量尽量异步化 / 削峰**
4. **热点对象单独治理**

### 具体策略

#### 1. 评论列表读流量走缓存

热点对象最容易把数据库打爆的，其实是读流量。

我在项目里已经设计了 Redis 缓存：

- 评论点赞数缓存
- 回复点赞数缓存
- 热评 ZSet

后续如果热点对象访问量进一步上升，还可以继续扩展：

- 评论列表页缓存
- 热评列表缓存
- topReplies 预计算缓存

目标是：

> 热点对象的大部分读请求由 Redis 承接，而不是每次都回源 MySQL

#### 2. 热评与普通评论分离

爆款场景下，用户并不一定要一次性看全部评论，而是：

- 先看热评
- 再按时间分页看普通评论

所以系统层面可以把：

- `热评列表`
- `普通评论分页列表`

拆开处理。

热评使用：

- `Redis ZSet`

普通评论使用：

- 基于对象维度分页查评论表

这样可以降低“全量评论排序”的压力。

#### 3. 高频写入做异步削峰

爆款对象下高频操作一般包括：

- 点赞
- 回复
- 统计更新
- 通知
- 热度更新

这里不能把所有逻辑都同步做完，否则主链路会很重。

我的思路是：

- 核心写库同步完成
- 非核心逻辑异步处理

例如：

- 点赞记录先写库
- `like_count` 先更新缓存 / 主表
- 热度更新、通知、统计可以走 MQ 异步

#### 4. 热点对象单独限流与降级

如果某个对象突然爆了，比如一个热门视频评论量瞬间上来，可以增加以下策略：

- 评论列表分页上限控制
- 只展示前 N 条热评 + 普通分页
- 楼中楼延迟加载
- 降级关闭部分非核心展示字段
- 极端情况下对评论写入做限流或排队

### 关键认知

热点问题本质上不是“表太大”这么简单，而是：

- 同一个 key 的读写流量集中

所以只靠分库分表不够，还必须配合：

- 缓存
- 异步
- 限流
- 热点隔离

### 一句总结

> 爆款评论热点不能只靠分库分表解决，核心要靠 Redis 承接读流量、热评与普通评论分离、写链路异步化，以及对热点对象做专门的限流和降级治理。

## 3. 表结构设计：一级评论表 vs 二级回复表字段设计？

### 面试回答版

我这里没有把评论和回复强行塞进一张表，而是拆成了：

- 一级评论表 `component_comment`
- 回复表 `component_comment_reply`

因为一级评论和回复虽然看起来都是“文本内容”，但它们的归属关系、查询路径和业务语义其实不一样。

### 一级评论表设计

一级评论表的核心字段是：

- `id`
- `comment_object_id`
- `comment_type`
- `content`
- `images`
- `comment_user_id`
- `sort`
- `reply_count`
- `like_count`
- `audit_status`
- `is_delete`
- `create_time`
- `update_time`

#### 设计原因

- 一级评论天然归属于某个内容对象，所以必须有：
  - `comment_object_id`
  - `comment_type`
- 评论列表经常要做置顶、热评、统计，所以需要：
  - `sort`
  - `reply_count`
  - `like_count`
- 评论本身是详情页第一层展示对象，所以它和回复不是同一个层级

### 回复表设计

回复表核心字段是：

- `id`
- `comment_id`
- `parent_reply_id`
- `reply_type`
- `content`
- `images`
- `reply_user_id`
- `be_replied_user_id`
- `like_count`
- `audit_status`
- `is_delete`
- `create_time`
- `update_time`

#### 设计原因

回复表最关键的是这 3 个字段：

##### 1. `comment_id`

表示这条回复最终归属哪条一级评论。

它的作用是：

- 查某条评论下所有回复
- 维护评论级别的统计，比如 `reply_count`
- 做回复表分片路由

##### 2. `parent_reply_id`

表示这条回复直接回复的是谁。

它的作用是：

- 支撑楼中楼树形结构
- 查某条回复的子回复

##### 3. `be_replied_user_id`

表示 UI 语义上的“被回复的人是谁”。

它的作用主要是：

- 前端展示“回复某某”
- 通知 / @ 关系

它**不承担树结构职责**，这一点很关键。

### 为什么不把评论和回复放一张表

如果强行一张表，会出现几个问题：

- 字段语义混乱
- 一级评论和回复的归属关系不一样
- 查询条件不一样
- 分片键也不一样
- 评论列表和回复列表都要大量额外判断类型

所以拆成两张表更清晰：

- 评论表负责对象维度
- 回复表负责评论维度和树结构

### 为什么 `reply_type` 不再用三态大包大揽

早期可以只用：

- `reply_type = 回复评论 / 回复人 / 回复回复`

但这样会导致：

- 语义和结构耦合
- 不利于标准树形建模

所以我后面把它优化成：

- `reply_type = 1` 表示回复评论
- `reply_type = 2` 表示回复回复

同时引入：

- `parent_reply_id`

让：

- `reply_type` 负责轻量业务语义
- `parent_reply_id` 负责树结构

### 一句总结

> 一级评论表负责对象维度的数据聚合，回复表负责评论维度和树结构关系；拆成两张表后，归属关系、查询路径、分片设计和缓存设计都更清晰。

## 4. 高并发更新：`reply_count` 热点数据频繁更新，优化策略是什么？

### 面试回答版

`reply_count` 是一个典型的冗余统计字段，它的价值是让评论列表查询时不用每次实时 `COUNT(*)`，但代价就是高并发下会变成热点更新字段。

我的处理思路是：

- **为什么要有 `reply_count`**
- **同步更新和异步更新分别适合什么场景**
- **高并发热点下如何削峰**

### 先说为什么保留 `reply_count`

如果不用 `reply_count`，评论列表查询时每条评论都去统计回复数，会带来两个问题：

1. 一页多条评论会产生大量聚合查询
2. 热门对象评论列表压力会明显增大

所以我保留 `reply_count` 作为冗余字段，优先优化查询性能。

### 更新策略

#### 方案 1：同步更新

最直接的做法是：

1. 插入回复
2. `comment.reply_count = reply_count + 1`

或者删除回复时：

1. 逻辑删除回复
2. `reply_count - 1`

优点：

- 实现简单
- 数据短时间更一致

缺点：

- 热门评论下 `reply_count` 会成为热点行
- 高频更新可能导致行锁竞争
- 主链路事务变长

#### 方案 2：异步更新

高并发场景下，更推荐：

1. 主流程先写回复表
2. 发送 MQ 事件
3. 由消费者异步更新 `reply_count`

优点：

- 主线程更轻
- 削峰效果更好
- 避免回复创建接口因为统计更新被拖慢

缺点：

- `reply_count` 会短时间最终一致

### 我项目里的推荐做法

我这个项目会按场景分层处理：

#### 普通流量场景

- 可以同步更新 `reply_count`
- 实现简单，便于保证体验

#### 热点对象 / 高并发场景

- 优先采用异步更新
- 主流程只保证回复写入成功
- `reply_count` 允许短时间最终一致

### 进一步优化手段

#### 1. 缓存承接热点读取

如果 `reply_count` 变成热点字段，除了更新问题，还有读取问题。

可以把对象维度评论统计放到 Redis：

- 评论列表优先读缓存值
- 数据库作为最终兜底

#### 2. 批量回刷 / 定时校正

为了避免异步更新造成长期误差，可以定期做校正：

- 定时任务扫描热点对象
- 重新 `COUNT(*)`
- 回写 `reply_count`

#### 3. 爆款对象专门降级

在极端热点场景下，评论列表可以允许：

- `reply_count` 短时间近似值
- 或优先展示缓存值

这样可以避免主库被热点统计更新打穿。

### 面试时要强调的点

这个问题本质上是：

- 用冗余字段换查询性能
- 再用异步化和缓存解决写热点问题

不是单纯“要不要冗余”，而是：

> 查询性能、一致性、热点更新成本三者之间的平衡

### 一句总结

> `reply_count` 是为了提升评论列表查询性能而保留的冗余字段；普通场景可以同步更新，高并发热点场景更适合通过 MQ 异步更新、Redis 承接热点读取，再结合定时任务做数据校正。

## 5. 最后可以怎么总括

如果面试官连续追问这 4 个问题，你最后可以总结成一句：

> 我这个评论系统的设计主线其实很清楚，就是先围绕真实访问路径做表结构和分片设计，再通过缓存、异步和用户索引表去解决热点读写和非主路径查询问题。
