# 需求澄清清单（前端展示页补充设计）

> 本文档用于在「是否为 ssp-comment-center 增加前端展示页面」这一决策前，梳理现有文档/代码中模糊或缺失的关键信息，并给出合理假设，以便后续设计落地。

---

## 一、前置结论：是否需要前端展示页？

**建议增加一个轻量级的「评论展示/交互演示页」**，理由如下：

1. **项目定位**：README 描述为「独立可运行评论系统」，目前已实现 15 个 HTTP 接口，覆盖评论、回复、点赞、热评、审核、站内通知等能力。
2. **教学/面试价值**：项目本身强调「给老师/面试官讲清楚链路」，一个可交互的页面比 curl 更能直观展示楼中楼、热评、点赞等核心能力。
3. **测试效率**：现有 API 测试依赖 curl/Postman，前端页面可一次性覆盖评论发布、回复、点赞、热评查看等完整链路验证。
4. **成本可控**：前端页仅作为后端能力的演示客户端，不侵入现有 DDD 四层架构，可采用纯静态 HTML 或独立 Vue/React 单页实现。

**不建议**在此阶段引入复杂后台管理系统、富文本编辑器、SSR 或独立前端工程化体系。

---

## 二、模糊或缺失点及合理假设

### 2.1 业务与场景假设

| 编号 | 模糊/缺失点 | 合理假设 | 影响范围 |
|------|------------|---------|---------|
| Q1 | 前端页的目标用户是谁？（普通用户、管理员、开发者自测） | **定位为开发者自测 + 面试演示**，兼顾普通用户浏览体验；管理员能力（置顶、审核回调）暂不暴露到页面，保留为 API 调用。 | 页面功能范围 |
| Q2 | 是否需要用户登录体系？ | **复用现有 `X-User-Id` Header 模拟登录**，页面顶部提供「切换用户」输入框（默认 10001），不接入真实 SSO/OAuth。 | 鉴权方式 |
| Q3 | 评论对象（commentObjectId / commentType）如何确定？ | **页面内置若干示例对象卡片**（如「帖子 10001」「视频 10002」），用户点击后进入对应评论区；也支持手动输入对象 ID。 | 入口设计 |
| Q4 | 评论内容是否支持富文本、图片、表情包？ | **第一版仅支持纯文本 + 图片 URL 列表字符串**（复用现有 `images` 字段，页面以逗号/JSON 字符串方式输入），不支持 Markdown/富文本编辑器。 | 前端复杂度 |
| Q5 | 楼中楼展开策略是什么？ | **默认每条评论展示前 3 条一级回复**（复用 `topReplyLimit=3`），点击「展开更多」再调 `/api/reply/list` 分页加载；支持回复的回复（楼中楼）展示。 | 交互设计 |
| Q6 | 热评与最新评论如何切换？ | **页面提供两个 Tab：「最新」调用 `/api/comment/list`，「热评」调用 `/api/comment/hot`**，默认展示最新。 | 页面结构 |
| Q7 | 删除/编辑后前端如何反馈？ | **操作成功后刷新当前列表第一页**；删除采用二次确认弹窗，编辑采用行内编辑框。 | 交互反馈 |

### 2.2 性能与并发假设

| 编号 | 模糊/缺失点 | 合理假设 | 影响范围 |
|------|------------|---------|---------|
| Q8 | 目标并发量 / QPS 是多少？ | **演示页本身不承载生产流量**，预期单用户或少数并发；后端接口沿用现有设计（连接池 20、Redis 单机）。 | 是否需要前端限流 |
| Q9 | 单对象评论数上限假设？ | **单对象评论数不超过 10 万条**，分页 pageSize 最大 50；热评缓存 TTL 假设 1 小时。 | 分页与缓存策略 |
| Q10 | 是否需要实时推送新评论？ | **第一版采用手动刷新 + 定时轮询（如 30 秒）**，不引入 WebSocket/SSE。 | 实时性设计 |

### 2.3 幂等性与一致性假设

| 编号 | 模糊/缺失点 | 合理假设 | 影响范围 |
|------|------------|---------|---------|
| Q11 | 点赞/取消点赞是否需要幂等？ | **需要幂等**；后端已通过 `uk_user_target` 唯一索引兜底重复点赞；前端按钮需做防连点（点击后 500ms 内禁用）。 | 前端交互 |
| Q12 | 创建评论/回复是否需要幂等？ | **需要幂等**；前端提交按钮在请求返回前禁用，并在网络超时后给出明确提示，不自动重试 POST。 | 前端交互 |
| Q13 | 缓存与数据库短暂不一致是否可接受？ | **可接受最终一致**；页面显示的点赞数、回复数允许与数据库存在秒级延迟，不做强制同步。 | 用户体验 |
| Q14 | 删除评论后，其下回复如何处理？ | **按现有后端设计：仅逻辑删除一级评论，子回复在查询阶段过滤**；前端列表中不再显示该评论即可，不提示「已删除的 N 条回复」。 | 前端展示 |

### 2.4 安全与审核假设

| 编号 | 模糊/缺失点 | 合理假设 | 影响范围 |
|------|------------|---------|---------|
| Q15 | 是否要在前端做敏感词过滤？ | **前端只做轻量提示（如空内容、超长内容拦截），敏感词审核仍由后端/异步审核服务完成**；演示页不接入审核回调 UI。 | 内容安全 |
| Q16 | 图片上传如何实现？ | **第一版不支持文件上传**，用户以文本形式输入图片 URL（可粘贴 CDN 链接），页面仅做图片预览。 | 前端实现 |
| Q17 | 是否需要防 CSRF/XSS？ | **前端输入内容在渲染前做 HTML 转义**，防止 XSS；因复用 `X-User-Id` 模拟登录，暂不处理 CSRF Token。 | 安全基线 |

### 2.5 多端与部署假设

| 编号 | 模糊/缺失点 | 合理假设 | 影响范围 |
|------|------------|---------|---------|
| Q18 | 前端页是否需要响应式/移动端适配？ | **第一版做简单响应式**（适配桌面浏览器 + 平板），不做独立 H5/小程序。 | 前端框架选择 |
| Q19 | 前端静态资源如何部署？ | **作为后端 Spring Boot 的 static 资源内置部署**（`src/main/resources/static`），访问 `http://localhost:8080/comment-demo.html` 即可；未来可拆分为独立 Nginx 静态站点。 | 部署方式 |
| Q20 | 是否需要与现有 start 模块解耦？ | **前端页作为 start 模块的静态资源**，不新增 Maven 模块，不引入前端构建工具链（第一版）。 | 工程结构 |

## 三、关键决策记录

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 是否加前端页 | ✅ 增加 | 提升可演示性、测试效率，成本可控 |
| 前端技术栈 | 纯 HTML + CSS + JavaScript（Vanilla JS） | 零构建依赖，直接嵌入 Spring Boot static 目录 |
| 鉴权方式 | `X-User-Id` Header 模拟登录 | 复用现有后端逻辑，不引入真实用户中心 |
| 实时性 | 手动刷新 + 30s 轮询 | 满足演示需求，不引入 WebSocket |
| 管理员功能 | 不暴露 | 置顶、审核回调仍通过 API/脚本触发 |
| 图片支持 | URL 文本输入 + 预览 | 避免文件上传带来的存储与安全成本 |

## 四、待产品/业务方确认事项

若后续由真实产品团队接手，以下事项需进一步确认：

1. 是否接入真实用户登录体系（JWT / SSO / Cookie）？
2. 是否需要在页面中展示被审核拒绝的内容状态？
3. 热评排序是否需要展示具体热度分数？
4. 评论列表是否需要支持按时间正序/倒序切换？
5. 是否需要 @用户、表情包、Markdown 等富交互？
6. 是否需要对评论进行举报/拉黑等用户治理功能？
