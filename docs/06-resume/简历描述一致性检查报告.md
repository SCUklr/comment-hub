## 一、项目客观事实（已编译验证通过）

### 1.1 接口数量

当前源码共实现 **15 个 HTTP 接口**：

| Controller | 接口数 | 路径 |
|------------|--------|------|
| `CommentController` | 11 | `/api/comment/create`、`/delete`、`/edit`、`/pin`、`/list`、`/like`、`/unlike`、`/audit/callback`、`/audit/history`、`/hot`、`/my/list` |
| `ReplyController` | 1 | `/api/reply/list` |
| `NotificationController` | 3 | `/api/notification/list`、`/read`、`/read/all` |

### 1.2 核心表数量

当前核心表共 **6 张**：

1. `component_comment`（一级评论）
2. `component_comment_reply`（回复 / 楼中楼）
3. `component_comment_like`（点赞）
4. `component_comment_audit`（审核记录）
5. `component_user_comment_index`（用户评论索引）
6. `component_notification`（站内通知）

### 1.3 分库分表规模

| 表 | 分库键 | 分表键 | 规模 |
|----|--------|--------|------|
| `component_comment` | `comment_type` | `comment_user_id` | **2 库 × 4 表 = 8 张物理表** |
| `component_comment_reply` | `comment_id` | `comment_id` | **2 库 × 4 表 = 8 张物理表** |
| `component_comment_like` | `user_id` | `user_id` | **2 库 × 4 表 = 8 张物理表** |
| `component_user_comment_index` | `user_id` | `user_id` | **2 库 × 4 表 = 8 张物理表** |
| `component_notification` | `user_id` | `user_id` | **2 库 × 4 表 = 8 张物理表** |
| `component_comment_audit` | 不分片 | 不分片 | 单表，存于默认库 |

**合计：5 张分片表 × 8 张物理表 + 1 张单表 = 41 张物理表。**

### 1.4 数据一致性策略

- **未使用分布式锁**。
- 主流程使用本地事务 `@Transactional` 保证写一致性。
- 非核心副作用（热度、缓存、用户索引、站内通知）通过：
  - `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async("commentEventExecutor")`
  - 实现最终一致性。

### 1.5 审核状态机

- `audit_status` 约定：**0=待审核，1=通过，2=拒绝**。
- 评论 / 回复创建后自动进入待审核（0）。
- 列表查询对未登录用户仅展示 `audit_status=1` 的内容。
- 作者（`comment_user_id` / `reply_user_id` 匹配当前用户）可见自己的待审核 / 拒绝内容。
- 审核历史可通过 `/api/comment/audit/history` 查询。

## 二、与简历描述可能不一致的风险点

### 风险点 1：分片规模

| 项目 | 说明 |
|------|------|
| 常见简历写法 | "基于 ShardingSphere-JDBC 实现 **2 库 16 表**" |
| 项目实际 | **2 库 × 4 表**，每逻辑表 8 张物理表，共 40 张分片物理表 + 1 张审核表 |
| 风险 | 面试官追问 "16 表怎么算的" 时无法自洽；若按 2 库 × 4 表讲解则与简历数字矛盾。 |
| 建议 | 简历统一写成 **"2 库 × 4 表（5 张业务表共 40 张物理分片表）"**，或扩展为 2 库 × 8 表后再写 "2 库 16 表"。 |

### 风险点 2：性能数据

| 项目 | 说明 |
|------|------|
| 常见简历写法 | "通过异步化将评论发布 P95 从 **240ms 优化到 140ms**" |
| 项目实际 | 代码层面已实现主链路精简 + 异步事件解耦，但**没有压测脚本与实测 P95 数据**。 |
| 风险 | 缺乏 JMH / k6 / JMeter 报告支撑，面试时会被质疑数据可信度；若无法复现则属于简历造假风险。 |
| 建议 | 二选一：  <br>① 补充压测脚本与实测数据后再写该数字；  <br>② 改成定性描述："通过 Spring Event 异步化解耦非核心逻辑，主链路仅保留校验 → 写库 → 返回，降低同步阻塞与长尾延迟"。 |

### 风险点 3：接口 / 表数量

| 项目 | 说明 |
|------|------|
| 常见简历写法 | "实现了 11 个接口 / 5 张核心表" |
| 项目实际 | **15 个接口 / 6 张核心表**（已包含审核历史、站内通知） |
| 风险 | 若简历写成 11 个接口，会漏掉已落地的通知与审核历史能力，显得项目不完整。 |
| 建议 | 简历更新为 **"15 个 HTTP 接口 + 6 张核心表"**。 |

### 风险点 4：分布式锁

| 项目 | 说明 |
|------|------|
| 常见简历写法 | "使用 Redis 分布式锁保证一致性" |
| 项目实际 | 未使用分布式锁，靠本地事务 + 异步事件最终一致性。 |
| 风险 | 若简历写分布式锁，面试会被追问锁粒度、加锁失败降级、可重入性等，与代码不符。 |
| 建议 | 如实描述为 "本地事务保证强一致写，Spring Event 异步化保证最终一致"。 |

## 三、推荐简历表述（与当前代码一致）

> 以下描述可直接用于简历，与项目现状 100% 对齐。

```text
1. 独立实现通用评论中心，采用 DDD 四层架构，提供评论、回复（楼中楼）、点赞、热评、
   审核状态机、站内通知、用户评论历史反查等 15 个 HTTP 接口。

2. 基于 ShardingSphere-JDBC 5.4.1 对 5 张核心表按业务维度做 2 库 × 4 表分片，
   共 40 张物理分片表；审核记录表作为单表存储于默认库。

3. 设计审核状态机（待审核 / 通过 / 拒绝），评论 / 回复创建后自动进入待审核，
   非作者用户仅可见审核通过内容，作者可见自己的待审核 / 拒绝内容。

4. 通过 @TransactionalEventListener(AFTER_COMMIT) + @Async 将热度更新、缓存清理、
   用户索引维护、站内通知等非核心逻辑异步化，实现主链路精简与最终一致性，
   避免分布式锁带来的复杂度。

5. 使用 Redis Hash + ZSet 缓存点赞数与热评排行，列表查询批量组装，避免 N+1。
```
