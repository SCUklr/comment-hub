## 1. §2.1.1 业务访问模式与分片键选型依据

### 1.1 核心访问模式（§2.1.1.1）

文档开篇定性（§2.1.1 摘要行）：

- `核心访问模式一：对象详情页 -> 评论列表`
- `核心访问模式二：评论详情/展开 -> 回复列表`
- `非主路径查询：按用户反查评论历史`
- `结论：评论表按 comment_object_id 分片，回复表按 comment_id 分片`

原文推理链（§2.1.1.1）：

1. 「评论平台的主要访问模式并不是"用户全局浏览所有评论"，而是围绕内容详情页展开」；
2. 链路：进入内容对象详情页（视频 / 专栏文章 / 题解 / 面经 / 商品页）→ 前端按内容对象加载评论列表 → 点击某条评论展开其回复列表 → 继续查看楼中楼则基于某条回复继续向下展开；
3. 两类核心查询：
   - **评论列表查询**：按 `comment_object_id + comment_type` 查询某个对象下的评论；
   - **回复列表查询**：按 `comment_id` 查询某条评论下的回复，再结合 `parent_reply_id` 区分第一层回复和楼中楼回复；
4. 关键定性句：「评论系统的访问模式天然具备明显的"**对象维度聚合**"特征和"**评论维度聚合**"特征，而不是**用户维度聚合**特征。」

### 1.2 评论表按 `comment_object_id` 分片（§2.1.1.2）

主查询 SQL 形态（原文）：

```sql
SELECT * FROM component_comment
WHERE comment_object_id = ? AND comment_type = ? AND is_delete = 0
ORDER BY sort DESC, create_time DESC LIMIT ?, ?;
```

「一级评论的主查询条件天然就是 `comment_object_id`（配合 `comment_type` 区分业务对象类型）」，因此：

- 分片键：`comment_object_id`；辅助业务维度：`comment_type`。

四条选型理由（原文逐条）：

1. **符合主查询路径**：用户进入详情页后，一定是先按对象维度查询评论列表；
2. **同一对象的评论可尽量落在同一分片**：便于评论列表分页、排序、置顶、热评等操作在单分片内完成；
3. **降低跨分片聚合成本**：避免查询某个对象评论时扫描多个分片；
4. **便于后续缓存设计协同**：评论缓存、热评缓存、点赞缓存通常也按对象维度组织。

**反例分析（原文）**：「不选择 `comment_user_id` 作为评论表分片键的原因：**用户维度并不是评论系统的主查询入口**。如果按用户 ID 分片，那么**同一个视频/帖子下的评论会被打散到多个分片**，导致评论列表查询必须做**跨分片聚合**，违背评论系统最核心的访问模式。」

### 1.3 回复表按 `comment_id` 分片（§2.1.1.3）

主查询 SQL 形态（原文两种）：

```sql
-- 第一层回复
SELECT * FROM component_comment_reply
WHERE comment_id = ? AND parent_reply_id = 0 AND is_delete = 0
ORDER BY create_time ASC LIMIT ?, ?;
-- 楼中楼
SELECT * FROM component_comment_reply
WHERE comment_id = ? AND parent_reply_id = ? AND is_delete = 0
ORDER BY create_time ASC LIMIT ?, ?;
```

核心判据（原文）：「回复查询的核心聚合维度是 **comment_id**，而不是 parent_reply_id。因为无论是一层回复还是楼中楼回复，它们最终**都归属于某条一级评论**。」

四条选型理由（原文）：

1. **符合回复主查询路径**：用户一定是先进入某条评论，再查看其下的回复；
2. **同一评论下的回复可尽量落在同一分片**：便于分页加载、楼中楼展开、删除评论时处理回复链等操作；
3. **降低树形结构查询复杂度**：回复树虽然通过 `parent_reply_id` 建立父子关系，但业务归属始终是某条一级评论；
4. **便于维护评论级统计字段**：例如 `reply_count` 的维护天然围绕 `comment_id` 进行。

**反例分析（原文）**：「不选择 **parent_reply_id** 作为回复表分片键原因：parent_reply_id 仅表示"直接回复的是谁"，它**只能表达局部父子关系，不能表达整条回复链最终归属于哪条一级评论**。如果按 parent_reply_id 分片，会导致同一评论下的回复树被打散到不同分片，反而增加查询和维护复杂度。」

### 1.4 分片对象与路由规则（§2.5.1.7.2 / §2.5.1.7.4 / §2.5.1.7.5）

- 分片对象仅两类（§2.5.1.7.2）：`component_comment` → 分片键 `comment_object_id`；`component_comment_reply` → 分片键 `comment_id`。
- 路由算法（§2.5.1.7.4）：

```text
commentDbIndex    = hash(comment_object_id) % 2
commentTableIndex = hash(comment_object_id) % 4
replyDbIndex      = hash(comment_id) % 2
replyTableIndex   = hash(comment_id) % 4
```

- 物理落点示例：`comment_object_id=1001` → `ds_comment_1.component_comment_1`；`comment_id=10001` → `ds_reply_0.component_comment_reply_1`（§2.5.1.7.4）。
- 物理分布：`ds_comment_${0..1}.component_comment_${0..3}`、`ds_reply_${0..1}.component_comment_reply_${0..3}`（§2.5.1.7.3、§2.5.1.8.6）。
- 场景一「查询某对象下评论列表」：按 `comment_object_id` 计算分片 → **仅访问目标分片** → 分片内分页/排序/过滤；「可以避免"查询评论列表时扫描所有评论分片"的广播路由问题」（§2.5.1.7.5）。
- 场景二「查询某条评论下回复列表」：按 `comment_id` 计算分片 → 仅访问目标回复分片 → 分片内查第一层回复或楼中楼（§2.5.1.7.5）。

## 2. §2.5.1 数据库设计

### 2.1 评论表 `component_comment`（§2.5.1.1）

| 字段 | 类型 | 必填/默认 | 说明 |
|---|---|---|---|
| id | bigint | 是 / AUTO_INCREMENT | 主键 |
| comment_object_id | bigint | 是 / 0 | 评论实体 ID（**分片键**） |
| comment_type | int | 是 / 1 | 注册的实体类型：1 题解，2 面经，3 跳蚤平台 |
| content | varchar(8192) | 是 / '' | 评论内容（纯文本） |
| images | varchar(8192) | 是 / '[]' | 图片 URL 列表，JSON 格式 |
| comment_user_id | int | 是 / 0 | 评论人用户 ID |
| sort | int | 否 / 0 | 排序字段，用于置顶，值越大越靠前（置顶设为较大值如 999） |
| create_time | datetime | 否 / CURRENT_TIMESTAMP | 创建时间 |
| update_time | datetime(3) | 否 / CURRENT_TIMESTAMP(3) | 更新时间，毫秒精度 |
| is_delete | int | 是 / 0 | 逻辑删除，0 未删除，1 已删除 |
| reply_count | int | 是 / 0 | 回复数量冗余统计字段；创建回复 +1，删除回复/一级评论 -相应数；**列表直接读，不 count(\*)** |
| like_count | int | （建议新增） | 点赞数冗余统计字段；§2.5.1.1 热评方案中提出，§2.5.1.6 标注「建议新增」 |

**索引设计（§2.5.1.1）**：

```sql
PRIMARY KEY (`id`),
-- 查询某个对象的评论列表，按排序和时间排序
KEY `idx_obj_type` (`comment_object_id`, `comment_type`, `sort`, `create_time`) USING BTREE
```

> ⚠️ 同节 `CREATE TABLE` 语句中该索引实际写为 `idx_obj_type(comment_object_id, comment_type, is_delete, sort, create_time)`（多一个 `is_delete`）。文档两处不一致，面试引用时建议说明「以建表语句为准」。

**索引为什么这么建（原文可推导）**：主查询恒为 `comment_object_id = ? AND comment_type = ? AND is_delete = 0 ORDER BY sort DESC, create_time DESC`（§2.1.1.2、§2.2.2.8.2 5B 步），因此联合索引以分片键 + 业务类型打头，后接排序字段，使过滤与排序在同一索引内完成。

**热度排序方案（§2.5.1.1，含 Redis 联动）**：

- 数据库排序：`ORDER BY sort DESC, (like_count * 100 + UNIX_TIMESTAMP(create_time)/100) DESC`（热度公式）；
- 性能优化：Redis ZSet 缓存热榜 `comment:hot:obj:{objectId}:type:{type}`，score = like_count * 100 + 时间戳，`zrange` 直接取 TopN，「彻底避免数据库排序压力」。

**`reply_count` 一致性方案（§2.5.1.1）**：采用「异步更新 + 最终一致性」（业界主流做法）：

- 同步场景（强一致要求）：事务内先操作回复表，再立即 `UPDATE component_comment SET reply_count = reply_count ± 1 WHERE id = ?`；
- 异步场景（推荐主力方案）：通过 MQ 发送 `CommentReplyChangedEvent`，由独立消费者异步增减 `reply_count`（→ **本项目未实现 MQ**）；
- 优点：主流程不阻塞，删除评论时即使级联删几千条回复也不会卡用户；容错：消费者失败可重试，极端不一致时可通过定时任务（每天凌晨）用 `COUNT(*)` 校正一次（→ **定时任务未实现**）；
- 「为什么不全同步？高并发下事务过长会导致死锁和慢响应。」
- 事务顺序原则：「事务处理中 先修改回复表 再修改评论表」（§2.5.1.1）。

### 2.2 回复表 `component_comment_reply`（§2.5.1.2）

| 字段 | 类型 | 必填/默认 | 说明 |
|---|---|---|---|
| id | bigint | 是 / AUTO_INCREMENT | 主键 ID |
| comment_id | bigint | 是 / 0 | 评论 ID；「这是关联一级评论不关联二级回复的」（**分片键**） |
| parent_reply_id | bigint | 是 / 0 | 父回复 ID，0 表示回复一级评论；>0 指向父回复 id |
| reply_type | int | 是 / 2（建表默认 1） | 回复类型：1 回复评论（parent_reply_id=0），2 回复回复（parent_reply_id>0） |
| content | varchar(8192) | 是 / '' | 内容 |
| images | varchar(8192) | 是 / '[]' | 图片列表，JSON |
| reply_user_id | int | 是 / 0 | 回复人 |
| be_replied_user_id | int | 是 / -1 | 被回复的人，-1 表示无被回复人 |
| create_time | datetime | 否 / CURRENT_TIMESTAMP | 创建时间 |
| update_time | datetime(3) | 否 / CURRENT_TIMESTAMP(3) | 更新时间 |
| is_delete | int | 是 / 0 | 逻辑删除 |
| like_count | int | （建议新增） | 点赞数冗余统计字段（§2.5.1.6） |

**索引设计（建表语句）**：

```sql
PRIMARY KEY (`id`),
-- 1) 查某评论第一层回复：where comment_id=? and parent_reply_id=0 order by create_time
-- 2) 查某回复的子回复：where parent_reply_id=? order by create_time
KEY `idx_comment_parent_time` (`comment_id`, `parent_reply_id`, `create_time`) USING BTREE,
KEY `idx_parent` (`parent_reply_id`) USING BTREE
```

> 同节前文简版索引写作 `KEY idx_comment (comment_id, create_time)`，与建表语句的 `idx_comment_parent_time` 不一致；建表语句注释已说明该联合索引「✅ 新增索引：支撑两类核心查询」。

### 2.3 用户点赞记录表 `component_comment_like`（§2.5.1.3）

字段：`id` bigint 主键；`user_id` bigint 默认 0；`target_id` bigint 默认 0（评论 ID 或回复 ID）；`target_type` int 默认 1（1-评论，2-回复）；`create_time` datetime 默认 CURRENT_TIMESTAMP。

索引与作用：

| 索引名 | 类型 | 字段 | 作用（原文） |
|---|---|---|---|
| PRIMARY | 主键 | id | 唯一标识一条点赞记录 |
| uk_user_target | 唯一索引 | (user_id, target_id, target_type) | **保证同一用户对同一个目标只能点一次赞** |
| idx_target_time | 普通索引 | (target_id, target_type, create_time) | 便于按目标查询点赞记录，并按时间排序/过滤 |

### 2.4 评论审核记录表 `component_comment_audit`（§2.5.1.4，3.5 修改版）

字段：`id`；`target_id`（审核目标 ID）；`target_type`（1-评论，2-回复）；`audit_content` varchar(8192)；`audit_status` int 默认 0（0-待审核，1-通过，2-不通过）；`audit_reason` varchar(512)；`audit_operator` bigint（审核人 ID，系统自动审核记 0）；`audit_time` datetime。

索引：`PRIMARY`；`idx_target_status(target_id, target_type, audit_status)`（查询某个评论/回复的审核状态）；`idx_audit_time(audit_time)`（按审核时间查询记录）。

设计说明（原文）：审核表采用统一目标模型，通过 `target_id + target_type` 同时支持评论和回复审核；「相比仅存 `comment_id` 的设计，统一目标模型更便于扩展，也与点赞表的建模方式保持一致」；后续图片/附件审核可沿用该模型扩展。

### 2.5 评论统计数据表 `component_comment_stat`（§2.5.1.5）

字段：`id`；`comment_object_id`；`comment_type`；`total_comment` bigint；`total_like` bigint；`total_reply` bigint；`stat_date` date。

索引：`PRIMARY`；`uk_object_type_date(comment_object_id, comment_type, stat_date)` 唯一索引——**保证同一评论对象在同一天只有一条统计记录**；`idx_date(stat_date)` 普通索引——按日期查询统计数据。

表关系定性（§2.5.1.6）：「统计表不是直接挂在单条评论或单条回复下面」，按「评论对象 + 评论类型 + 日期」维度聚合，「主要服务于统计分析、报表、趋势展示，**不直接参与主流程 CRUD 查询**」。

### 2.6 用户评论索引表 `component_user_comment_index`（§2.2.2.13，无 DDL）

字段设计：`user_id`、`comment_object_id`、`comment_type`、`interaction_type`（1=评论，2=回复）、`target_comment_id`、`target_reply_id`、`latest_content`（最近一次评论/回复内容摘要）、`latest_time`、`interaction_count`（该用户在该对象下的累计互动次数）。

核心作用（原文）：按 `user_id` 维度组织数据；把原本分散在评论表、回复表中的用户互动行为提前归并成用户可查询的结构；「避免每次打开"我的评论"页面都跨分片扫描业务主表」。

查询 SQL：`SELECT * FROM component_user_comment_index WHERE user_id = ? ORDER BY latest_time DESC LIMIT ?, ?;`

### 2.7 表关系（§2.5.1.6）

- 评论 1 : N 回复（`reply.comment_id` 关联 `comment.id`）；`comment_id` 负责「归属关系」，`parent_reply_id` 负责「树形结构关系（楼中楼）」；
- 回复表自关联（`parent_reply_id = 上级回复 id`）；
- 评论/回复均可是点赞目标、审核目标，通过 `(target_id, target_type)` 统一关联；同一用户对同一目标只能有一条点赞记录，由唯一索引保证。

## 3. §2.5.2 缓存设计

### 3.1 设计目标与分层（§2.5.2 开篇）

目标：降低数据库读压力、提升用户体验、支撑热点场景、便于后续扩展。缓存围绕两类能力：**点赞缓存结构设计**（点赞数 + 用户点赞状态）、**热点数据缓存策略**（热评列表 + 热点对象）。

点赞缓存拆两层：**计数缓存**（评论/回复的点赞数）、**状态缓存**（某用户是否已点赞某目标）。原因：一页评论 10 条、每条含若干回复，逐条查点赞数会形成大量额外 IO；前端渲染"已点赞/未点赞"逐条查点赞记录表压力大。

### 3.2 Key 命名与数据结构选型

| 用途 | Key | 结构 | Field/Member/Value | TTL | 章节 |
|---|---|---|---|---|---|
| 评论点赞数 | `comment:like:obj:{commentObjectId}` | Hash | Field `{commentId}` → Value `{likeCount}` | — | §2.5.2.1.1 |
| 回复点赞数 | `reply:like:obj:{commentObjectId}` | Hash | Field `{replyId}` → Value `{likeCount}` | — | §2.5.2.1.2 |
| 用户点赞状态 | `user:like:{userId}:target:{targetType}:{targetId}` | String | Value `1` | **7 天** | §2.5.2.1.3 |
| 热评列表 | `comment:hot:obj:{commentObjectId}:type:{commentType}` | ZSet | Member `{commentId}`，Score `{hotScore}` | **1 小时** | §2.5.2.2.1、§2.2.2.12 |
| 评论统计（辅助） | `comment:stat:obj:{commentObjectId}:type:{commentType}` | Hash | Field `total_comment/total_like/total_reply` | 1 小时 | §2.5.2.2.4 |

批量读取示例（§2.5.2.1.1）：`redisTemplate.opsForHash().multiGet(key, commentIds)` → `HMGET` 一次取多个评论点赞数。

### 3.3 为什么 Hash 而不是 String + pipeline（§2.5.2.1.1.1）

对比表（原文，五维度）：网络 IO（pipeline 减少 RTT vs HMGET 单命令批量）、内存占用（每评论独立 key 有额外元数据开销 vs 多 field 共享一个大 key 元数据，小对象场景 Hash 编码更紧凑）、key 管理（N 评论 = N key，TTL/删除/迁移逐个处理 vs 按对象维度统一过期删除）、语义匹配度（人为维护 key 规则 vs `key=对象维度`、`field=commentId` 天然表达）、扩展性（独立 key 越多运维监控成本越高 vs 更适合聚合读取场景）。

**最终结论（原文）**：「`pipeline` 解决的是"多次请求的网络往返次数"问题；但它并没有解决"**key 爆炸、元数据开销大、TTL 管理复杂、对象维度聚合不自然**"这些更根本的问题；而评论系统的点赞数读取，本质上就是一个"**围绕对象维度聚合、批量读取多个评论 ID**"的场景，因此 `Hash` 更匹配业务特征。」

### 3.4 读写策略与一致性

- **点赞数缓存选型理由**（§2.5.2.1.1）：符合对象维度查询场景；支持 `HMGET` 批量读取；降低网络 IO；便于按对象维度统一清理。回复点赞数（§2.5.2.1.2）：回复常随评论列表展示（"评论 + top3 回复"），可批量获取；避免对 `component_comment_like` 表大量重复查询。
- **用户点赞状态**（§2.5.2.1.3）：与数据库唯一索引形成双保险——「Redis 负责加速读取；MySQL 的 `uk_user_target(user_id, target_id, target_type)` 负责最终一致性和幂等保障」；后续数据量增长可升级为用户维度 Set / Bitmap。
- **点赞 / 取消点赞缓存更新**（§2.5.2.1.4）：
  - 点赞：① 插入 `component_comment_like` 记录 → ② 点赞数缓存 `HINCRBY +1` → ③ 写入用户点赞状态缓存 → ④ 若目标是评论则异步更新热评 ZSet 分值；
  - 取消点赞：① 删除点赞记录 → ② `HINCRBY -1` → ③ 删除用户点赞状态缓存 → ④ 若目标是评论则异步更新热评 ZSet 分值。
- **热评读取策略**（§2.5.2.2.2）：「优先读缓存，未命中再回源数据库」：查 Redis ZSet → 命中则取评论 ID 列表并组装详情 → 未命中则查 MySQL 按热度规则排序 → 回填 ZSet → 返回。优势：热门对象绝大部分请求由 Redis 承接，显著降低数据库排序压力。
- **热评更新与失效**（§2.5.2.2.3）：更新——点赞/取消点赞异步更新分值；删除评论则删除对应热评成员；评论新增「可延迟加入热评集合，避免冷数据过早进入热榜」；管理员置顶仍以 `sort` 优先，「热评缓存仅处理非置顶区的热度排序」。失效——固定 TTL（如 1 小时）；热门对象可通过访问续期或主动刷新；冷门对象自动过期。一致性——点赞数、热评分值允许短时间最终一致；数据库是最终真实来源；缓存未命中或异常可降级回源。
- **缓存设计总结**（§2.5.2.3）：优先缓存高频读、低频写数据；缓存结构贴合业务聚合维度（评论点赞数按 commentObjectId、回复点赞数按 commentObjectId、热评按 commentObjectId + commentType 组织）；优先保证列表加载和互动反馈性能；允许局部最终一致，数据库始终是最终真实来源。
- **缓存降级**（§2.5.2.4）：四原则——主流程优先保证成功；缓存失败可兜底回源；热点 key 防瞬时击穿；缓存整体不可用要有降级路径。四场景：
  - Redis 写入失败（§2.5.2.4.1）：采用「异常隔离」，MySQL 是主流程强依赖、Redis 是性能优化依赖，「Redis 写失败时，只记录日志，不影响主流程正常返回」；结论句「**缓存可以失败，但不能拖垮主业务链路**」；
  - 缓存击穿（§2.5.2.4.2）：热点 key 恰好过期 + 大量请求同时回源；用互斥锁控制重建——`SETNX` 抢锁（示例锁 TTL 3 秒），仅一个请求回源重建，其余短时重试或返回旧值/降级值；
  - 缓存雪崩（§2.5.2.4.3）：大量 key 同一时刻失效；「若大量热点对象的缓存统一设置为"1 小时整点过期"，就很容易出现这个问题」；方案为 TTL 随机抖动：基础 TTL 1 小时 + 随机 0~10 分钟；
  - Redis 整体不可用（§2.5.2.4.4）：点赞数直接读 MySQL `like_count`；评论列表直接走数据库分页；热评列表降级为 `like_count DESC, create_time DESC` 排序查询；「Redis 是性能优化层；MySQL 是最终真实来源；缓存不可用时，允许系统退回"慢一点但能用"的状态」。

## 4. §3.2 稳定性风险分析

### 4.1 兼容性（§3.2.1）

向前兼容：新接口兼容老版本请求参数，新增参数设置默认值；向后兼容：老接口继续支持，逐步迁移；数据库兼容：表结构变更采用**新增字段**方式，不删除原有字段。

### 4.2 热点数据分析（§3.2.2）

原文三条（可直接用于追问应答）：

- **热点对象**：「热门帖子的评论量可能达到百万级，需要分库分表」；
- **热点用户**：「大 V 用户的评论可能引发大量互动，需要限流」；
- **热点数据**：「热评列表的访问量极高，需要缓存优化」。

### 4.3 强弱依赖（§3.2.3）

- 强依赖：MySQL（存储核心业务数据）；
- 弱依赖：Redis 缓存、Elasticsearch、RabbitMQ、内容审核服务（→ 后三者在项目中未实现，见第 5 节）；
- 降级策略：弱依赖服务不可用时采用降级方案（如直接查询数据库、跳过审核等）。

### 4.4 数据一致性分析（§3.2.4）

原文三条：**缓存一致性**「采用写后删除缓存策略，确保缓存与数据库数据一致」；**MQ 一致性**「采用事务消息或最终一致性方案，确保消息不丢失」（未实现）；**统计数据一致性**「定时任务同步统计数据，确保统计结果准确」（未实现）。

> 补充对齐：项目中实际落地的一致性手段见 §2.5.1.1（reply_count 事务内同步更新）、§2.5.2.1.4（HINCRBY 后写状态缓存）、§2.5.2.4.1（缓存写失败异常隔离）。

### 4.5 资源容量评估（§3.2.5.1，五步推导）

1. **设定目标**：评论系统典型特征是**读多写少，读写比约 10:1**；读 QPS 5000、写 QPS 500。
2. **估算单库吞吐上限**：MySQL 索引命中下简单查询约 1~5ms，按平均 2ms 估算；8 核 16G 机器有效并发连接约 100 → 理论上限 `100 × (1000/2) = 50000`；「但实际要考虑锁竞争、慢查询、热点行等因素，保守估算单库能稳定承载约 **1000~1500 读 QPS**」；写操作涉及事务提交、索引更新、binlog 写入，比读慢，「单库稳定写 QPS 大约在 **500~800**」。
3. **从 QPS 推导分片数**：`5000 / 1500 ≈ 4 个读分片`；`500 / 600 ≈ 1 个写分片（有余量）`；取读写都能覆盖的值，「至少需要 **4 个分片**」。
4. **从数据量推导分表数**：日均新增评论 10 万条、保留 3 年 → `10万 × 365 × 3 ≈ 1 亿行`；「MySQL 单表超过 1000 万行后，索引 B+ 树层数增加，查询性能开始下降。建议单表控制在 500~1000 万行以内」→ `1 亿 / 500 万 = 20 张表`、`1 亿 / 1000 万 = 10 张表`，取中间值约需 **8~16 张物理表**。
5. **综合结论**：`2 个库 × 4 张表 = 8 个物理分片`；每分片数据量 `1 亿 / 8 = 1250 万行`「在可接受范围内」；每分片读 QPS `5000 / 8 = 625`「远低于单库上限」→「**2 库 8 表** 是合理的第一版方案，既满足 QPS 吞吐，也满足数据量分散」；「后续如果业务增长超预期，可以进一步扩展到 4 库 16 表」。

**资源配置估算（§3.2.5.2）**：

| 资源 | 预估 QPS | 所需配置 | 说明 |
|---|---|---|---|
| MySQL | 5000 读 / 500 写 | 8 核 16G，2 库 8 表，主从架构 | 评论表和回复表各 2 库 8 表 |
| Redis | 5000 | 4 核 8G，集群架构 | 承接点赞数、热评、用户点赞状态缓存 |
| Elasticsearch | 2000 | 4 核 8G，3 节点集群 | 扩展搜索和用户维度反查（**未实现**） |
| RabbitMQ | 1000 | 4 核 8G，主备架构 | 异步通知、统计更新、热度更新（**未实现**） |

### 4.6 其他稳定性条目

- 监控告警（§3.1）：接口响应时间 >500ms、错误率 >5%、数据库连接数 >80%、Redis 内存使用率 >80%、MQ 消息堆积 >1000 条（MQ 项未实现）。
- 灰度（§3.3）：按用户 ID 灰度，比例 1% → 10% → 50% → 100%；实时监控响应时间/错误率/反馈；出问题立即回滚。

## 6. 其他高价值论据（支撑"分片键选型 / 热点治理 / 容量评估"追问）

### 6.1 为什么必须带分片键（§2.5.1.8.5）

「在分库分表场景下，分片键的作用相当于"路由入口"。如果 SQL 中不包含分片键，ShardingJDBC 就无法确定目标数据在哪个分片中，只能进行**广播路由**，即把 SQL 发往多个分片执行，再在应用侧归并结果。」反例 SQL 为 `WHERE comment_user_id = 12345 ORDER BY create_time DESC LIMIT 0,20`——「由于该 SQL 未携带评论表分片键 comment_object_id，系统无法直接定位目标分片，可能需要扫描多个评论分片。这类查询在数据规模较大时成本较高，因此不适合作为评论系统主路径查询。」结论：主路径查询必须带分片键（评论列表带 `comment_object_id`、回复列表带 `comment_id`）。

### 6.2 分库分表的收益与代价 + 核心原则（§2.5.1.7.6）

- **收益**：核心高频查询命中分片更稳定；单表数据量和索引压力显著下降；热点流量被拆散到多个物理库表，系统容量更高；更利于后续横向扩容。
- **代价**：跨分片查询变复杂；「例如"我评论过哪些内容""某用户发过哪些回复"这类按用户维度的反查，不再天然命中分片键」；需通过用户维度索引表、搜索引擎、宽表或离线聚合优化。
- **核心原则（原文引用）**：「**优先保证评论详情页、回复展开页等主路径查询的路由效率；对于用户维度反查等非主路径查询，再通过补充索引和扩展方案处理。**」

### 6.3 用户维度反查为什么难（§2.2.2.13）

三个难点（原文）：① 查询条件不命中评论表分片键（`comment_user_id` vs `comment_object_id`）→ 触发跨分片扫描；② 不命中回复表分片键（`reply_user_id` vs `comment_id`）→ 同样跨分片扫描；③ 需把评论与回复统一聚合到"内容对象维度"——回复记录本身不持有对象维度信息，需先通过 `comment_id` 找到所属一级评论再拿对象信息，「这意味着用户维度反查不仅跨分片，还可能需要额外关联」。结论：「在分库分表场景下，**不适合直接扫评论表和回复表来实现"我评论过哪些"功能**。」

方案收益/代价（§2.2.2.13）：避免跨分片扫主表；查询链路更稳定；符合分库分表后读写分离思路（主表服务对象/评论维度主路径，用户索引表服务用户维度反查）；便于扩展"我点赞过哪些""我回复过哪些"等。代价：需新增索引表；主流程外需额外维护索引一致性；删除评论/回复需同步或异步更新用户索引；**允许短时间最终一致，不保证强一致实时可见**。设计原则原文：「主业务表优先服务对象维度和评论维度查询；用户维度反查通过额外索引表承接，以换取更稳定的查询性能。」

### 6.4 字段演进与选型对比（§2.5.1.9）

- **content 与 images 拆分**（§2.5.1.9.2-1）：备选「一个 JSON 大字段」缺点为不利于全文检索、敏感词审核和内容分析不方便、难以分别处理；最终选拆分方案（职责清晰、更适合搜索/审核/渲染）。
- **回复结构**（§2.5.1.9.2-2）：旧版仅 `reply_type` 三态「只能表达"回复语义"，无法清晰表达树结构」，楼中楼父子关系不明确；最终 `parent_reply_id` 表达树结构 + `reply_type` 精简两态保留轻量语义，「不再让 reply_type 一字段承担过多职责」。
- **reply_count 冗余**（§2.5.1.9.2-3）：实时 `COUNT(*)` 数据天然准确，但「评论列表一页往往有多条评论；如果每条评论都实时 count 回复数，会增加数据库聚合压力；在高并发场景下，列表加载成本会明显升高」；最终选冗余字段，「先满足查询性能，再通过同步/异步机制保证一致性」，代价是「需要额外维护一致性」。
- **统一目标模型**（§2.5.1.9.2-4）：备选"评论一张表、回复一张表"会导致表结构/代码逻辑重复、接口与 Service 出现两套几乎相同实现、扩展性差；最终 `target_id + target_type` 统一建模。
- **总结原则**（§2.5.1.9.3）：优先贴合真实业务场景；优先保证主查询链路性能（如 `reply_count`、优化回复树结构）；避免一个字段承担过多职责；尽量统一建模方式；允许从简单方案逐步演进。

### 6.5 避免 N+1 的列表组装（§2.2.2.8.2 / §2.2.2.8.3）

流程：「Mapper 分两次查询数据库（先查评论，再查每条评论的前 N 条回复）→ 组装后返回」；5A 先 `COUNT(*)` 取 total，5B 查当前页评论（「每条评论包含 reply_count 字段，**不需要再 count 子回复**」）；第 6 步「~~循环~~**批量查询**」：收集当前页评论 ID → `ReplyMapper.selectByCommentIds(commentIds)`，SQL 为 `WHERE comment_id IN (?,...) AND parent_reply_id = 0 AND is_delete = 0 ORDER BY create_time ASC` → 应用层用 `Collectors.groupingBy(Reply::getCommentId)` 分组并截取前 N 条。原文说明该步为「2026.3.5 重点优化」，`topReplyLimit` 默认 3（§2.5.3 动态配置）。

### 6.6 热评治理细节（§2.2.2.12）

- 热度排序规则：**置顶评论优先（按 `sort` 降序）**；非置顶评论按热度分降序；`hotScore = likeCount * 100 + 时间因子`，其中「时间因子：用于让新评论在点赞数接近时具备一定竞争力，**避免老评论长期垄断热榜**」。
- 第一版可先基于数据库字段 `like_count DESC, create_time DESC` 近似热度；引入 Redis ZSet 后统一由 score 计算。
- 读路径：`ZREVRANGE comment:hot:obj:1001:type:1 start end` 取当前页评论 ID → 批量查详情 → 按 Redis 顺序组装 → 未命中则查 MySQL 后 `ZADD` 回填并设 TTL（如 1 小时）。热评列表仅返回一级评论。

### 6.7 动态配置（§2.5.3）

`CommentConfig`（`@ConfigurationProperties(prefix = "comment")`）：`topReplyLimit = 3`（每条评论预加载的回复数量）、`hotScoreTimeWeight = 100`（热评排序时间权重）、`cacheExpireHour = 1`（缓存过期小时）、`auditEnabled = true`（内容审核开关）、`sensitiveWordReplace = "*"`（敏感词替换规则）。

### 6.8 分片选型总结（§2.5.1.8.7）

「评论围绕对象查询，因此评论表按 `comment_object_id` 路由；回复围绕评论查询，因此回复表按 `comment_id` 路由；应用层仍面向逻辑表开发，降低业务代码复杂度；分片路由、SQL 改写、结果归并统一交由中间件处理。」选型 ShardingJDBC 原因（§2.5.1.8）：接入成本较低（JDBC 驱动增强）、适合教学和项目表达（体现"逻辑表→路由→物理表"过程）、支持分片路由/分布式主键/读写分离/结果归并、业务代码无须感知具体物理表。
