- 分片键：**评论表 `comment_object_id`**（不是 `comment_type`、不是 `comment_user_id`）。
  - 注：`docs/01-design/技术方案选型说明.md` §1.4 写的是过期的 `comment_type` / `comment_user_id`，**以源码 `application.yml` 为准**。

- **存在跨库写入路径**：`createReply`（回复表按 `comment_id`、评论表按 `comment_object_id`）与 `createComment`（评论表可能落 `ds_1`、审核表固定 `ds_0`）；项目没有分布式事务框架。**不要沿用旧手册"同分片所以不需要分布式事务"的说法**（见 §3.1 Q8 / §5.1 ④）。

## 1. 事实底稿

### 1.1 项目定位

面向题解社区、二手交易等多业务线的**统一评论中台**，解决各业务线独立建评论导致的数据孤岛与重复开发；核心挑战是海量评论场景下的高并发读写与热点内容读放大。

**中台的统一模型**：用 `comment_object_id + comment_type` 抽象任意业务对象（题解 / 面经 / 商品 / 帖子…），新业务线接入只需扩展 `comment_type`，**分片键不变**，评论能力复用。

### 1.2 技术栈

| 层 | 技术 |
|---|---|
| 框架 | Spring Boot 3.0.7、Java 17/21 |
| 数据库 | MySQL 8.0 + ShardingSphere-JDBC 5.4.1 |
| ORM | MyBatis 3.5 + XML |
| 缓存 | Redis + Redisson |
| 异步 | Spring Event + `@Async` |
| 架构 | DDD 四层（start / application / domain / infrastructure） |
| 压测 | k6 |

### 1.3 DDD 四层与调用链

| 层 | 关键内容 | 职责 |
|---|---|---|
| `start` | `CommentController` / `ReplyController` / `NotificationController`、ReqVO/RespVO、`CommentVOConvertor`、`UserContext` | 收请求、参数校验、从 `X-User-Id` 取用户、BO→VO |
| `application` | `CommentBizService`、`bo/`、`listener/` | 用例编排、调 DomainService、4 个事件监听器 |
| `domain` | `CommentDomainService`、`entity/`、`repository/`（接口）、`route/CommentShardRouter`、`event/` | 核心业务规则、分片路由思路、缓存读写、发布事件 |
| `infrastructure` | RepositoryImpl、5 个 Mapper + XML、PO、`CommentDPConvertor` | 持久化实现、Entity↔PO |

调用链：`Controller → CommentBizService → CommentDomainService → RepositoryImpl → Mapper/XML`。

**依赖倒置**：domain 层只依赖 `CommentRepository` 等仓储接口，不依赖 Mapper/PO；infrastructure 提供实现。这是"领域层防腐"的体现。

### 1.5 6 张表 + 分片矩阵

| 表 | 职责 | 分库键 / 分表键 | 规模 |
|---|---|---|---|
| `component_comment` | 一级评论 | `comment_object_id` / `comment_object_id` | 2 库 × 4 表 |
| `component_comment_reply` | 回复 / 楼中楼 | `comment_id` / `comment_id` | 2 库 × 4 表 |
| `component_comment_like` | 点赞记录 | `user_id` / `user_id` | 2 库 × 4 表 |
| `component_user_comment_index` | 用户评论索引 | `user_id` / `user_id` | 2 库 × 4 表 |
| `component_notification` | 站内通知 | `user_id` / `user_id` | 2 库 × 4 表 |
| `component_comment_audit` | 审核记录 | 不分片（单表存 `ds_0`） | 1 张 |

**实际配置**（`application.yml`，INLINE 算法）：

```yaml
component_comment:        ds_${comment_object_id % 2} . component_comment_${comment_object_id % 4}
component_comment_reply:  ds_${comment_id % 2}         . component_comment_reply_${comment_id % 4}
component_comment_like:   ds_${user_id % 2}            . component_comment_like_${user_id % 4}
component_user_comment_index: ds_${user_id % 2}        . component_user_comment_index_${user_id % 4}
component_notification:   ds_${user_id % 2}            . component_notification_${user_id % 4}
```

**关键字段与索引**：

```sql
-- component_comment
id BIGINT PK(雪花ID), comment_object_id BIGINT, comment_type INT,
content TEXT, images VARCHAR(2000) DEFAULT '[]', comment_user_id INT,
sort INT DEFAULT 0(置顶), reply_count INT DEFAULT 0, like_count INT DEFAULT 0,
audit_status INT DEFAULT 0, is_delete TINYINT DEFAULT 0, create_time, update_time
INDEX idx_object (comment_object_id, comment_type, is_delete, sort, create_time)
INDEX idx_user   (comment_user_id, is_delete)

-- component_comment_reply
id, comment_id(分片键), parent_reply_id DEFAULT 0, reply_type DEFAULT 1,
content, images, reply_user_id, be_replied_user_id DEFAULT -1,
like_count, audit_status, is_delete, 时间字段
INDEX idx_comment (comment_id, parent_reply_id, is_delete)
INDEX idx_user    (reply_user_id, is_delete)

-- component_comment_like（统一目标模型）
id, user_id(分片键), target_id, target_type(1评论/2回复), create_time
UNIQUE uk_user_target (user_id, target_id, target_type)   -- 幂等兜底
INDEX  idx_target     (target_id, target_type)
```

**索引设计理由**（高频追问）：
- `idx_object(comment_object_id, comment_type, is_delete, sort, create_time)` 直接把主查询的**过滤条件 + 排序字段**全部包进联合索引，实现"过滤即排序"，避免 filesort；最左前缀 `comment_object_id` 同时是分片键。
- `idx_comment(comment_id, parent_reply_id, is_delete)` 同时支撑"查一级回复（`parent_reply_id=0`）"和"展开楼中楼（`parent_reply_id>0`）"两种查询。
- `uk_user_target` 是**防重复点赞的数据库最终兜底**，不是靠应用层 `exists` 判断。

### 1.6 Redis 缓存（Redisson）

| 用途 | Key | 结构 | 说明 |
|---|---|---|---|
| 评论点赞数 | `comment:like:obj:{objectId}` | `RMap<Long,Integer>` Hash | field=commentId → likeCount，按对象聚合、批量读 |
| 回复点赞数 | `reply:like:obj:{objectId}` | `RMap<Long,Integer>` Hash | 同上 |
| 用户点赞状态 | `user:like:{userId}:target:{type}:{targetId}` | `RBucket<String>` | 存 `"1"`，**不设 TTL**（与 DB 点赞记录同生命周期）；存在即已赞 |
| 热评排序 | `comment:hot:obj:{objectId}:type:{type}` | `RScoredSortedSet<Long>` | member=commentId，score = `likeCount * 100 + 当前秒时间戳` |

**读写路径**：
- 评论列表：`batchFillCommentLikeCount` 批量读 Hash，命中则**覆盖** MySQL 的 `like_count` 旧值；未命中保留 MySQL 值。
- 热评列表：先 `valueRangeReversed` 从 ZSet 取 ID → 批量回表查详情 → 按 ZSet 顺序组装；ZSet 为空则回源 `queryHotPageByObject` 并按热度回填 ZSet。
- 用户点赞状态：直接读 Redis，不读 MySQL；MySQL `component_comment_like` 做持久化与幂等兜底。

### 1.7 异步事件与监听器

**5 个事件**（domain 层 `event/` 包，不可变 record）：

| 事件 | 触发点 |
|---|---|
| `CommentCreatedEvent` | 创建一级评论后 |
| `ReplyCreatedEvent` | 创建回复后 |
| `CommentLikedEvent` | 点赞 / 取消点赞后（含 `isLike`、`newLikeCount`） |
| `CommentDeletedEvent` | 删除评论 / 回复后 |
| `CommentAuditChangedEvent` | 审核回调后 |

**4 个监听器**（application 层），**统一 `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async("commentEventExecutor")`**：

| 监听器 | 消费事件 | 做什么 |
|---|---|---|
| `UserIndexUpdateListener` | Created / Deleted | 异步维护 `component_user_comment_index` |
| `HotScoreUpdateListener` | Liked / AuditChanged | 更新 / 移除热评 ZSet |
| `CacheEvictListener` | Liked / Deleted | 刷新点赞数 Hash / 删除整个对象的点赞缓存 |
| `NotificationListener` | ReplyCreated / Liked | 写站内通知 |

**线程池**（`AsyncEventConfig`）：

```java
corePoolSize = 4;  maxPoolSize = 16;  queueCapacity = 500;
threadNamePrefix = "comment-event-";
rejectedExecutionHandler = CallerRunsPolicy;          // 反压：不丢事件，但会拖慢调用线程
waitForTasksToCompleteOnShutdown = true;              // 优雅停机
awaitTerminationSeconds = 10;
```

**主链路 vs 旁路**：
- 主链路（同步，事务内）：校验 → 写评论/回复表 → 写默认审核记录 → 更新 `reply_count` → 提交 → 返回 ID。
- 旁路（异步，提交后）：用户索引、通知、热评分数、缓存刷新。

### 1.8 审核状态机（先发后审）

- `audit_status`：**0 待审核 / 1 通过 / 2 拒绝**。
- 当前实现为**先发后审**：创建后默认通过（可见），审核回调可改为拒绝；一条内容可多次流转（通过 → 拒绝 → 申诉通过），每次回调**新增一条审核记录**而非更新，保证 `/audit/history` 完整。
- 列表过滤：`audit_status = 1`，或作者本人可见自己的非通过内容。
- **拒绝时的一致性补偿**（高频追问点）：
  1. 热评 ZSet 中 `remove(targetId)`；
  2. `reply_count` 回退 `-1`，且**先查当前状态，只有 1→2 才扣**，防重复扣减；
  3. 用户索引表对应记录置 `is_delete = 1`（否则"我评论过的"点进去不存在）。

### 1.9 二级扁平化回复模型

只有两层：**一级评论表 + 二级回复表**，不做无限嵌套。

| 字段 | 职责 |
|---|---|
| `comment_id` | **归属**：属于哪条一级评论；同时是回复表分片键 |
| `parent_reply_id` | **树结构**：`0` = 直接回复评论；`>0` = 回复某条回复（楼中楼） |
| `reply_type` | **轻量语义**：1 一级回复 / 2 楼中楼（不再承担树结构职责） |
| `be_replied_user_id` | **回复给谁**：UI 展示"XX 回复 YY"、发通知；默认 `-1`，与树结构解耦 |

**为什么不用无限嵌套**：B 站/微博/小红书都是两级；无限嵌套需要递归查询或应用层递归组装树，前端展示也复杂，深层引用通常用"@某人"替代。**二级扁平化消除了嵌套回复的递归查询**。

## 2. 自我介绍（可直接照读）

### 2.1 40 秒版

> 第二个项目是一个**通用评论中台**。背景是社区、二手交易等多条业务线都需要评论区，各建各的会出现**数据孤岛和重复开发**，所以我想做一套统一、可复用的评论能力。
>
> 最大的挑战是**海量评论下的高并发读写**，以及**热点内容的读放大**——一个爆款内容下面可能挂上万条评论，读压力非常大。
>
> 针对它我主要做了四件事：
> 1. **基于 DDD 四层架构**设计系统，用 ShardingSphere-JDBC 做分库分表（2 库 × 4 表），**按业务维度差异化选分片键**：评论表按评论对象 ID、回复表按所属评论 ID，让同一对象下的评论、同一评论下的楼中楼都落到同一分片、列表查询单点命中；点赞、用户索引、通知这些用户维度表按用户 ID 分片，治理单表膨胀和热点写倾斜。
> 2. **用 Spring Event 把通知、热度计算、审核流转这些旁路逻辑从主事务里剥离**，事务提交后再异步执行，主链路只保留核心写库，核心与旁路彻底解耦。
> 3. **基于 Redis（Redisson）做热点读缓存**，点赞计数用 Hash、热评排序用 ZSet，配合事务提交后异步更新保证最终一致；回复表用**二级扁平化模型**，消除嵌套回复的递归查询。
> 4. 最后用 **k6 做了分级压测**：读链路峰值 **430 QPS**（50 并发，P99 218ms），热评读 **440 QPS**（P99 96ms），写链路 **1.5k TPS**（P99 41ms），**全程 0 错误**；并发加到 200 时吞吐趋稳、P99 升到 917ms，圈出了**容量拐点**，为后续连接池限流、列表级缓存提供了依据。

### 2.2 一句话版

> 一个为多条业务线复用统一评论能力的评论中台，用分库分表 + 事件异步化 + Redis 多级缓存解决海量评论的高并发读写和热点读放大，实测读 430 QPS、写 1.5k TPS、0 错误。

### 2.3 3 个诚实雷点（开场别说满，追问时兜住）

## 3. 简历四条逐条拆解

### 3.1 分库分表（被问最多）

**Q1：分片键怎么选的？为什么这么选？**

一句话结论：**主查询路径决定分片键**。

- 评论表 `component_comment` → `comment_object_id`。评论系统的核心访问模式是"进入内容详情页 → 加载该对象的评论列表"，主查询条件天然是 `comment_object_id + comment_type`；按对象分片可让**同一对象下所有评论落同一物理分片**，列表分页/排序/置顶/热评都在单分片内完成。
- 回复表 `component_comment_reply` → `comment_id`。回复的核心聚合维度是"属于哪条一级评论"，无论一级回复还是楼中楼最终都归属某条评论；按 `comment_id` 分片保证**同一评论的回复树不被打散**，也便于维护 `reply_count`。
- 点赞 / 用户索引 / 通知 → `user_id`。这三个是**用户维度反查**场景（"我赞过哪些""我评论过哪些""我的通知"），按 `user_id` 分片可单点命中。
- 审核表不分片，单表存 `ds_0`：数据量小，且运营后台需要全量状态扫描，不分片反而避免跨库聚合。

**反例（必须会）**：
- 评论表若按 `comment_user_id` 分片 → 同一视频/帖子下的评论被打散到多个分片 → 加载评论区变成**跨分片聚合**，ShardingSphere 要 SQL 改写 + 内存归并，分页越深越差。
- 回复表若按 `parent_reply_id` 分片 → 只能表达局部父子关系，不能表达"最终归属哪条一级评论"，回复树被打散。
- 按 `comment_id` 随机分 → 单条查评论快，但"加载评论区"要把 N 条评论分别路由到不同分片，性能不可接受。

**Q2：项目量也不大，为什么分？**

诚实答：这是练手项目，2 库 × 4 表不是为扛当前量，而是**提前预演高并发生产环境**、理解分片键选型与跨片查询限制。

**工业级触发条件（背下来）**：
1. 单表行数超 **500 万~1000 万**（InnoDB B+ 树从 3 层变 4 层，随机读多一次 IO）；
2. 核心查询 P95 > 100ms，执行计划出现全表扫描或 filesort；
3. 单库写入接近单机 MySQL 上限（约 3000~5000 写/s）；
4. 数据增速预估 3~6 个月触达阈值；
5. 备份时长、DDL 锁表时长超过业务容忍窗口。

**Q3：ShardingSphere-JDBC 底层怎么工作的？**

- 客户端嵌入模式（**Driver 层增强**），对业务代码透明；**不是 Proxy 模式**（Proxy 才是独立进程代理，多一跳网络、需独立运维）。选 JDBC 的原因：轻量 Jar、直连性能高、无额外部署、与 Spring Boot 集成简单、配置集中 `application.yml`。
- 四层流程：**SQL 解析**（AST 提取分片键）→ **路由计算**（INLINE 表达式算出目标库/表）→ **SQL 改写**（逻辑表名换物理表名）→ **执行 + 结果归并**（单分片直接返回；跨分片多线程并行发 SQL 再流式/内存归并）。
- 逻辑表是业务看到的 `component_comment`；物理表是 `ds_0.component_comment_0` 到 `ds_1.component_comment_3` 共 8 张。
- 项目里 `CommentShardRouter` 在源码层显式体现路由思路（算逻辑路由 + 注释说明为什么按该键），Repository/Mapper 仍面向逻辑表编码，**真正的物理路由由 ShardingSphere 接管**。

**Q4：分库分表后分页怎么做？会不会漏掉全局 Top100？**

- 本项目**天然规避**跨片分页：`queryCommentPage` 带 `comment_object_id` → 路由到单分片，就是普通 `LIMIT offset, size`；`queryMyComments` 查用户索引表，按 `user_id` 分片，同样单点命中。
- 但**如果真做跨片分页（如全站热评），各分片取 Top100 拼起来确实会漏**——真正的全局第 1 名可能在某分片排第 101。必须回答"**有，会漏**"，不能含糊。
- 工业级方案：① 每分片取 `TopN + offset`，合并后内存排序；② 禁止深分页，用游标 `where id > last_id`；③ 异构索引（ES / 按排序维度分片的表）。

**Q5：数据倾斜怎么解？爆款几万条评论、冷门只有一条。**

- 现状：固定 2 库 × 4 表哈希取模，**没有动态扩容或热点拆分代码**；爆款 `object_id` 会让单分片膨胀。
- 工业级解法：① **热点后缀拆分**（爆款 key 走独立表/特殊路由）；② **缓存层扛读**（列表和点赞数走 Redis，MySQL 只承担写和冷数据）；③ **二次拆分**（同库内按 `object_id + time_bucket` 再分表）；④ 阈值触发迁移或 Range 分片。
- 关键认知：**热点问题的本质是同一个 key 的读写流量集中，只靠分库分表不够**，必须配合缓存、异步、限流、热点隔离。

**Q6：扩容怎么办？**

取模分片扩容需要**数据迁移**（4 表 → 8 表时大部分数据要重分布）。方案：停机迁移 / 双写迁移 / ShardingSphere-Scaling / 一致性哈希减少迁移量。当前项目是练手规模，没做扩容实现。

**Q7：全局唯一 ID 怎么生成？**

自研**雪花算法** `SnowflakeIdUtils`：41bit 时间戳 + 5bit 数据中心 + 5bit 机器 + 12bit 序列号。分库分表后自增 ID 会冲突，雪花 ID 全局唯一且趋势递增（利于 B+ 树插入）。**时钟回拨**：当前代码直接抛异常；工业级方案是小回拨等待、大回拨切换机器位/告警，或美团 Leaf、百度 UidGenerator。

**Q8：分布式事务怎么处理？**

> ⚠️ **这是整个项目最容易被问穿的一个点，务必按下面口径答，不要背旧手册的错话。**
>
> 旧文档（`面试拷打回答手册.md` §9）说："回复表按 `comment_id` 分片，跟评论表同分片，所以这条 UPDATE 和 INSERT 回复在同库内，不需要分布式事务。" —— **这句话是错的**。评论表按 `comment_object_id % 2` 分库，回复表按 `comment_id % 2` 分库，两者是**不同的键值**，绝大多数情况下路由到**不同库**。

**诚实的答法**：

- 项目**没有引入分布式事务框架**（无 Seata/TCC/Saga），也没有 XA。
- **存在两条跨库写入路径**（都可能在 `ds_0` / `ds_1` 之间分布）：
  1. `createReply`：`INSERT component_comment_reply`（按 `comment_id` 路由）与 `UPDATE component_comment SET reply_count`（按 `comment_object_id` 路由）——两个键值不同，可能落不同库；
  2. `createComment`：`INSERT component_comment`（按 `comment_object_id` 可能落 `ds_1`）与 `INSERT component_comment_audit`（**审核表不分片，固定落 `ds_0`**）——也可能跨库。
- 单库单表的场景是安全的：点赞只写 `component_comment_like`；删除评论只改本表；`queryMyComments` 只读用户索引表。
- **我认识到这个问题**，当前的处理是：`reply_count`、审核记录都按"允许最终一致/可补偿"来对待，`reply_count` 由后续定时校正兜底（**未实现，仅方案**）。
- **工业级改进**：把 `reply_count`、审核记录、用户索引这类"非主记录"的写入从主事务剥离到 `@TransactionalEventListener(AFTER_COMMIT)` 或 MQ 消费端（本地消息表保证投递），主事务只写一张核心表；或者用 Seata AT 兜住跨库写。这正是"冗余字段/旁路表换查询性能，再用异步换一致性"的典型权衡。

**可以主动抛出来**："这个项目里我复盘最深的一点就是：分片键不同会让看似一个事务的操作变成跨库写。我当时把它当冗余字段处理，允许最终一致；如果要严格，应该把它异步化或上 Seata。"——这种回答比背"同分片所以不需要分布式事务"安全得多，也更显水平。

**Q9：用户维度反查为什么单独建索引表？**

"我评论过哪些"按 `user_id` 查，不命中评论表分片键（`comment_object_id`）和回复表分片键（`comment_id`），会触发**广播路由 + 跨分片归并**；而且回复记录本身不持有对象维度信息，还要先通过 `comment_id` 找到所属一级评论。所以单独建 `component_user_comment_index`，**按 `user_id` 分片**，直接按 `latest_time` 倒序分页，空间换时间。写入用 `INSERT ... ON DUPLICATE KEY UPDATE` 维护 `latest_content` / `latest_time` / `interaction_count`，由 `UserIndexUpdateListener` 异步维护，**允许秒级最终一致**。

**本节雷点**
- 不要说"ShardingSphere 用代理模式"——JDBC 是客户端嵌入模式。
- 被问"各分片 Top100 拼起来有没有问题"，必须答"有，会漏"。
- "量小为什么分"必须诚实。

### 3.2 Spring Event 异步化

**Q1：你把什么异步化了？主链路精简了什么？**

`CommentDomainService.createComment()` 主事务内只做两件事：
1. `INSERT component_comment`；
2. `INSERT component_comment_audit`（默认审核记录）。

然后 `publishEvent(new CommentCreatedEvent(...))`。事务提交后，三个异步监听器分别执行：`UserIndexUpdateListener`（写用户索引）、`NotificationListener`（发通知）、`HotScoreUpdateListener`（热评 ZSet）；点赞/删除场景由 `CacheEvictListener` 刷新缓存。

**优化逻辑**：如果把"写索引 + 写通知 + 更新热评"全放主事务里，主事务持有数据库连接时间变长，且下游故障会导致主事务回滚（**通知失败不该影响评论发布**）。异步化后主链路只对"评论发布成功"负责，旁路最终一致。

**Q2：底层原理？**

1. `publishEvent` 把事件交给 `ApplicationEventMulticaster` 广播；
2. 标了 `@TransactionalEventListener` 的监听器**不会立即执行**，而是注册到当前事务的 `TransactionSynchronizationManager`；
3. 事务提交成功后（`afterCompletion = COMMITTED`）触发 `afterCommit()` 回调；
4. 若方法还标了 `@Async`，Spring 通过 AOP 代理把调用包装成 `Runnable` 提交给 `commentEventExecutor` 线程池；
5. **事务回滚则事件不触发**（这是用 `AFTER_COMMIT` 的核心价值：避免"数据没落库但缓存/热榜已更新"的脏写）。

**Q3：为什么不用 MQ？**

- 事件量不大（发评论/点赞频率），Spring Event 足够轻量，不需要引入 Kafka/RabbitMQ 的运维复杂度；
- 事件丢了后果是"通知没发"或"索引没更新"，不是核心数据丢失，可容忍；
- **不要说"Spring Event 是 MQ 的替代品"**。应该说："在轻量级场景下替代 MQ、降低复杂度；事件定义与消费方式解耦，工业级量大时可以把事件层换成 MQ 生产者、监听器换成消费者，**事件契约不用改**。"
- 诚实边界：**内存事件不可靠**，JVM 崩溃会丢未消费事件，需要 MQ + 本地消息表兜底。

**Q4：线程池参数怎么定的？**

`core=4 / max=16 / queue=500`。监听器任务是 IO 密集（写库、写 Redis），CPU 核数不高时不需要太大；先 core → 队列 → max → 拒绝策略。队列 500 是缓冲削峰，超过后触发 `CallerRunsPolicy`。

**Q5：为什么选 CallerRunsPolicy？**

让提交任务的业务线程自己执行，相当于**反压降速**——保证事件不丢，但会拖慢主链路。对比：`AbortPolicy` 抛异常丢事件、`DiscardPolicy` 静默丢弃、`DiscardOldestPolicy` 丢最老的。选它的理由：旁路事件丢失比主链路变慢更不可接受（通知丢了用户投诉，慢一点只是延迟）。

**Q6：@Async 失效的场景？异步线程里 ThreadLocal 会丢吗？**

- 失效：自调用（同类内部调用不走代理）、方法非 public、没开 `@EnableAsync`。
- **会丢**：项目里 `UserContext` 用 ThreadLocal 存登录用户，异步监听器在另一个线程执行，拿不到主线程的上下文。**所以事件对象必须携带全部所需数据**（本项目的事件 record 就是这么设计的：带 `commentObjectId`、`commentUserId`、`targetAuthorId` 等）。`InheritableThreadLocal` 对线程池复用线程也不可靠。

**Q7：事件丢了怎么办？**

诚实答：内存事件不可靠，生产应换 MQ（RocketMQ 事务消息 / 本地消息表）；当前方案可接受短暂不一致 + 缓存 TTL 兜底。

**本节雷点**：不要讲成 MQ；不要忽略"事件对象必须自带上下文"这个真实约束。

### 3.3 Redis 缓存 + 二级扁平化

**Q1：缓存了什么？为什么用这些数据结构？**

见 §1.6。要点：
- 点赞数用 **Hash**（`RMap`）而不是 String + pipeline：一个对象下多条评论的点赞数聚合成一个 Hash，**减少 key 数量、共享元数据、支持 `HMGET` 批量读、可按对象维度统一清理/TTL**。pipeline 只解决"网络往返次数"，没解决 key 爆炸和 TTL 管理复杂的问题。
- 热评用 **ZSet**：score 天然支持排序 + 范围分页（`valueRangeReversed`）。
- 用户点赞状态用 **String/Bucket（不设 TTL）**：只需判断"存在即已赞"。原设计带 7 天 TTL 会导致状态位过期后用户重复点赞撞 DB 唯一索引，已于 2026-09-14 修正。

**Q2：MySQL 和 Redis 怎么保证一致性？**

**Cache-Aside + 事务事件驱动 + 最终一致**：写操作先落 MySQL，**事务提交成功后**通过 Spring Event 异步更新 Redis。

- 点赞：`save()`（写 like 表）→ `updateLikeCount()`（MySQL）→ 事务提交 → `CommentLikedEvent` → `CacheEvictListener` 在 `AFTER_COMMIT` 更新 Redis Hash。
- 删除评论：`CacheEvictListener` 直接 `delete()` 整个对象的点赞 Hash，而不是逐条改。
- 关键注解：`@TransactionalEventListener(phase = AFTER_COMMIT)`（回滚则不发事件、不脏写）+ `@Async("commentEventExecutor")`（隔离主链路延迟）。
- **追问：为什么提交前删缓存不行？** 事务可能回滚，导致缓存被误删/脏读。**追问：AFTER_COMMIT 就一定能执行吗？** JVM 崩溃会丢事件 → 需要 MQ + 本地消息表兜底。
- **诚实边界**：用户点赞状态 `markUserLiked()` 是**在事务内同步写 Redis** 的，严格说仍有"事务回滚但 Redis 已写"的窗口；改进方向是把这一步也移到 `AFTER_COMMIT`。

**Q3：缓存穿透 / 击穿 / 雪崩？**

- 穿透：查不存在的数据 → 布隆过滤器 / 缓存空值。**本项目没做布隆过滤器**。
- 击穿：热点 key 过期瞬间大量请求打到 MySQL → 互斥锁（Redisson `tryLock`）/ 逻辑过期。**本项目没做互斥锁**。
- 雪崩：大量 key 同时过期 → TTL 加随机值 / 多级缓存 / 熔断降级。**本项目热评 ZSet 目前没有设 TTL**（这其实和压测发现的"残留旧 ID 导致 hot 返回空"直接相关）。
- 雷点：**诚实说"知道概念，项目并发不高没实践，工业级会加"**。

**Q4：热评分数公式是什么？有什么缺陷？**

`score = likeCount * 100 + 当前秒时间戳`。缺陷：时间戳是低位，**点赞数差 1 就能覆盖时间差**，所以新评论只要多一个赞就能压过老评论；且点赞数为 0 时完全靠时间排序。这是"简单可用"的权衡；工业级会用时间衰减公式（Reddit hot ranking / 牛顿冷却）。

**Q5：二级扁平化回复模型是什么？为什么不用无限级嵌套？**

见 §1.9。要点：`comment_id` 负责归属、`parent_reply_id` 负责树结构、`reply_type` 只保留两态语义、`be_replied_user_id` 负责"回复给谁"；列表查询只挂前 N 条（`topReplyLimit` 默认 3），展开时按 `comment_id + parent_reply_id` 查楼中楼。**消除递归查询**是核心收益。

**Q6：`reply_count` 热点更新怎么办？**

- 现状：**在 MySQL 事务里直接 `UPDATE component_comment SET reply_count = reply_count + 1`**，没有额外缓冲层。因为要提升列表查询性能（避免每条评论 `COUNT(*)`）。
- 代价：爆款评论下 `reply_count` 成为**热点行**，InnoDB 行锁竞争，高频更新会串行化。
- 工业级：Redis `INCR comment:reply_count:{id}` 先返回最新值 → MQ 异步刷库 → 消费者**批量合并**（1 秒内同一 commentId 的 100 次追评合并成一条 `+100`）→ 定时任务 `COUNT(*)` 校正。
- **雷点**：不要说本项目用了 Redis + MQ 做计数，诚实说"当前是事务内直接 UPDATE"。

**Q7：评论列表怎么避免 N+1？**

先分页查评论 → 收集评论 ID → **批量**查一级回复（`comment_id IN (...)` + `parent_reply_id = 0`）→ **批量**读 Redis 点赞数 Hash → 应用层 `groupingBy` 分组挂 `topReplies`（每条截前 3 条）。两次数据库查询 + 两次缓存批量读，不是 N+1。

### 3.4 k6 压测（数据唯一出处：`loadtest/REPORT.md`）

**Q1：数据怎么来的？**

k6 分三个维度：
- 基线：`list-baseline.js`（20 VU / 30s）、`hot-baseline.js`（20 VU / 30s）、`create-write.js`（20 VU / 30s）；
- 阶梯：`list-ramp.js`，1 → 25 → 50 → 100 → 150 → 200，每档 30s；
- 分档：`generic-vu.js`，`VUS=50/100/200` 各 25s。

环境：jar 部署 8080；MySQL 8.0 容器（端口 33306）；2 库 × 4 表共 40 张分片表 + 审核单表；Redis 6379；预置热对象 `comment_object_id=10001` 1 万条评论；**运行时关闭 SQL-show 和 MyBatis 调试日志**（默认每条 SQL 打日志会严重拉低吞吐、污染数据）。

**Q2：数据是多少？**

| 场景 | 并发 | 吞吐 | P99 | 错误 |
|---|---|---|---|---|
| 评论列表 `list` | 20 | 358 QPS | 135ms | 0% |
| **评论列表 `list`** | **50** | **429 QPS** | **218ms** | **0%** |
| 评论列表 `list` | 100 | 372 QPS | 513ms | 0% |
| 评论列表 `list` | 200 | 380 QPS | **917ms**（max 1.32s） | 0% |
| 热评 `hot` | 20 | 444 QPS | 96ms | 0% |
| 创建 `create` | 20 | ≈1498 TPS | 41ms | 0% |

**Q3：怎么解读拐点？**

吞吐在 **50 并发时到顶 ≈430 QPS**（P99 218ms），之后加并发**吞吐不再增长**（稳定在 370~380 QPS），延迟急剧恶化到 P99 917ms。这是标准的**饱和曲线**：加并发不加吞吐、只加延迟 → 系统容量接近 MySQL / 连接池上限。

原因：读主链路是 **DB 密集**（list 每次都回源 MySQL，无列表级缓存），HikariCP 每库 `maximum-pool-size=20`，连接池打满后请求排队 → 用**排队论 / Little 定律**解释：并发 = 吞吐 × 响应时间，吞吐封顶后并发增加只能推高响应时间。

**Q4：为什么写比读还快（1.5k TPS vs 430 QPS）？**

- 写链路主链路只做"校验 + 写库 + 发事件"，重活（缓存、热度、通知、索引）被 Spring Event 异步剥离；
- 写测试是**分散对象 ID**（`10001~11200`），写入均匀落在 2 库 × 4 表，没有单分片写竞争；
- **注意主动说明**：如果压单个热对象（全写同一分片），数值会明显下降。

**Q5：为什么热评比普通列表快（444 vs 358）？**

热评走 Redis ZSet 取 ID 再回表，排序在 Redis 完成；但要注意**它仍然回表查详情**，所以不是纯缓存命中。ZSet 里只存一级评论 ID。

**Q6：瓶颈在哪？怎么定位的？**

- 资源观测：MySQL `Threads_connected` 空闲 ~42 → 峰值 **101**，压测结束仍保持 101；`Threads_running` 峰值 47；Redis ~100 万+ hits / **1 miss**（缓存命中极佳，**Redis 不是瓶颈**）；HTTP 全程 0 错误。
- 结论：**瓶颈是 MySQL 与连接池**，不是 Redis。
- 定位手段：MySQL 连接数监控、EXPLAIN 看索引命中、日志打印 SQL 耗时、连接池监控。

**Q7：找到瓶颈后怎么优化？（简历里写的方向）**

① 连接池限流（信号量/Hystrix，把 101 收敛到 40 并快速失败）；② 列表级缓存（第一页整页缓存）；③ 读写分离；④ ES 承接复杂检索。

**Q8：压测暴露了什么问题？**（加分项）

见 §5.2，两条：热评缓存残留旧 ID 导致 hot 返回空；Hikari 连接数没按配置收敛（40 → 101）。

**本节雷点**：禁止用 240ms→140ms；1500 TPS 要说明是分散写入。

## 4. 高频八股速查（按类别，答不上来的优先补）

**分库分表**
- 绑定表（Binding Table）：分片规则一致的关联表配 binding，避免跨库 join 笛卡尔积。评论表与回复表**分片键不同，不能配成绑定表**。
- 广播表：字典/配置表每个库一份全量。
- 跨分片 `count`/排序/聚合：ShardingSphere 归并引擎（流式归并 / 内存归并）；`LIMIT` 改写深分页性能问题。
- 取模分片缺点：均匀但扩容迁移量大；范围分片扩容友好但有热点；一致性哈希减少迁移；Hint 强制路由。
- 数据均匀性：取模依赖分片键分布，若 `comment_object_id` 是连续自增且增长不均，会倾斜。

**Redis**
- ZSet 底层：skiplist + hashtable；元素少时用 listpack/ziplist，超阈值转 skiplist。
- Redisson 分布式锁：Lua 保证原子性、hash 存重入次数、watchdog 默认 30s 续期 1/3。**本项目未使用**。
- 持久化：RDB / AOF / 混合；淘汰策略 LRU/LFU/随机；过期删除惰性 + 定期。
- 大 key / 热 key：热评 ZSet 若某对象有几百万评论就是大 key。
- 集群：主从、哨兵、Cluster（16384 槽）、槽迁移。
- **RMap 的 `get` + `put` 有并发问题吗？** 有，见 §5.1。

**Spring / 并发**
- `@Transactional` 失效：自调用、非 public、异常被吞、`rollbackFor` 不匹配（项目显式写了 `rollbackFor = Exception.class`）。
- 事务传播：REQUIRED / REQUIRES_NEW / NESTED。
- `@TransactionalEventListener` 各 Phase：BEFORE_COMMIT / AFTER_COMMIT / AFTER_ROLLBACK / AFTER_COMPLETION。
- 线程池任务执行流程：core → 队列 → max → 拒绝策略。
- Spring Bean 生命周期、IOC/AOP、动态代理（JDK vs CGLIB）、自动装配原理。
- ThreadLocal 原理与内存泄漏；`InheritableThreadLocal` 对线程池不可靠。

**MySQL**
- 深分页 `limit 100000,20` 为什么慢 → 延迟关联 / 游标 / ES。
- InnoDB 为什么 B+ 树；RR 隔离级别如何用 MVCC + Next-Key Lock 解决幻读。
- `count(*)` 大表慢 → 分片后单表可控 / 缓存计数 / 近似计数。
- `exists` 再 `insert` 的并发问题 → 靠唯一索引兜底（本项目 `uk_user_target`）。
- EXPLAIN 关注字段、索引失效场景、最左前缀、覆盖索引、索引下推。

**业务设计**
- 删除：逻辑删除 `is_delete`；软删数据膨胀治理（归档/分区）。
- 删除一级评论时回复怎么处理：级联标记删除 或 保留占位"该评论已删除"。
- 先发后审 vs 先审后发怎么选；拒绝时的一致性补偿（见 §1.8）。
- 点赞幂等 + 防刷：唯一索引 + Redis 标记 + 限流。
- 通知过多：聚合通知（"xx 等 100 人赞了你"）、已读未读、计数用 Redisson。
- 新业务线接入（如直播弹幕）：扩展 `comment_type`，**分片键不变**——这是中台扩展性的体现。
- 读扩散 vs 写扩散：若做"关注的人评论流"就是 Timeline 推拉问题。

## 5. 主动坦白：真实代码隐患（加分项）

> 建议主动讲："我复盘时发现了这几个问题，改进方案是……"——把被动拷问变成主动展示复盘能力。

### 5.1 四个代码隐患

**① 点赞数缓存 `get` + `put` 竞态**
`CacheEvictListener.onCommentLiked()` 是 `map.get(targetId)` 再 `map.put(targetId, current + delta)`，两步非原子。两个并发点赞可能丢一次计数。
**改进**：`RMap.addAndGet()`（底层 HINCRBY）或 Lua 脚本保证原子。注意还要处理"计数不能为负"。

**② `CommentDomainService` 用成员变量 HashMap 传中间结果**
`commentLikedCarrier` / `replyLikedCarrier` / `commentLikeReplyCarrier` 是**单例 Bean 的成员变量**（`HashMap`，非线程安全），在方法入口 `clear()`、过程中 `put()`、最后读。多线程并发时 A 用户的 `liked` 状态可能串给 B 用户，甚至 `clear()` 互相踩踏。
**改进**：改成方法返回值携带、或方法内局部变量、或用 `ThreadLocal`（但异步场景仍有上下文问题）。**这是面试官看 GitHub 源码最可能点的问题**。

**③ `like()` 的 `exists` + `save` 并发窗口**
先 `commentLikeRepository.exists()` 再 `save()`，两个并发请求可能都通过校验，最终靠 `uk_user_target` 唯一索引抛异常兜底。
**这是"代码校验 + DB 约束"双保险的经典案例**：应用层给友好提示，DB 层保证最终正确。可以说："我故意保留唯一索引做最后防线。"

**④ 主事务里的跨库写入窗口**（最容易被问穿，见 §3.1 Q8）
两条路径：
- `createReply` 事务内 `INSERT component_comment_reply`（分片键 `comment_id`）+ `UPDATE component_comment SET reply_count`（分片键 `comment_object_id`），两个键值不同 → 可能路由到**不同库**；
- `createComment` 事务内 `INSERT component_comment`（可能落 `ds_1`）+ `INSERT component_comment_audit`（**不分片，固定 `ds_0`**）→ 也可能跨库。

本地事务无法跨库保证原子性，且项目**没有分布式事务框架**。
**当前处理**：`reply_count` 当冗余统计字段、审核记录当旁路数据，容忍最终一致。
**改进**：把 `reply_count` / 审核记录维护移到 `AFTER_COMMIT` 监听器或 MQ 消费端（本地消息表保证投递），主事务只写一张核心表。
**⚠️ 旧手册 `面试拷打回答手册.md` §9 说"同分片所以不需要分布式事务"是错的，不要背。**

**（附）`incrementCommentLikeCache` / `incrementReplyLikeCache` 是死代码**
domain 层定义了这两个方法但从未调用，点赞数 Hash 的实际更新在 `CacheEvictListener` 里。属于重构遗留，清理即可——可以坦然说"这是我重构到事件监听器后没删干净的旧方法"。

### 5.2 压测暴露的两个发现

**① 热评缓存与库不一致（真实 BUG）**
Redis `comment:hot:obj:10001:type:1` 若残留**旧 ID**，`queryByIds` 会因 `where id in (...) and comment_object_id = 10001` 匹配不到而返回空列表，导致 hot 接口"有数据却返回空"。清掉 ZSet 回源 DB 后即恢复。
**根因**：ZSet 没有 TTL、也没有失效/重建策略。
**治理方向**：设 TTL、事件驱动重建（删除/审核拒绝时移除）、启动预热、回源结果为空时视为未命中并清空 ZSet。

**② 连接数跑到 101，超过配置预期**
配置 `maximum-pool-size: 20`（ds_0 / ds_1 各一个，合计 40），但压测后 `Threads_connected` 恒为 101。
**两种可能**：(a) ShardingSphere YAML 里 Hikari 参数没按 `hikari:` 嵌套绑定生效，走了默认值；(b) 存在额外连接来源。
**这也解释了为什么全程 0 错误**——连接没被真正限流，请求在 HTTP 线程里排队而非被连接池拒绝。若把池严格限到 40，高并发下很可能出现 `Connection is not available` 超时。**值得核查 pool 配置是否生效**——这是一个"发现问题比跑出数字更有价值"的例子。

### 8.2 追问弹药：容量评估五步法（原文来自架构文档，用于回答"你怎么估容量"）

1. **设定目标**：评论系统读多写少，读写比约 **10:1**，目标读 5000 QPS、写 500 QPS；
2. **单库上限**：简单查询命中索引约 1~5ms，8 核 16G 有效并发约 100，理论 `100 × 500 = 50000`，保守估**单库稳定 1000~1500 读 QPS、500~800 写 QPS**；
3. **从 QPS 推分片数**：`5000 / 1500 ≈ 4 个读分片`；
4. **从数据量推分表数**：日均 10 万条 × 3 年 ≈ **1 亿行**；单表控制 500 万~1000 万行 → 需 10~20 张表；
5. **综合**：`2 库 × 4 表 = 8 个物理分片`，每分片约 1250 万行、约 625 读 QPS，在可接受范围内；后续可扩到 4 库 × 8 表。

> 讲这段时补一句："这是设计阶段的容量推演，后来用 k6 实测的拐点在 50 并发 / 430 QPS，比理论估算保守——说明连接池和单机 MySQL 才是真实瓶颈。"

### A.1 表关系

```
内容对象（外部系统）
    │ 一对多
    ▼
component_comment（一级评论）
    │ 一对多
    ▼
component_comment_reply（回复 / 楼中楼）
    │
    │ 统一目标模型（target_id + target_type）
    ▼
component_comment_like（点赞）  component_comment_audit（审核）

component_user_comment_index（用户索引，独立维度，不直接关联主表）
component_notification（站内通知，按接收人分片）
```

### A.2 评论与回复的标准树形建模

- 评论表 `component_comment` 负责**对象维度**
- 回复表 `component_comment_reply` 负责**评论维度 + 树结构**
- `comment_id` 负责归属，`parent_reply_id` 负责树结构，两者解耦

### A.3 评论列表批量组装，避免 N+1

- 先分页查评论
- 批量收集评论 ID，批量查一级回复
- 批量读 Redis 点赞数 Hash
- 应用层分组挂 `topReplies`

### A.4 用户维度反查通过索引表承接

- "我评论过哪些"不命中主表分片键（主表按对象 / 评论维度分片）
- 单独设计 `component_user_comment_index`，以 `user_id` 为第一维度
- 主表继续按对象 / 评论维度分片，用户查询走索引表

### A.7 踩坑记录（面试加分项）

| 坑 | 根因 | 解法 |
|----|------|------|
| 雪花 ID 精度丢失 | `744087244154953728` 超出 JS `Number.MAX_SAFE_INTEGER`（2^53-1），JSON.parse 后尾部失真 | Jackson 全局将 boxed `Long` 序列化为字符串，前端按 string 处理 |
| 编辑/删除缺权限校验 | edit 接口未传 currentUserId，delete SQL 无归属条件 | controller 透传 userId → domain `checkOwner` 校验 |
| MySQL 8 `Public Key Retrieval` | caching_sha2_password 插件非 SSL 连接需公钥获取 | JDBC URL 加 `allowPublicKeyRetrieval=true` |
| 宿主机 MySQL 占 3306 | Homebrew launchd 服务与 Docker 容器竞争端口 | `launchctl unload ~/Library/LaunchAgents/homebrew.mxcl.mysql.plist` |
