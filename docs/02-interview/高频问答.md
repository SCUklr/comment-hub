## 一、分库分表与分片键

### 1.1 分片键怎么选的？

**结论**：一级评论表按 `comment_object_id` 取模，回复表按 `comment_id` 取模，点赞 / 用户索引 / 通知表按 `user_id` 取模，审核表不分片。

**项目实际（`application.yml` + `ddl-sharding.sql`）**：

- `component_comment`：`comment_object_id % 2` 分库、`% 4` 分表 → 2 库 × 4 表 = 8 张物理表。同一对象（同一个题解 / 面经 / 帖子 / 视频）下的所有评论落在同一物理分片。
- `component_comment_reply`：`comment_id % 2` 分库、`% 4` 分表。**真实收益是"按一级评论查回复恒定命中单分片"**——楼中楼查询一定带 `comment_id`，所以回复列表永远不跨片。
- `component_comment_like` / `component_user_comment_index` / `component_notification`：`user_id` 取模，支撑"我点赞过哪些""我评论过哪些""我的通知"这类用户维度反查单点命中。
- `component_comment_audit`：不分片，单表存于默认库 `ds_0`。审核数据量小，运营后台需要全量状态扫描，不分片避免跨库聚合。

**面试回答版（口语化）**：

我这个评论系统里，评论表和回复表的分片键不是同一个：

- 评论表 `component_comment` 的分片键我选的是 `comment_object_id`；
- 回复表 `component_comment_reply` 的分片键我选的是 `comment_id`。

原因是评论系统的主查询路径不是按用户查，而是：

1. 用户先进入某个内容对象详情页（某个题解、某篇面经、某个帖子、某个视频）；
2. 然后加载这个对象下的评论列表；
3. 再基于某条一级评论展开回复列表。

所以评论表最核心的查询条件是 `comment_object_id + comment_type`，回复表最核心的查询条件是 `comment_id`——评论跟着内容对象走，回复跟着一级评论走。

**背后考量一：优先保证主查询链路命中分片**

我做分片键选择时，最优先考虑的是：

> 高频主查询能不能稳定命中单分片，而不是跨片扫描。

比如评论列表：

```sql
SELECT *
FROM component_comment
WHERE comment_object_id = ?
  AND comment_type = ?
  AND is_delete = 0
ORDER BY sort DESC, create_time DESC
LIMIT ?, ?;
```

这种查询天然就是对象维度，所以评论表用 `comment_object_id` 分片。

而回复列表：

```sql
SELECT *
FROM component_comment_reply
WHERE comment_id = ?
  AND parent_reply_id = ?
  AND is_delete = 0
ORDER BY create_time ASC
LIMIT ?, ?;
```

这种查询天然就是评论维度，所以回复表用 `comment_id` 分片。

**背后考量二：为什么不按 `user_id` 分片**

按用户 ID 分片听起来也有道理，因为"我发过什么评论"是个真实场景，但它不是评论系统主路径。如果按 `user_id` 分片，会导致：

- 同一个视频 / 帖子下的评论被打散到多个分片；
- 评论列表查询变成跨片聚合；
- 热评、置顶、分页排序都更难做。

所以我优先保证详情页评论列表和回复列表这种主路径，再通过额外索引表去解决用户维度反查。

**背后考量三：用户维度反查怎么解决**

像"我评论过哪些"这种场景，因为不命中主分片键，所以我单独设计了一张 `component_user_comment_index`，让主表继续按对象和评论维度分片，用户维度查询走索引表承接（详见 1.6）。

**延伸**：

- 如果评论表按 `user_id` 分片，加载评论区会变成跨所有分片的聚合查询，ShardingSphere 需要 SQL 改写 + 内存归并，性能差且易 OOM。
- 代价是"查某用户在全站的所有评论"要跨片，所以单独建了 `component_user_comment_index` 按 `user_id` 分片来做反查补偿——空间换时间。

> ⚠️ **注意（合并纠错）**：不要因为"回复表按 `comment_id` 分片"就推论出"回复表和评论表同分片、所以同库"。评论表按 `comment_object_id % 2` 分库、回复表按 `comment_id % 2` 分库，是两个不同的键值，绝大多数情况落在**不同库**。完整口径见 1.10。

**一句总结**：

> 评论表按 `comment_object_id` 分片，回复表按 `comment_id` 分片，本质上是为了让"内容详情页评论列表"和"评论回复列表"这两条主链路尽量命中单分片。

### 1.2 为什么评论表选 `comment_object_id`，而不是 `comment_id`、`user_id` 或随机分片？

**结论**：因为评论区加载是**最高频的读场景**，按 `comment_object_id` 保证"查某个视频 / 帖子的全部评论"单点命中；如果按 `comment_id` 随机分或按用户 ID 分，这个场景会跨片。

**项目实际**：

- `queryCommentPage` 接口的 SQL 条件总是带 `comment_object_id = ?`，ShardingSphere 路由后能精准落到 `ds_0.component_comment_1` 这类单一物理表。
- 如果按 `comment_id` 随机分，虽然单条查评论很快，但"加载评论区"需要把 N 条评论的 `comment_id` 分别路由到不同分片，变成 N 次查询或一次跨片聚合，性能不可接受。

**延伸——如果按评论 ID 随机分，"我的评论"跨片问题**：

- 按 `user_id` 查评论时，用户的评论分散在所有分片，必须做全分片扫描 + 内存归并排序。
- ShardingSphere 支持这种跨片查询，但会改写 SQL 发到所有分片，再归并结果，分页越深性能越差（Page 100 时可能要扫 1000 万条才能归并出 100 条）。
- 所以项目用**异构索引表** `component_user_comment_index` 按 `user_id` 分片来补偿，空间换时间。

### 1.3 什么情况下才需要分库分表？这个项目量不大，为什么分？

**结论**：当前项目数据量不大，分库分表的初衷是**提前预演高并发生产环境**，理解分片键选型和跨片查询限制；工业级触发条件是单表行数或查询延迟超标。

**项目实际**：

- 这是一个练手 / 面试项目，配置的是 2 库 × 4 表，不是为了扛当前量，而是为了演示"在代码层面如何处理分片键、如何在 ShardingSphere 配置 INLINE 算法、如何规避跨片查询"。

**工业级判断维度（背下来）**：

1. **数据量阈值**：单表超过 500 万 ~ 1000 万行（InnoDB B+ 树高度从 3 层变 4 层，随机读增加一次 IO）。
2. **查询性能**：核心查询 P95 延迟超过 100ms，执行计划出现全表扫描或 filesort。
3. **写入瓶颈**：单库 TPS 接近单机 MySQL 上限（约 3000 ~ 5000 写/s）。
4. **数据增速**：预估 3 ~ 6 个月内会触达阈值，提前拆分避免救火。
5. **运维成本**：备份时间、DDL 锁表时长超过业务容忍窗口。

**雷点**：面试官追问"量小为什么要分"，不要硬编"因为数据量大"，诚实说"为了提前理解分片键和跨片分页限制，练手性质"。

### 1.4 为什么用 ShardingSphere-JDBC 而不是 ShardingSphere-Proxy / MyCat？

**考察点**：Client（客户端嵌入）模式 vs Proxy（独立代理）模式的区别。

**回答锚点**：JDBC 以 jar 包形式嵌入应用，无额外部署和代理层网络开销，性能损耗小，适合单体 / 中小规模；Proxy 对业务透明、支持异构语言，但多一跳网络、需要独立运维集群。

**雷点**：不要说"ShardingSphere 用代理模式"——JDBC 是**客户端嵌入模式**（Driver 层），Proxy 才是独立进程代理模式。本项目用的是 JDBC。

### 1.5 ShardingSphere-JDBC 底层是怎么工作的？真的深入了解过吗？

**结论**：它是 JDBC 驱动层的增强代理，对业务代码透明，底层走 SQL 拦截 → 解析 → 分片路由 → SQL 改写 → 执行 → 结果归并。

**项目实际**：

- 配置在 `application.yml` 里，数据源 `ds_0`、`ds_1`，逻辑表 `component_comment`，物理节点 `ds_${0..1}.component_comment_${0..3}`。
- 算法用的是 INLINE：`ds_${comment_object_id % 2}` 分库，`component_comment_${comment_object_id % 4}` 分表。
- 代码中 MyBatis 写 `component_comment`，ShardingSphere 自动改写为 `component_comment_2` 并选择 `ds_1` 的连接。

**底层流程（四层）**：

1. **SQL 解析**：将 SQL 解析成 AST，提取分片键（如 `WHERE comment_object_id = 123`）。
2. **路由计算**：根据分片键值和 INLINE 表达式 `comment_object_id % 2`，算出目标库 `ds_1`；`% 4` 算出目标表 `component_comment_3`。
3. **SQL 改写**：把逻辑表名替换为物理表名，生成 `SELECT * FROM component_comment_3 WHERE ...`。
4. **结果归并**：单分片查询直接返回；跨分片查询（如不带分片键的 `SELECT count(*)`）需要多线程并行发 SQL，再对结果做流式归并。

**逻辑表 vs 物理表**：逻辑表是业务代码看到的 `component_comment`，物理表是 `ds_0.component_comment_0` 到 `ds_1.component_comment_3` 共 8 张真实表。

### 1.6 分库分表后分页怎么做？各分片 Top100 拼起来会不会漏？

**结论**：本项目评论区查询天然规避了跨片分页，因为带 `comment_object_id` 分片键；但如果真的做跨片分页（如"全站热评"），简单拼接各分片 Top100 确实会漏。

**项目实际**：

- `queryCommentPage` 按 `comment_object_id` 查，路由到单分片，分页就是普通 `LIMIT offset, page_size`，没有跨片问题。
- `queryMyComments` 查 `component_user_comment_index`，按 `user_id` 分片，也是单点命中。

**跨片分页的工业级方案（必须会）**：

- **问题**：10 个分片各取 Top100，合并后排序取全局 Top100，但真正的全局第 1 名可能在某个分片里排第 101，只取 Top100 会漏掉。
- **解法 1（全局排序）**：每个分片取 `TopN + offset`，比如要取全局 100 条，每个分片取 100 条，合并后内存排序再取 100。内存压力大，但准确。
- **解法 2（禁止深分页）**：业务层限制只能翻 5 ~ 10 页，深分页用游标（`where id > last_id`）或 ES 替代。
- **解法 3（异构索引）**：把需要全局排序的数据额外写一份到 ES 或按排序维度分片的表，查 ES 返回 ID 再回表。

**不带分片键的查询怎么办（八股追问）**：

- 考察点：广播表、绑定表、全分片路由 + 内存归并排序、ES 异构索引、基因法。
- 锚点：项目建了 `component_user_comment_index` 索引表解决"我评论过哪些"的反向查询——这就是**索引表 / 基因法思路**。

**雷点**：如果面试官问"各分片取 Top100 拼起来有没有问题"，必须回答**有，会漏**，不能含糊。

### 1.7 2 库 4 表怎么定的？扩容怎么办？取模分片有什么缺点？

**考察点**：分片数量预估、扩容痛点（**取模分片扩容需要数据迁移**）、一致性哈希 / 翻倍扩容 / 数据迁移方案（停机迁移、双写、ShardingSphere-Scaling、elasticjob）。

**回答锚点**：

- **数量怎么定**：按数据量预估反推。2 库 × 4 表是练手规模，工程上常用 2^n 便于后续翻倍扩容。
- **扩容怎么做**：4 表 → 8 表时大部分数据要重分布。方案：停机迁移 / 双写迁移 / ShardingSphere-Scaling / 一致性哈希减少迁移量。当前项目是练手规模，没做扩容实现。
- **取模的缺点**：取模均匀但扩容迁移量大；范围分片扩容友好但有热点。项目用的是 INLINE 算法 `ds_${comment_object_id % 2}`。

**取模分片的数据均匀性依赖什么？**

- 取模对**连续值**同样均匀（`1,2,3,4…` 取模 4 会轮流落表），所以 `comment_object_id` 连续自增本身不会造成分布不均。
- 真正的风险不在"均匀"，而在"**热点**"：均匀 ≠ 无热点。爆款对象的 ID 会被高频读写，即使分布均匀，单个分片仍会因访问量集中而过载（见第二章）。

**其他分片算法**：INLINE 取模 vs 范围分片 vs 一致性哈希 vs 自定义算法（ComplexInline、Hint）。

### 1.8 跨分片的 count / 排序 / 聚合怎么做？

**考察点**：ShardingSphere 归并引擎（流式归并、内存归并）、改写 SQL 的限制（`limit` 改写为 `limit 0, offset+size` 的性能问题、深分页）。

**回答要点**：

- 带分片键 → 单分片执行，无归并开销（本项目主路径都是这种）。
- 不带分片键 → 全分片广播 + 内存归并排序，`ORDER BY + LIMIT` 会被改写成每个分片都取 `limit 0, offset + size`，页越深每个分片扫的行越多，这就是分库分表后"深分页更贵"的根因。
- 规避手段：让查询带上分片键、建异构索引表、把复杂检索交给 ES、或用近似计数代替精确 `count(*)`。

### 1.9 什么是绑定表（Binding Table）？什么是广播表？

**绑定表**：

- 考察点：分片规则一致的关联表配置 binding，避免笛卡尔积跨库 join。
- 回答锚点：绑定表要求两张表**分片键相同、分片规则相同**，这样关联查询时能确保落到同一分片，避免"N×M"的笛卡尔积路由。
- **本项目能不能把评论表和回复表配成绑定表？** 严格说不能：评论表分片键是 `comment_object_id`，回复表分片键是 `comment_id`，规则不一致，配绑定表没有意义。这也是 1.10 里"跨库写"问题的根源之一。

**广播表**：

- 定义：每个库都存一份全量数据的表（如字典表、配置表、类型表）。
- 场景：数据量小、改动少、且**几乎每个查询都要关联**它，放每个库一份可以避免跨库 join。

### 1.10 分库分表后分布式事务怎么处理？

> ⚠️ **纠错说明（本节为权威口径）**：旧版 `面试拷打回答手册.md` 曾在 `reply_count` 一节写过——"回复表按 `comment_id` 分片，跟评论表同分片，所以这条 UPDATE 和 INSERT 回复在同库内，不需要分布式事务"。**这个结论是错的**。评论表按 `comment_object_id % 2` 分库，回复表按 `comment_id % 2` 分库，两者是**不同的键值**，绝大多数情况下会路由到**不同库**。回复表按 `comment_id` 分片的真实收益只有一个：**"按一级评论查回复"恒定命中单分片**；不包括"和评论表同库"，更不包括"因此不需要分布式事务"。

**诚实的答法**：

- 项目**没有引入分布式事务框架**（无 Seata / TCC / Saga），也没有 XA。
- **存在两条跨库写入路径**（都可能在 `ds_0` / `ds_1` 之间分布）：
  1. `createReply`：`INSERT component_comment_reply`（按 `comment_id` 路由）与 `UPDATE component_comment SET reply_count`（按 `comment_object_id` 路由）——两个键值不同，可能落不同库；
  2. `createComment`：`INSERT component_comment`（按 `comment_object_id` 可能落 `ds_1`）与 `INSERT component_comment_audit`（**审核表不分片，固定落 `ds_0`**）——也可能跨库。
- 单库单表的场景是安全的：点赞只写 `component_comment_like`；删除评论只改本表；`queryMyComments` 只读用户索引表。
- **我认识到这个问题**，当前的处理是：`reply_count`、审核记录都按"允许最终一致 / 可补偿"来对待，`reply_count` 由后续定时校正兜底（**未实现，仅方案**）。
- **工业级改进**：把 `reply_count`、审核记录、用户索引这类"非主记录"的写入从主事务剥离到 `@TransactionalEventListener(AFTER_COMMIT)` 或 MQ 消费端（本地消息表保证投递），主事务只写一张核心表；或者用 Seata AT 兜住跨库写。这正是"冗余字段 / 旁路表换查询性能，再用异步换一致性"的典型权衡。

**可以主动抛出来**：

> "这个项目里我复盘最深的一点就是：分片键不同会让看似一个事务的操作变成跨库写。我当时把它当冗余字段处理，允许最终一致；如果要严格，应该把它异步化或上 Seata。"

这种回答比背"同分片所以不需要分布式事务"安全得多，也更显水平。

**八股延伸**：

- 考察点：ShardingSphere 支持的 XA / BASE（Seata AT、TCC、Saga）、本地消息表、最大努力通知。
- 锚点：项目里跨分片写入主要靠 **Spring Event 异步 + 最终一致**规避了强分布式事务——注意这是**设计选择**（容忍不一致），不是"不存在跨库写"。

---

### 1.11 用户维度反查为什么单独建索引表？

"我评论过哪些"按 `user_id` 查，不命中评论表分片键（`comment_object_id`）和回复表分片键（`comment_id`），会触发**广播路由 + 跨分片归并**；而且回复记录本身不持有对象维度信息，还要先通过 `comment_id` 找到所属一级评论。

所以单独建 `component_user_comment_index`，**按 `user_id` 分片**，直接按 `latest_time` 倒序分页，空间换时间。写入用 `INSERT ... ON DUPLICATE KEY UPDATE` 维护 `latest_content` / `latest_time` / `interaction_count`，由 `UserIndexUpdateListener` 异步维护，**允许秒级最终一致**。

**本节雷点**：

- 不要说"ShardingSphere 用代理模式"——JDBC 是客户端嵌入模式。
- 被问"各分片 Top100 拼起来有没有问题"，必须答"有，会漏"。
- "量小为什么分"必须诚实。

---

## 二、数据倾斜与热点对象

### 2.1 数据倾斜怎么解？爆款视频几万条评论，冷门只有一条

**面试回答版**：

爆款视频或爆款帖子下的评论会出现典型热点问题。即使做了分库分表，如果一个超级热门对象的 `comment_object_id` 特别热，相关评论流量还是会集中到同一个逻辑分片，**所以分库分表本身不能完全解决热点问题**。

**项目实际**：

- 当前配置是固定 2 库 × 4 表，**没有动态扩容或热点拆分代码**。`comment_object_id` 是哈希取模，所以 `object_id = 100` 和 `object_id = 104` 可能落在同一张表，如果 `100` 是爆款，这张表会膨胀。

**关键认知**：

热点问题本质上不是"表太大"这么简单，而是：

- **同一个 key 的读写流量集中**。

所以只靠分库分表不够，还必须配合：**缓存、异步、限流、热点隔离**。

---

### 2.2 工业级解法（分片层）：热点拆分与二次分片

1. **热点后缀拆分**：对爆款的 `object_id`，在表名后加后缀（如 `component_comment_0_hot`），ShardingSphere 配置分片算法识别热点 key 做特殊路由。
2. **二次拆分**：第一层按 `object_id % 2` 分库，第二层在同库内按 `object_id + time_bucket` 再分表，把**时间维度**引入打散热点。
3. **设定阈值 / Range 分片**：单表超过 500 万行自动触发迁移，或做 Range 分片（如 0~100 万在表_0，100~200 万在表_1），避免哈希倾斜。

---

### 2.3 工业级解法（缓存与异步层）：让 Redis 承接热点读、让旁路异步

**一、评论列表读流量走缓存**

热点对象最容易把数据库打爆的，其实是读流量。项目里已经设计了 Redis 缓存：

- 评论点赞数缓存
- 回复点赞数缓存
- 热评 ZSet

后续如果热点对象访问量进一步上升，还可以继续扩展：

- 评论列表页缓存
- 热评列表缓存
- `topReplies` 预计算缓存

目标是：

> 热点对象的大部分读请求由 Redis 承接，而不是每次都回源 MySQL。

**二、热评与普通评论分离**

爆款场景下，用户并不一定要一次性看全部评论，而是先看热评、再按时间分页看普通评论。所以系统层面可以把"热评列表"和"普通评论分页列表"拆开处理：

- 热评使用 `Redis ZSet`；
- 普通评论使用基于对象维度分页查评论表。

这样可以降低"全量评论排序"的压力。

**三、高频写入做异步削峰**

爆款对象下高频操作一般包括：点赞、回复、统计更新、通知、热度更新。这里不能把所有逻辑都同步做完，否则主链路会很重。我的思路是：

- 核心写库同步完成；
- 非核心逻辑异步处理。

例如：点赞记录先写库 → `like_count` 更新缓存 / 主表 → 热度更新、通知、统计走 MQ 或 Spring Event 异步。

**补充**：评论列表和点赞数走 Redis，MySQL 只承担写和冷数据，可以降低单分片读压。

---

### 2.4 工业级解法（治理层）：热点对象单独限流与降级

如果某个对象突然爆了，比如一个热门视频评论量瞬间上来，可以增加以下策略：

- 评论列表分页上限控制；
- 只展示前 N 条热评 + 普通分页；
- 楼中楼延迟加载；
- 降级关闭部分非核心展示字段；
- 极端情况下对评论写入做限流或排队。

---

### 2.5 一句总结

> 爆款评论热点不能只靠分库分表解决，核心要靠 Redis 承接读流量、热评与普通评论分离、写链路异步化，以及对热点对象做专门的限流和降级治理。

---

## 三、表结构与二级扁平化回复

### 3.1 评论表和回复表怎么设计的？多级回复（树状）怎么查？

**结论**：只有两层结构——一级评论表 + 二级回复表，不做无限嵌套。

我这里没有把评论和回复强行塞进一张表，而是拆成了：

- 一级评论表 `component_comment`
- 回复表 `component_comment_reply`

因为一级评论和回复虽然看起来都是"文本内容"，但它们的归属关系、查询路径和业务语义其实不一样。

---

### 3.2 一级评论表 `component_comment` 的字段与设计原因

**核心字段**：

- `id`
- `comment_object_id`
- `comment_type`
- `content`
- `images`
- `comment_user_id`
- `sort`（置顶排序）
- `reply_count`（冗余计数，减少查回复表）
- `like_count`（当前项目直接读 MySQL 字段，查询时 Redis 会覆盖）
- `audit_status`
- `is_delete`
- `create_time`
- `update_time`

**设计原因**：

- 一级评论天然归属于某个内容对象，所以必须有 `comment_object_id` + `comment_type`；
- 评论列表经常要做置顶、热评、统计，所以需要 `sort`、`reply_count`、`like_count`；
- 评论本身是详情页第一层展示对象，所以它和回复不是同一个层级。

**建表索引（`ddl-sharding.sql`）**：

- `INDEX idx_object (comment_object_id, comment_type, is_delete, sort, create_time)` —— 直接覆盖评论列表的查询与排序条件；
- `INDEX idx_user (comment_user_id, is_delete)`。

---

### 3.3 回复表 `component_comment_reply` 的字段与设计原因

**核心字段**：

- `id`
- `comment_id`（所属一级评论 ID，**分片键**）
- `parent_reply_id`
- `reply_type`
- `content`
- `images`
- `reply_user_id`
- `be_replied_user_id`（被回复人，`-1` 表示无）
- `like_count`
- `audit_status`
- `is_delete`
- `create_time`
- `update_time`

**回复表最关键的是这 3 个字段**：

1. **`comment_id`**：表示这条回复最终归属哪条一级评论。作用是查某条评论下所有回复、维护评论级别统计（如 `reply_count`）、做回复表分片路由。
2. **`parent_reply_id`**：表示这条回复**直接回复的是谁**。`0` 表示直接回复一级评论；`>0` 表示回复某条回复（楼中楼）。它负责**树结构**。
3. **`be_replied_user_id`**：表示 UI 语义上的"被回复的人是谁"。作用是前端展示"回复某某"、通知 / @ 关系。**它不承担树结构职责**，这一点很关键。

**建表索引**：`INDEX idx_comment (comment_id, parent_reply_id, is_delete)`、`INDEX idx_user (reply_user_id, is_delete)`。

---

### 3.4 查询方式：查评论区 / 查楼中楼

- **查评论区**：先查 `component_comment` 按 `comment_object_id` 分页，得到一级评论列表；再用 `comment_id IN (...)` 查 `component_comment_reply` 中 `parent_reply_id = 0` 的回复（直接回复评论）；每条评论下只展示前 N 条（默认 3 条，`topReplyLimit`）。
- **查楼中楼**：点击"展开更多回复"时，按 `comment_id` + `parent_reply_id > 0` 查二级回复。

**列表组装避免 N+1**：先分页查评论 → 收集评论 ID → **批量**查一级回复（`comment_id IN (...)` + `parent_reply_id = 0`）→ **批量**读 Redis 点赞数 Hash → 应用层 `groupingBy` 分组挂 `topReplies`（每条截前 3 条）。两次数据库查询 + 两次缓存批量读，不是 N+1。

---

### 3.5 为什么不把评论和回复放一张表？

如果强行一张表，会出现几个问题：

- 字段语义混乱；
- 一级评论和回复的归属关系不一样；
- 查询条件不一样；
- 分片键也不一样；
- 评论列表和回复列表都要大量额外判断类型。

所以拆成两张表更清晰：评论表负责对象维度，回复表负责评论维度和树结构。

---

### 3.6 为什么 `reply_type` 不再用三态大包大揽？

早期可以只用 `reply_type = 回复评论 / 回复人 / 回复回复` 三态，但这样会导致：

- 语义和结构耦合；
- 不利于标准树形建模。

所以后面优化成：

- `reply_type = 1` 表示回复评论；
- `reply_type = 2` 表示回复回复。

同时引入 `parent_reply_id`，让：

- `reply_type` 负责**轻量业务语义**；
- `parent_reply_id` 负责**树结构**。

---

### 3.7 为什么不支持无限级嵌套？

- 业务上两层足够（B 站、小红书、抖音都是两层：评论 → 回复）；
- 无限嵌套需要递归或树形组装，前端展示也复杂，通常用"@用户名"的方式替代深层引用；
- **消除递归查询**是二级扁平化模型的核心收益。

---

### 3.8 冗余字段怎么设计的？怎么减少查询 IO？

**结论**：一级评论表冗余了 `reply_count`，减少查回复表；回复表冗余了 `be_replied_user_id`，减少 join 被回复人信息。

**项目实际**：

- `reply_count`：一级评论表里直接存了回复数。发回复时 `commentRepository.updateReplyCount(commentId, objectId, 1)`，删除回复时 `-1`。查评论列表时不需要 `COUNT(*)` 回复表。
- `be_replied_user_id`：回复表直接存了被回复人 ID，前端展示"XX 回复 YY"不需要再查一次被回复的回复记录。
- `like_count`：表里直接存了，但查询时会被 Redis 中的实时点赞数覆盖（`batchFillCommentLikeCount` 方法）。

**工业级补充（阿里追问"2 万条评论怎么办"）**：

- 当前 `content` 是 `TEXT`、`images` 是 `VARCHAR(2000)` 存 JSON，如果评论支持图文混排、视频、长文本，应该拆出 `comment_content` 表一对一关联，主表只保留索引字段（`id`, `object_id`, `user_id`, `time`），让主表行宽变小，一页缓存更多行。
- 热评 / 置顶评论可以单独抽一张 `comment_hot` 表或走 Redis，避免在大表里扫排序。

**雷点**：项目里**没有** `top_reply_id` 冗余（之前面试可能说混了），是查回复列表时按时间排序取前 N 条。如果面试官问"一级表里有没有冗余前几条回复 ID"，要诚实回答"当前版本没有，是通过评论 ID 查回复表取 TopN"。

---

### 3.9 如果二级评论内容很复杂（图文 / 视频 / 纯文本），下挂在一级表不合适，怎么办？

**结论**：当前项目用 `content` + `images` JSON 的简单方案；工业级应该主表轻量化，内容拆一对一表，查询时才加载。

**项目实际**：`component_comment` 的 `content` 是 `TEXT`，`images` 是 `VARCHAR(2000)` 存 JSON 数组；`component_comment_reply` 同样结构；没有单独的内容表。

**工业级通用方案**：

1. **主表瘦身**：`component_comment` 只存 `id`, `object_id`, `user_id`, `create_time`, `audit_status`, `is_delete` 等索引和状态字段，行宽控制在 100 字节以内，一页 16KB 能存 160 行。
2. **内容拆表**：`comment_content` 表一对一关联，存 `content` 长文本、`images` 多图 URL、`video_url` 等。查评论列表时先查主表分页，再按需 `IN` 查内容表。
3. **多媒体走 OSS**：图片 / 视频上传后返回 CDN URL，库里只存 URL 字符串，不走数据库 blob。
4. **热评缓存**：热评列表直接走 Redis ZSet，不再回源 MySQL 排序。

**一句总结**：

> 一级评论表负责对象维度的数据聚合，回复表负责评论维度和树结构关系；拆成两张表后，归属关系、查询路径、分片设计和缓存设计都更清晰。

---

## 四、高并发计数（reply_count / like_count）

### 4.1 为什么保留 `reply_count`？

`reply_count` 是一个典型的冗余统计字段，它的价值是让评论列表查询时不用每次实时 `COUNT(*)`，但代价就是高并发下会变成热点更新字段。

如果不用 `reply_count`，评论列表查询时每条评论都去统计回复数，会带来两个问题：

1. 一页多条评论会产生大量聚合查询；
2. 热门对象评论列表压力会明显增大。

所以我保留 `reply_count` 作为冗余字段，优先优化查询性能。

---

### 4.2 项目现状：事务内直接 UPDATE

```java
// 在 createReply 的事务内直接执行
commentRepository.updateReplyCount(commentId, commentObjectId, 1);
```

这是一个简单的 `UPDATE component_comment SET reply_count = reply_count + 1 WHERE id = ?`。

> ⚠️ **纠错**：旧版 `面试拷打回答手册.md` §9 在这里写过"因为回复表按 `comment_id` 分片，跟评论表同分片，所以这条 UPDATE 和 INSERT 回复在同库内，不需要分布式事务"——**该结论是错的**。评论表按 `comment_object_id % 2` 分库、回复表按 `comment_id % 2` 分库，是两个不同的键值，绝大多数情况路由到**不同库**。完整口径见 **1.10 分布式事务怎么处理**。

**代价**：爆款评论下 `reply_count` 会成为**热点行**，高频更新导致行锁竞争，主链路事务变长。

---

### 4.3 更新策略：同步 vs 异步

**方案 1：同步更新**

最直接的做法是插入回复后 `comment.reply_count = reply_count + 1`，或者删除回复时逻辑删除后 `reply_count - 1`。

- 优点：实现简单，数据短时间更一致；
- 缺点：热门评论下 `reply_count` 会成为热点行，高频更新可能导致行锁竞争，主链路事务变长。

**方案 2：异步更新**

高并发场景下更推荐：主流程先写回复表 → 发送 MQ（或 Spring Event）事件 → 由消费者异步更新 `reply_count`。

- 优点：主线程更轻，削峰效果更好，避免回复创建接口因为统计更新被拖慢；
- 缺点：`reply_count` 会短时间最终一致。

**工业级经典做法**：

- **Redis 缓冲**：发回复时先 `INCR comment:reply_count:{commentId}`，返回最新值，前台立即展示；同时发 MQ 消息异步刷 MySQL。
- **MySQL 最终一致**：MQ 消费者**批量合并**更新（如 1 秒内同一个 `commentId` 的 100 次追评合并成一条 `UPDATE ... SET reply_count = reply_count + 100`），减少行锁竞争。
- **为什么不能用 MySQL 扛高频计数**：`UPDATE` 同一行会触发行锁，InnoDB 行锁粒度是索引记录锁，几万并发追评会串行化，TPS 上限就是单核 CPU 处理能力。

---

### 4.4 我项目里的分层做法

- **普通流量场景**：可以同步更新 `reply_count`，实现简单，便于保证体验。
- **热点对象 / 高并发场景**：优先采用异步更新，主流程只保证回复写入成功，`reply_count` 允许短时间最终一致。

---

### 4.5 进一步优化手段

1. **缓存承接热点读取**：如果 `reply_count` 变成热点字段，除了更新问题还有读取问题。可以把对象维度评论统计放到 Redis——评论列表优先读缓存值，数据库作为最终兜底。
2. **批量回刷 / 定时校正**：为了避免异步更新造成长期误差，可以定期做校正——定时任务扫描热点对象，重新 `COUNT(*)`，回写 `reply_count`。
3. **爆款对象专门降级**：在极端热点场景下，评论列表可以允许 `reply_count` 短时间近似值，或优先展示缓存值，避免主库被热点统计更新打穿。

**雷点**：不要硬说本项目用了 Redis + MQ 做计数，诚实说"当前是事务内直接 UPDATE，工业级会用 Redis 缓冲 + MQ 异步刷库 + 定时校正"。

---

### 4.6 面试时要强调的点

这个问题本质上是：**用冗余字段换查询性能，再用异步化和缓存解决写热点问题**。不是单纯"要不要冗余"，而是：

> 查询性能、一致性、热点更新成本三者之间的平衡。

---

### 4.7 点赞计数（`like_count`）的并发问题

`CacheEvictListener.onCommentLiked()` 里点赞缓存是"先 `map.get(targetId)` 再 `map.put(targetId, current + delta)`"，**两步非原子**——两个并发点赞可能丢一次计数（两个人同时读到 5，各自写回 6）。

**正确做法**：`HINCRBY` / Lua 脚本 / `RMap.addAndGet`（底层即 HINCRBY）。注意还要处理"计数不能为负"（当前代码用 `Math.max(..., 0)` 兜底）。

> 这是面试官看你源码时极佳的追问点，要提前准备好"如何改进"的回答。另外 domain 层还留有 `incrementCommentLikeCache` / `incrementReplyLikeCache` 两个**从未被调用的死代码方法**，点赞数 Hash 的实际更新在 `CacheEvictListener` 里——可以坦然说"这是我重构到事件监听器后没删干净的旧方法"。

---

### 4.8 四个话题连起来的收尾话术

如果面试官连续追问"分片键 → 数据倾斜 → 表结构 → `reply_count`"这四个问题，最后可以总结成一句：

## 五、Redis 缓存与一致性

### 5.1 Redis 缓存了什么？用到什么数据类型？

**结论**：缓存了 3 类数据（4 个 key 模式），对应 3 种 Redisson 数据结构。

| Key 模式 | 数据类型 | 缓存内容 |
|---------|---------|---------|
| `comment:like:obj:{objectId}` | **Hash**（`RMap<Long, Integer>`） | 该对象下所有评论的点赞数（`commentId → likeCount`） |
| `reply:like:obj:{objectId}` | **Hash**（`RMap<Long, Integer>`） | 该对象下所有回复的点赞数（`replyId → likeCount`） |
| `user:like:{userId}:target:{type}:{targetId}` | **String**（`RBucket<String>`） | 用户是否点赞（存 `"1"`，**不设 TTL**；原 7 天 TTL 已废弃） |
| `comment:hot:obj:{objectId}:type:{type}` | **Sorted Set**（`RScoredSortedSet<Long>`） | 热评排序（score = `likeCount * 1000000 + 创建时间(小时)`，1 小时 TTL） |

**用法**：

- 查评论区时，`batchFillCommentLikeCount` 先从 Redis Hash 取点赞数，命中则覆盖 MySQL 的旧值，未命中则保留 MySQL 值。
- 用户点赞状态直接查 Redis String，不读 MySQL。
- 热评列表查 Redis ZSet 逆序取 ID，再回表查评论详情。

**为什么点赞计数用 Hash（RMap）而不是 String？为什么热评用 ZSet？**

- 一个对象下多条评论的点赞数聚合在一个 Hash 里（`comment:like:obj:{objectId}`），减少 key 数量、支持批量读取；
- ZSet 的 score 天然支持热评分数排序 + 范围分页（`valueRangeReversed`）。
- ZSet 底层是 **skiplist + hashtable**（ziplist / listpack 与 skiplist 之间有转换条件）。

---

### 5.2 热评分数公式是什么？有什么缺陷？

**第一版实现（有缺陷，已于 2026-09-14 修复）**：`score = likeCount * 100 + 当前秒时间戳`（`updateHotCommentScore` 与 `HotScoreUpdateListener` 两处各写了一遍）。

**追问与缺陷**：

- 时间戳是**秒级、量级约 1.7 × 10⁹**，而点赞项是 `likeCount × 100`。也就是说时间每前进 1 秒，需要约 **1700 万赞**才能抵消——实际效果接近"**最新优先**"，而不是"最热优先"。
- ⚠️ **注意**：不要在面试里背"点赞数差 1 就能覆盖时间差"这种说法，按上面的量级算一遍就知道是错的。
- 改进方向：把时间项改成小权重衰减（如 `likeCount * 100 - ageHours`），或换成时间衰减公式（牛顿冷却 / Reddit hot ranking）。

**✅ 修复后（当前代码）**：`score = likeCount * 1000000 + 创建时间(小时)`，公式统一收敛到 `HotScoreUtils`（原先两处各写一遍）。

- 1 个赞 = 100 万小时（约 114 年）的时间差 → **赞数主导排序，时间只在赞数相同时决定先后（新评论靠前）**；
- 用"评论创建时间"而不是"当前时间"，分数**不会随时间漂移**（原公式里老评论会越来越吃亏）；
- 已实测验证：1000 赞的 1 年前评论在原公式下输给 0 赞新评论，修复后正常胜出；
- 顺带把热评榜加了 1 小时 TTL，脏数据不会永久留在榜上。

---

### 5.3 MySQL 和 Redis 怎么保证一致性？

**结论**：采用 **Cache-Aside + 事务事件驱动 + 最终一致性**。写操作先落 MySQL，事务提交成功后通过 `Spring Event` 异步更新 Redis，确保缓存不超前于数据库。

**项目实际**：

- 点赞流程：`commentLikeRepository.save()`（MySQL）→ `commentRepository.updateLikeCount()`（MySQL）→ 事务提交 → 发布 `CommentLikedEvent` → `CacheEvictListener` 在 `AFTER_COMMIT` 阶段更新 Redis Hash。
- 删除评论：`CacheEvictListener` 直接 `delete()` 整个对象的点赞 Hash，而非逐条修改。
- 用户点赞状态：`markUserLiked()` 直接写 Redis String（**不设 TTL**，与 DB 点赞记录同生命周期；原 7 天 TTL 会导致状态位过期后重复点赞撞唯一索引，已于 2026-09-14 修正），MySQL 的 `component_comment_like` 表做持久化备份和幂等校验。

**关键注解**：

- `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`：事务回滚则不发布事件，Redis 不会脏写。
- `@Async("commentEventExecutor")`：异步线程池隔离，不影响主链路延迟。

**为什么用"事务提交后失效"，而不是提交前删缓存？**

- 考察点：Cache Aside 模式、先删缓存还是先更新库、延时双删、为什么删缓存而不是更新缓存。
- 如果在事务提交前删缓存：事务可能回滚，导致缓存被误删甚至被并发读回填旧值（脏读）。
- 追问：AFTER_COMMIT 就一定能执行吗？——**不一定**，JVM 崩溃会丢事件，需要 MQ + 本地消息表兜底（见 5.5）。

---

### 5.4 缓存穿透、击穿、雪崩怎么防？

**标准八股**：

- **穿透**：查询不存在的数据 → 布隆过滤器 / 缓存空值（追问布隆过滤器原理、误判率、删除问题）。
- **击穿**：热点 key 过期瞬间大量请求打到 DB → 互斥锁（Redisson 分布式锁）/ 逻辑过期。
- **雪崩**：大量 key 同时过期 → TTL 加随机值、多级缓存、熔断降级。

**本项目实际（诚实口径）**：

- 本项目**没有实现布隆过滤器和互斥锁**，诚实说"知道概念，项目里因为数据量和并发不高没实践，工业级会加"。
- 更需要注意的是：热评 ZSet **既没有 TTL，也没有失效 / 重建策略**，所以真实风险不是"过期击穿"，而是"**miss 重建无锁**"——ZSet 为空时并发请求会全部回源 DB 并重复写回；同时点 ZSet 的 key 在不点赞时不会被清理。
- 改进方向：设 TTL、事件驱动重建（删除 / 审核拒绝时移除）、启动预热、回源结果为空时视为未命中并清空 ZSet。

---

### 5.5 Spring Event 异步丢了怎么办？如何保证最终一致？

**锚点**：诚实回答——内存事件不可靠，生产应换 MQ（RocketMQ 事务消息 / 本地消息表）；当前方案可接受短暂不一致，**靠缓存 TTL / 定时校正兜底**（注意：当前代码里热评 ZSet 与点赞 Hash 尚未设置 TTL，属于待改进项，见 5.4）。

Spring Event 的机制与"为什么不用 MQ"详见第六章。

---

### 5.6 计数对账：Redis 计数和 MySQL 字段两份数据怎么对账？

**考察点**：计数系统架构——缓存计数定期 / 触发式落库、binlog 对账、最终一致。

**回答要点**：

- 以 MySQL 字段为**最终权威**，Redis 计数是"加速层"；
- 用定时任务或 binlog 消费做周期对账（比如按热点对象重新 `COUNT(*)` 或 `SUM`）；
- 对账差异写告警，而不是静默覆盖，避免掩盖真实的丢更新。

### 5.7 速查清单（Redis 缓存）

- **Q：Redisson 分布式锁的原理？看门狗机制？可重入怎么实现？** 考察点：Lua 脚本保证原子性、hash 存重入次数、watchdog 默认 30s 续期 1/3。
- **Q：Redis 为什么快？单线程模型？6.0 多线程是什么？**
- **Q：Redis 持久化？** RDB vs AOF、混合持久化。
- **Q：Redis 集群？** 主从复制、哨兵、Cluster 分片（16384 槽位）、槽位迁移。
- **Q：大 key / 热 key 怎么发现和治理？** 你的热评 ZSet 如果某个爆款对象有几百万评论就是大 key。
- **Q：Redis 内存淘汰策略？** LRU / LFU / 随机；过期删除策略：惰性删除 + 定期删除。
- **Q：RMap 的 get + put 两步有并发问题吗？** 见 4.7。

## 六、Spring Event 与异步 / 线程池

### 6.1 你把什么异步化了？主链路精简了什么？

`CommentDomainService.createComment()` 主事务内只做两件事：

1. `INSERT component_comment`；
2. `INSERT component_comment_audit`（默认审核记录）。

然后 `publishEvent(new CommentCreatedEvent(...))`。事务提交后，异步监听器分别执行：

- `UserIndexUpdateListener`：写 `component_user_comment_index`；
- `NotificationListener`：给评论作者发通知（回复场景）；
- `HotScoreUpdateListener`：更新 Redis ZSet 热评分数 + 审核拒绝时移除；
- `CacheEvictListener`：清理 / 更新点赞缓存。

**优化逻辑**：如果把"写索引 + 写通知 + 更新热评"全放在主事务里，主事务持有数据库连接时间变长，且下游故障会导致主事务回滚（**通知失败不该影响评论发布**）。异步化后，主链路只负责"评论发布成功"这个核心承诺，旁路逻辑最终一致。

---

### 6.2 Spring Event 异步监听原理是什么？

**结论**：Spring 的 `ApplicationEventMulticaster` 负责事件广播；`@TransactionalEventListener` 把监听器注册到 `TransactionSynchronization` 中，事务 `commit` 后才触发回调；`@Async` 通过 AOP 代理把回调逻辑交给线程池执行。

**详细流程**：

1. 业务代码 `eventPublisher.publishEvent(new CommentCreatedEvent(...))`，事件进入 `ApplicationEventMulticaster` 的监听器列表。
2. 如果监听器标了 `@TransactionalEventListener`，Spring 把它挂到当前事务的 `TransactionSynchronizationManager` 中，而**不是立即执行**。
3. 事务提交成功后（`afterCompletion` 状态为 `COMMITTED`），Spring 调用 `TransactionSynchronization.afterCommit()`，触发事件。
4. 如果方法还标了 `@Async`，Spring 用 `AopProxy` 生成代理，把调用包装成 `Runnable` 提交给 `TaskExecutor`（本项目是 `commentEventExecutor` 线程池）。
5. 如果事务回滚，事件不会触发。

**项目配置**：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Async("commentEventExecutor")
public void onCommentCreated(CommentCreatedEvent event) { ... }
```

**核心价值**：用 `AFTER_COMMIT` 避免"数据没落库但缓存 / 热榜已更新"的脏写。

---

### 6.3 `@TransactionalEventListener` 和 `@EventListener` 的区别？各个 Phase？

**考察点**：观察者模式、`ApplicationEventMulticaster`、默认同步执行，`@Async` 才走线程池。

**Phase 说明**：

- `AFTER_COMMIT`：事务提交成功后触发（**本项目全部监听器都用这个**）；
- `AFTER_ROLLBACK`：事务回滚后触发，适合做补偿 / 清理；
- `AFTER_COMPLETION`：无论提交还是回滚都触发；
- `BEFORE_COMMIT`：提交前触发，此时还在事务内。

**锚点**：项目里全部监听器都用 `AFTER_COMMIT` + `@Async("commentEventExecutor")`，要能解释为什么——旁路操作不能在主事务内做，且不能因为主事务回滚而脏写缓存。

---

### 6.4 为什么不直接用 MQ 而用 Spring Event？

- 事件量不大（发评论 / 点赞的频率），Spring Event 足够轻量，不需要引入 Kafka / RabbitMQ 的运维复杂度。
- 如果事件丢了，后果是"通知没发"或"索引没更新"，不是核心数据丢失，可以容忍。
- **不要说"Spring Event 是 MQ 的替代品"**。应该说："在轻量级场景下替代 MQ、降低复杂度；事件定义与消费方式解耦，工业级量大时可以把事件层换成 MQ 生产者、监听器换成消费者，**事件契约不用改**。"
- **诚实边界**：内存事件不可靠，JVM 崩溃会丢未消费事件，需要 MQ + 本地消息表兜底；工业级量大时应该换 MQ + 死信队列。

---

### 6.5 线程池参数怎么配的？`corePoolSize=4 / max=16 / queue=500` 怎么定的？

**项目配置**：

```java
@Bean("commentEventExecutor")
public Executor commentEventExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(500);
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    // ...
}
```

**考察点**：线程池参数估算（CPU 密集 N+1、IO 密集 2N 或更高）、任务执行流程（先 core → 队列 → max → 拒绝策略）。

**回答锚点**：监听器任务是 IO 密集（写库、写 Redis），CPU 核数不高时不需要太大；队列 500 是缓冲削峰，超过后触发 `CallerRunsPolicy`。

---

### 6.6 为什么选 `CallerRunsPolicy` 拒绝策略？四种拒绝策略分别是什么？

**回答锚点**：`CallerRunsPolicy` 让提交任务的业务线程自己执行，相当于**反压降速**——保证事件不丢，但会拖慢主链路（这也是高并发下写链路延迟上升的一个来源）。

**四种拒绝策略**：

- `AbortPolicy`：直接抛 `RejectedExecutionException`（默认）；
- `CallerRunsPolicy`：调用者线程执行；
- `DiscardPolicy`：静默丢弃；
- `DiscardOldestPolicy`：丢掉队列里最老的任务再提交。

---

### 6.7 `@Async` 失效场景？异步线程里 ThreadLocal 会丢吗？优雅停机怎么做？

- **`@Async` 失效**：自调用（同类内部方法调用绕过代理）、方法非 `public`、未开启 `@EnableAsync`。
- **ThreadLocal 会丢**：项目里有 `UserContext`（ThreadLocal 存登录用户），异步监听器里**拿不到主线程的用户上下文**——所以事件对象必须携带全部数据。这是非常实际的追问点。
- **优雅停机**：线程池 `shutdown` 时 `setWaitForTasksToCompleteOnShutdown` 用于等待已提交任务执行完再退出，避免异步事件在停机时被截断。

## 七、MySQL 与 SQL

### 7.1 评论列表查询的索引怎么建的？

**考察点**：联合索引最左前缀、索引下推、覆盖索引。

**回答锚点**：DDL 中：

- 评论表 `idx_object (comment_object_id, comment_type, is_delete, sort, create_time)` —— 字段顺序与"按对象过滤 + 未删除 + 置顶排序 + 时间排序"的查询完全对齐；
- 回复表 `idx_comment (comment_id, parent_reply_id, is_delete)`；
- 点赞表唯一索引 `uk_user_target (user_id, target_id, target_type)`。

---

### 7.2 点赞表的唯一索引起什么作用？

**幂等防重**：同一用户对同一目标只能点赞一次，DB 层兜底"请勿重复点赞"。应用层给友好提示，DB 层保证最终正确。

---

### 7.3 "先查再插入点赞记录"有没有并发问题？

**有。** `like()` 是先在应用层 `exists` 查询再 `save`，两个并发请求可能都通过校验。

**锚点**：靠 `uk_user_target` **唯一索引兜底**——这就是"代码校验 + DB 约束"双保险的经典案例。可以说："我故意保留唯一索引做最后防线。"

---

### 7.4 深分页问题：`limit 100000, 20` 为什么慢？怎么优化？

- **为什么慢**：MySQL 会先扫描并丢弃前 100000 行，再取 20 行，代价随 offset 线性增长。
- **优化**：延迟关联（先用覆盖索引拿到主键再回表）、游标分页（`where id > last_id`）、业务上限（只允许翻 N 页）、复杂检索交给 ES。

---

### 7.5 `count(*)` 大表慢怎么办？

项目分页都会先 `countByObject`。分片后单表数据量可控；进一步可以用近似计数、缓存计数（Redis 维护计数），或把 `count(*)` 换成"是否还有下一页"的判断（`limit pageSize + 1`）。

---

### 7.6 事务隔离级别？RR 怎么解决幻读？

- 常见答法：MySQL 默认 RR，通过 **MVCC + Next-Key Lock** 解决幻读（快照读靠 MVCC，当前读靠 Next-Key Lock）。
- 结合项目：点赞的 `exists + save` 在 RR 下仍可能并发通过，所以最终防线是唯一索引（见 7.3）。

---

### 7.7 InnoDB 为什么用 B+ 树？和 B 树、哈希索引的区别？

- **B+ 树**：非叶子节点只存索引、不存数据，扇出大、树更矮（3 ~ 4 层即可支撑千万行），叶子节点用链表相连，天然支持范围查询与顺序扫描——这正是评论列表"按对象过滤 + 按时间排序"的高频场景。
- **vs B 树**：B 树的非叶子节点也存数据，扇出更小、树更高，范围查询需要中序遍历回跳。
- **vs 哈希索引**：等值查询 O(1)，但不支持范围查询和排序；InnoDB 的自适应哈希索引（AHI）是引擎内部优化，用户不能直接建。
- **结合项目**：`idx_object (comment_object_id, comment_type, is_delete, sort, create_time)` 这类联合索引能同时承接过滤和排序，正是因为 B+ 树叶子节点有序。

---

### 7.8 explain 关注哪些字段？什么情况下索引失效？

- **关注的字段**：
  - `type`：访问类型，出现 `ALL`（全表扫描）要警惕，`ref` / `range` / `index` 一般可接受；
  - `key` / `key_len`：实际用了哪个索引、用到了联合索引的几列；
  - `rows`：预估扫描行数；
  - `filtered`；
  - `Extra`：`Using index`（覆盖索引）是好的；`Using filesort`、`Using temporary` 要警惕。
- **索引失效常见场景**：对索引列做函数 / 运算、隐式类型转换（字符串列传数字）、`like '%xx'` 前导通配、`OR` 连接非索引列、联合索引不满足最左前缀、`!=` / `NOT IN` 让优化器放弃索引（视数据分布而定）。
- **结合项目**：`is_delete = 0` 这种低区分度字段放在联合索引中段，是为了配合索引下推；定位问题要看 `EXPLAIN`，不要靠猜。

---

## 八、分布式 ID / 雪花算法

### 8.1 雪花算法的结构？优缺点？

自研 **雪花算法** `SnowflakeIdUtils`：**41bit 时间戳 + 5bit 数据中心 + 5bit 机器 + 12bit 序列号**。

- 优点：全局唯一、趋势递增；
- 缺点：依赖系统时钟、机器 ID 需要分配。

**分库分表后为什么必须换掉自增 ID**：分表后自增 ID 会冲突（每张表各自从 1 开始），雪花 ID 全局唯一。

---

### 8.2 时钟回拨怎么处理？

当前代码是**直接抛异常**（`throw new RuntimeException("时钟回拨")`）。

**追问生产方案**：小回拨等待、大回拨切换机器位 / 报警，或用美团 Leaf、百度 UidGenerator。

---

### 8.3 雪花 ID 在分库分表场景有什么额外好处？

- 全局唯一，避免分表后自增冲突；
- **趋势递增**，利于 B+ 树顺序插入，减少页分裂；
- 可解析出时间，便于排查和归档。

---

### 8.4 为什么不用数据库自增 ID？分表后自增会重复吗？

**会重复**：每张物理表独立自增，`component_comment_0` 和 `component_comment_1` 都会产生 `id = 1`。

所以分库分表后必须使用全局唯一 ID 方案：雪花算法 / 号段模式（Leaf-segment）/ UUID / Redis INCR。UUID 无序且占空间，不利于 B+ 树插入；号段模式需要额外的号段服务；雪花算法无中心化依赖，所以项目选了它。

## 九、架构设计与 DDD

### 9.1 什么是 DDD 四层架构？你的项目每层放什么？

**回答锚点**：

- **start（接口层）**：Controller / VO / 拦截器 / 自研基础组件；
- **application（应用层）**：`CommentBizService`、事件监听器（`UserIndexUpdateListener`、`NotificationListener`、`HotScoreUpdateListener`、`CacheEvictListener`）；
- **domain（领域层）**：`CommentDomainService`、实体、仓储接口、分片路由、雪花 ID；
- **infrastructure（基础设施层）**：Mapper、仓储实现、外置配置。

**追问：领域层为什么只依赖仓储接口不依赖 Mapper？** —— 依赖倒置，防腐。领域层定义仓储接口，基础设施层提供实现，避免领域逻辑绑定具体持久化技术。

**诚实边界（可主动说）**：domain 模块目前仍直接依赖 Redisson（`RMap` / `RScoredSortedSet`）和 Spring，属于"贫血模型 + 基础设施依赖"的务实取舍；严格 DDD 应该抽 `CachePort` 接口再由基础设施实现。

---

### 9.2 DDD 和 MVC / 三层架构的区别？贫血模型 vs 充血模型？

- 三层架构按"技术职责"分层（Controller / Service / DAO），DDD 按"业务边界"分层（接口 / 应用 / 领域 / 基础设施），领域层承载业务规则，可以脱离框架单测。
- 贫血模型：实体只有字段 + getter/setter，逻辑全在 Service；充血模型：实体自带业务行为。
- **诚实回答**：我的实体基本还是贫血模型，逻辑集中在 `CommentDomainService`；DDD 主要落地在分层与依赖方向上。

---

### 9.3 什么是中台？评论中台解决了什么问题？

- **问题**：各业务线（题解社区、二手交易等）独立建设评论功能，导致**重复开发**与**数据孤岛**。
- **解法**：用统一模型抽象不同业务线——`comment_object_id` + `comment_type` 表示"对什么对象评论"，评论能力（发布、回复、点赞、热评、审核、通知、反查）统一沉淀到中台，业务线只传对象 ID 和类型。
- **收益**：能力复用、口径统一、一次优化多业务线受益。

---

### 9.4 二级扁平化回复模型是什么？为什么不用无限级嵌套？

要点：`comment_id` 负责归属、`parent_reply_id` 负责树结构、`reply_type` 只保留两态语义、`be_replied_user_id` 负责"回复给谁"；列表查询只挂前 N 条（`topReplyLimit` 默认 3），展开时按 `comment_id + parent_reply_id` 查楼中楼。**消除递归查询**是核心收益。详见第三章。

---

### 9.5 评论系统的读扩散 vs 写扩散？

如果做"关注的人评论流"，就是 Timeline 推拉模式问题：

- **写扩散（推）**：发布时写入所有粉丝的收件箱，读便宜写昂贵，适合粉丝量小的场景；
- **读扩散（拉）**：读时聚合关注列表，写便宜读昂贵，适合大 V 场景；
- 工业界常用**推拉结合**：普通用户推、大 V 拉。

## 十、性能与压测数字

### 10.1 真实压测数据（唯一出处：`loadtest/REPORT.md`）

> ⚠️ **纠错**：旧版 `面试拷打回答手册.md` §10 的标题是"**P95 从 240ms 降到 140ms**，怎么优化的？"——**240ms → 140ms 是已废弃的旧估算数字，禁止再使用**。以下是 k6 实测数据（单机环境、jar 部署 8080、MySQL 8.0 容器、Redis 6379、预置热对象 `comment_object_id=10001` 共 1 万条评论，运行时关闭 SQL-show 与 MyBatis 调试日志）。

| 场景 | 并发 | 吞吐 | P99 | 错误率 |
|---|---|---|---|---|
| 评论列表 `list` | 20 | 358 QPS | 135ms | 0% |
| **评论列表 `list`** | **50** | **429 QPS** | **218ms** | **0%** |
| 评论列表 `list` | 100 | 372 QPS | 513ms | 0% |
| 评论列表 `list` | 200 | 380 QPS | **917ms**（max 1.32s） | 0% |
| 热评 `hot` | 20 | 444 QPS | 96ms | 0% |
| 创建 `create` | 20 | ≈1498 TPS（≈1.5k） | 41ms | 0% |

**一句话口径**：读链路峰值 **~430 QPS（50 并发，P99 218ms）**；热评缓存读 **~440 QPS（P99 96ms）**；写链路 **~1.5k TPS（P99 41ms）**；并发加到 200 时吞吐趋稳 **~380 QPS**、P99 升至 **917ms**，**全程 0 错误**。

---

### 10.2 怎么解读这个拐点？

吞吐在 **50 并发时到顶 ≈430 QPS**（P99 218ms），之后加并发**吞吐不再增长**（稳定在 370 ~ 380 QPS），延迟急剧恶化到 P99 917ms。这是标准的**饱和曲线**：加并发不加吞吐、只加延迟 → 系统容量接近 MySQL / 连接池上限。

**原因**：读主链路是 **DB 密集**（`list` 每次都回源 MySQL，无列表级缓存），HikariCP 每库 `maximum-pool-size=20`，连接池打满后请求排队 → 用**排队论 / Little 定律**解释：`并发 = 吞吐 × 响应时间`，吞吐封顶后并发增加只能推高响应时间。

---

### 10.3 为什么写比读还快（1.5k TPS vs 430 QPS）？

- 写链路主链路只做"校验 + 写库 + 发事件"，重活（缓存、热度、通知、索引）被 Spring Event 异步剥离；
- 写测试是**分散对象 ID**（`10001 ~ 11200`），写入均匀落在 2 库 × 4 表，没有单分片写竞争；
- **注意主动说明**：如果压单个热对象（全写同一分片），数值会明显下降。

---

### 10.4 为什么热评比普通列表快（444 vs 358）？

热评走 Redis ZSet 取 ID 再回表，排序在 Redis 完成；但要注意**它仍然回表查详情**，所以不是纯缓存命中。ZSet 里只存一级评论 ID。

---

### 10.5 主链路精简 + 异步化是怎么做的？（原 §10 的优化逻辑）

**结论**：核心手段是**主链路精简 + 异步化旁路逻辑**。发评论 / 回复时，主事务只写核心表（评论表 + 审核表），用户索引、站内通知、热评分数等通过 `Spring Event` 异步监听器在事务提交后执行。

**项目实际**：

- `CommentDomainService.createComment()` 的主事务内只做两件事：插入 `component_comment`、插入默认审核记录 `component_comment_audit`；
- 然后发布 `CommentCreatedEvent`；
- 事务提交后，异步监听器分别执行：`UserIndexUpdateListener`（写用户索引）、`NotificationListener`（发通知）、`HotScoreUpdateListener`（更新热评 ZSet）、`CacheEvictListener`（清理 / 更新点赞缓存）。

**优化逻辑**：

- 原来如果把"写索引 + 写通知 + 更新热评"全放在主事务里，主事务持有数据库连接时间变长，且下游故障会导致主事务回滚（通知失败不该影响评论发布）。
- 异步化后，主链路只对"评论发布成功"负责，旁路逻辑最终一致。
- **收益用实测数据说话**：写链路（创建评论）实测 **≈1.5k TPS / P99 41ms / avg 13.3ms**；而读链路因为无列表级缓存是 DB 密集，反而成为瓶颈（见 10.1、10.2）。

**线程池配置**：见 6.5（`core=4 / max=16 / queue=500 / CallerRunsPolicy`）。

---

### 10.6 怎么发现和定位瓶颈？

- 看日志全链路耗时（日志打印 SQL 执行时间）；
- 看 MySQL 执行计划（`EXPLAIN`），确认是否命中索引；
- 看连接池监控（HikariCP），确认是否因事务过长导致连接池耗尽；
- 看 MySQL 连接数 / `Threads_running`（压测期间 `Threads_connected` 空闲 ~42 → 峰值 **101**，`Threads_running` 峰值 47）；
- 看 Redis 命中情况（压测期间 ~100 万+ hits / **1 miss**，缓存命中极佳，**Redis 不是瓶颈**）。

**结论**：**瓶颈是 MySQL 与连接池**，不是 Redis。

---

### 10.7 找到瓶颈后怎么优化？

① 连接池限流（信号量 / Hystrix，把 101 收敛到 40 并快速失败）；② 列表级缓存（第一页整页缓存）；③ 读写分离；④ ES 承接复杂检索。追问每个方案的细节时要能展开取舍。

---

### 10.8 压测暴露了什么问题？（加分项）

1. **热评缓存与库不一致（真实 BUG）**：Redis `comment:hot:obj:10001:type:1` 若残留**旧 ID**，`queryByIds` 会因 `where id in (...) and comment_object_id = 10001` 匹配不到而返回空列表，导致 hot 接口"有数据却返回空"。根因是 ZSet 没有 TTL、也没有失效 / 重建策略（见 5.4）。
2. **连接数跑到 101，超过配置预期**：配置 `maximum-pool-size: 20`（`ds_0` / `ds_1` 各一个，合计 40），但压测后 `Threads_connected` 恒为 101。可能是 ShardingSphere YAML 里 Hikari 参数没按 `hikari:` 嵌套绑定生效，也可能是额外连接来源。**这也解释了为什么全程 0 错误**——连接没被真正限流，请求在 HTTP 线程里排队而非被连接池拒绝；若把池严格限到 40，高并发下很可能出现 `Connection is not available` 超时。

> 这是一个"发现问题比跑出数字更有价值"的例子。详见 `loadtest/REPORT.md` §3、§4。

### 10.10 速查清单（性能 / 压测基础）

- **Q：P99 和 avg 为什么要分开看？** avg 会被大量快请求拉平，P99 反映长尾体验；容量规划要看尾部延迟，压测里 P99 先恶化往往意味着排队开始。
- **Q：k6 压测和 JMeter 的区别？阶梯压测（ramping VUs）怎么设计？** k6 用 JS 脚本、原生输出 P50/P95/P99 与错误率、资源占用低；阶梯压测按档位（1 → 25 → 50 → 100 → 150 → 200，每档 30s）观察吞吐拐点。
- **Q：QPS / TPS / RT / 并发数的关系？单机 Tomcat 默认线程数（200）对容量意味着什么？** `并发 = 吞吐 × RT`（Little 定律）；Tomcat 默认 200 工作线程是另一道隐性上限——连接池（40）与工作线程（200）要一起看，否则会出现"线程都在等连接"的排队。
- **Q：压测时为什么要把 `sql-show` 和 MyBatis 调试日志关掉？** 默认配置每条 SQL 打日志会严重拉低吞吐、污染数据（同步日志的 IO 开销）；这也是"压测环境要与生产配置对齐、只改必要参数"的典型例子。

## 十一、Java / Spring 基础

### 11.1 `@Transactional` 失效的场景？

自调用（同类内部调用不走代理）、方法非 `public`、异常被吞、`rollbackFor` 不匹配（默认只对 `RuntimeException` 回滚）。

**锚点**：项目代码显式写了 `@Transactional(rollbackFor = Exception.class)`，要能解释为什么——把受检异常也纳入回滚范围，避免"写了一半没回滚"。

---

### 11.2 事务传播机制？`REQUIRED` / `REQUIRES_NEW` / `NESTED` 的区别？

- `REQUIRED`（默认）：有事务就加入，没有就新建；
- `REQUIRES_NEW`：挂起当前事务，自己开一个新事务（适合"旁路日志必须独立提交"）；
- `NESTED`：嵌套事务，用保存点实现，外层回滚会连带内层，内层回滚不影响外层。

---

### 11.3 Service 里用 HashMap 做 carrier 传递批量查询结果，线程安全吗？

**不安全，这是一个真实的代码隐患。**

`commentLikedCarrier` / `replyLikedCarrier` / `commentLikeReplyCarrier` 是 `CommentDomainService` 这个**单例 Bean 的成员变量**（`HashMap`，非线程安全），在方法入口 `clear()`、过程中 `put()`、最后读。多线程并发时 A 用户的 `liked` 状态可能串给 B 用户，甚至 `clear()` 互相踩踏。

**正确做法**：改成方法返回值携带、或方法内局部变量、或用 `ThreadLocal`（但异步场景仍有上下文问题）。

> 这是面试官看 GitHub 源码最可能点的问题，务必准备好"已发现并知道如何修"的回答。

---

### 11.4 `HashMap` 和 `ConcurrentHashMap` 的区别？

- `HashMap` 线程不安全，多线程 `put` 可能丢数据 / 结构损坏；
- `ConcurrentHashMap` 通过 CAS + `synchronized`（JDK8，锁单个桶）保证线程安全；JDK7 用分段锁（Segment）。

---

### 11.5 `ThreadLocal` 原理？内存泄漏？`InheritableThreadLocal` 能解决异步传递吗？

- 原理：每个 `Thread` 持有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 弱引用，value 强引用；
- 内存泄漏：线程池里线程长期存活，`ThreadLocal` 被回收后 value 仍挂在 Entry 上——所以必须 `remove()`；
- `InheritableThreadLocal` 只在**创建子线程**时复制，线程池里的线程是复用的，所以**不能**可靠解决异步上下文传递——项目里异步监听器拿不到 `UserContext`，只能靠事件对象携带数据。

---

### 11.6 Spring Bean 的生命周期？IOC / AOP 原理？AOP 在 `@Transactional` / `@Async` 中怎么体现？

- 生命周期：实例化 → 属性注入 → `BeanNameAware`/`BeanFactoryAware` → `BeanPostProcessor` 前置 → `@PostConstruct` / `InitializingBean` → 后置处理（AOP 代理在这里生成）→ 使用 → 销毁。
- AOP 原理：动态代理——目标类有接口用 JDK 动态代理，否则用 CGLIB 子类代理。
- `@Transactional` / `@Async` 都靠代理拦截：前者在方法前后开启 / 提交事务，后者把调用包装成 `Runnable` 提交线程池。**这也是"自调用会失效"的根因**。

---

### 11.7 Spring Boot 自动装配原理？

`@SpringBootApplication` 里的 `@EnableAutoConfiguration` 通过 `@Conditional` 系列按条件筛选配置类；Spring Boot 2.7 之前读 `spring.factories`，之后读 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。

## 十二、业务设计开放式追问

### 12.1 全链路架构：用户发一条带图评论，从点击提交到前端展示，整个链路怎么设计？

**结论**：分 5 层——客户端 → 网关 → 应用层 → 存储层 → 回显。

**工业级全流程**：

1. **客户端**：图片先走独立上传通道到 **OSS / CDN**，拿到 URL 后再提交评论内容（避免评论接口带宽被图片占满）；前端做防抖，3 秒内重复点击只发一次。
2. **网关层（Nginx / Gateway）**：限流（单用户 1 秒最多 1 条评论，令牌桶）；防刷（IP + 用户维度限流）；就近接入（CDN 节点或边缘机房，减少网络 RTT）。
3. **应用层（Spring Boot）**：参数校验 + 敏感词过滤（Trie 树或调用审核服务）；主事务写评论表 + 审核表（默认通过）；发布 Spring Event，异步写用户索引、通知、热评分数、缓存。
4. **存储层**：MySQL 评论主表按 `object_id` 分片，保证单点写入；Redis 缓存点赞数、热评排序；图片 / 视频 OSS 存原图，CDN 边缘缓存缩略图。
5. **回显**：前端轮询或长连接（WebSocket / SSE）拉取新评论；或者用户刷新页面时从缓存读取最新列表。

**网络层优化（阿里国际追问）**：

- **SSL 卸载**：TLS 握手在网关层（Nginx / OpenSSL）完成，后端服务走明文 HTTP，减少 CPU 消耗；
- **同机架部署**：评论服务、MySQL 主库、Redis 尽量同机房甚至同机架，降低网络跳数和延迟；
- **连接池**：HikariCP 配置 `maximum-pool-size: 20`，避免连接数爆炸；
- **独立带宽**：图片上传走独立域名和带宽通道，不影响文本 API。

---

### 12.2 评论删除是物理删除还是逻辑删除？为什么？

项目用 `is_delete` **软删**。原因：删除要可追溯（审核、申诉、恢复），且评论被通知 / 索引 / 热评多处引用，物理删除会产生悬空引用。

**追问：软删数据膨胀怎么治理？** —— 低频评论可归档到历史表 / 冷存储，热点表只保留活跃数据；或者按时间分表后整表归档。

---

### 12.3 删除一级评论时，下面的回复怎么处理？

两种方案：

- **级联标记删除**：把该评论下所有回复一并标记删除（一致性好，但写放大）；
- **保留占位**：只标记一级评论删除，前端展示"该评论已删除"，回复保留（读时需处理占位展示）。

项目当前是软删标记，选择哪一种取决于业务对"回复上下文"的需求。

---

### 12.4 先发后审 vs 先审后发怎么选？你的审核流转怎么设计的？

- **先审后发**：合规压力小，但用户体验差（评论要等审核）。
- **先发后审**：体验好，需要"审核拒绝后的补偿"。
- **项目锚点**：项目有先发后审改造方案 + 审核回调接口（`handleAuditCallback`）；审核拒绝时热评 ZSet 移除（`HotScoreUpdateListener` 监听 `CommentAuditChangedEvent`）、回复数回退——要把这些**一致性补偿逻辑**讲清楚。
- 审核状态机与 `component_comment_audit` 记录表配合，审核表不分片、固定落 `ds_0`（这也是跨库写路径之一，见 1.10）。

---

### 12.5 点赞接口怎么做幂等？防刷怎么做？

- **幂等**：`uk_user_target (user_id, target_id, target_type)` 唯一索引 + 应用层 `exists` 预校验 + Redis 标记（`user:like:...`）做快速判断（见 7.2、7.3）；
- **防刷**：网关层 IP + 用户维度限流、单用户 QPS 上限、异常行为检测（短时间大量点赞不同目标）。

---

### 12.6 评论通知怎么实现的？消息过多怎么办？

**项目实现**：`NotificationListener` 监听 `ReplyCreatedEvent`（以及点赞等事件）写 `component_notification` 表，该表按 `user_id` 分片，支撑"我的通知"单点查询。

**追问：消息过多怎么办？**

- **聚合通知**："xx 等 100 人赞了你"，把同类通知合并成一条；
- **已读未读**：用 Redisson 计数（未读数）而不是每次 `count(*)`；
- **分级**：重要通知（被回复）实时推，次要通知（点赞）合并或降频。

---

### 12.7 如果接入一个新的业务线（比如直播弹幕），你的中台模型怎么扩展？

- 复用统一模型：传新的 `comment_type` 即可，**分片键不变**（评论仍按 `comment_object_id`），不需要改表结构、不需要改分片算法；
- 需要单独评估的是**量级差异**：弹幕的写 QPS 远超评论，需要单独限流 / 削峰 / 甚至独立集群，而不能直接吃同一个连接池；
- 这正是中台的价值：**能力复用 + 隔离治理**。

### 13.2 建议主动坦白的代码隐患（加分项）

建议主动讲："我复盘时发现了这几个问题，改进方案是……"——把被动拷问变成主动展示复盘能力。

1. **点赞数缓存 `get` + `put` 竞态**（见 4.7）：改进用 `RMap.addAndGet` 或 Lua。
2. **`CommentDomainService` 用成员变量 HashMap 传中间结果**（见 11.3）：改成返回值携带或局部变量。**这是面试官看 GitHub 源码最可能点的问题**。
3. **`like()` 的 `exists` + `save` 并发窗口**（见 7.3）：靠 `uk_user_target` 唯一索引兜底，属"代码校验 + DB 约束"双保险。
4. **主事务里的跨库写入窗口**（见 1.10）：`createReply` 与 `createComment` 两条路径都可能跨库；本地事务无法跨库保证原子性。改进是把非主记录写入移到 `AFTER_COMMIT` 监听器或 MQ 消费端。
5. **死代码**：`incrementCommentLikeCache` / `incrementReplyLikeCache` 从未被调用，属重构遗留。
